## Definition

The mandatory non-B-tree, non-GIN [bloat](../../glossary.md#bloat) tests are this wiki's shared **measurement protocol** for any claim about how much space a PostgreSQL 17 index is wasting, or how much a rebuild would return, when the index's [access method](../../glossary.md#access-method) is neither [B-tree](../../glossary.md#b-tree) nor [GIN](../../glossary.md#gin). Four core access methods are scored under it - [hash](../../glossary.md#hash-index), [GiST](../../glossary.md#gist), [SP-GiST](../../glossary.md#sp-gist) and [BRIN](../../glossary.md#brin) - and a fifth rule admits a non-core index AM such as [`contrib/bloom`](../../glossary.md#contrib) or one installed by `CREATE ACCESS METHOD`. The protocol fixes ten things and nothing else: the five phases every scored fixture runs; the per-AM proof that the index work actually ran, because a [`VACUUM`](../../glossary.md#vacuum) that returned is not evidence that the index was touched; the maintenance step and census that stand in for [autovacuum](../../glossary.md#autovacuum) and auto-analyze so that no fixture is scored against unmaintained churn; the prohibition on defeating that maintenance, because a `VACUUM ANALYZE` can be skipped, cancelled or stripped of its [removal horizon](../../glossary.md#xmin-horizon) and still return success; the BRIN summarization stand-in, because on BRIN the maintenance step *adds* index [tuples](../../glossary.md#tuple) rather than removing them; the [`SHARE ROW EXCLUSIVE`](../../glossary.md#lock-mode) measurement lock; one oracle, a measured [`REINDEX INDEX`](../../glossary.md#reindex) bracketed by [`pg_relation_size(index, 'main')`](../../glossary.md#relation-size-functions), together with the per-AM inputs that oracle depends on; the declaration of every published quantity as a lower bound, an upper bound or a level; the per-AM instrument matrix, which decides what a run is allowed to read at all; and the cross-checks and reading rules. It deliberately does **not** define a fixture corpus: the numbered fixtures, their recipes and their results stay on the question page that runs them, and this page is what that page must state it followed. Every scored fixture assumes that normal autovacuum and auto-analyze maintain every table, and stands in for both by hand: after its churn it runs `VACUUM ANALYZE` on every table the churn touched, and a BRIN fixture whose point is autosummarization also runs the summarization that only an autovacuum worker performs.

## Why It Exists

Eleven properties of the v17 engine make a plausible reading of these four access methods wrong, and each is the reason one protocol rule exists.

**No instrument covers all four, and two of them are refused outright.** [`pgstattuple`](../../glossary.md#pgstattuple)'s dispatch sends a B-tree, a hash and a GiST index to its generic index scan and raises "is not supported" for SP-GiST and BRIN ([pgstattuple.c#pgstat_relation-dispatch](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple.c#L260-L297)). `contrib/pgstattuple` ships exactly one AM-specific reader for this set, `pgstathashindex` ([pgstatindex.c#pgstathashindex](../../../raw/postgres-17/contrib/pgstattuple/pgstatindex.c#L579-L610), [pgstattuple--1.4--1.5.sql#pgstathashindex](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple--1.4--1.5.sql#L121-L136)). [`contrib/pageinspect`](../../glossary.md#pageinspect) ships page decoders for hash, GiST and BRIN and none for SP-GiST ([hashfuncs.c#functions](../../../raw/postgres-17/contrib/pageinspect/hashfuncs.c#L25-L29), [gistfuncs.c#functions](../../../raw/postgres-17/contrib/pageinspect/gistfuncs.c#L30-L32), [brinfuncs.c#functions](../../../raw/postgres-17/contrib/pageinspect/brinfuncs.c#L30-L33), [pageinspect.sgml#gist-funcs](../../../raw/postgres-17/doc/src/sgml/pageinspect.sgml#L724-L725), [pageinspect.sgml#hash-funcs](../../../raw/postgres-17/doc/src/sgml/pageinspect.sgml#L814-L815)). [`contrib/amcheck`](../../glossary.md#amcheck) 1.4 verifies B-tree indexes and heaps only ([amcheck.control:3](../../../raw/postgres-17/contrib/amcheck/amcheck.control#L3), [amcheck--1.3--1.4.sql#bt-only](../../../raw/postgres-17/contrib/amcheck/amcheck--1.3--1.4.sql#L13-L25)). A method built on a composite of these has no single refusal to hide behind, which is why the protocol scores the number rather than the tool.

**None of these access methods returns a [block](../../glossary.md#block) to the operating system.** The only truncation code in any index AM is compiled out: `spgvacuumscan` carries a `RelationTruncate` call inside `#ifdef NOT_USED`, with a comment naming concurrent inserts and the [metapage](../../glossary.md#metapage)'s cached free-space pointers as the reasons, and stating that B-tree does not do this either ([spgvacuum.c#truncation-disabled](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L877-L900)). The hash README says the same in prose: there is no provision to shrink a hash index other than `REINDEX`, overflow pages are recycled but never given back, and the bucket count never shrinks ([README#no-shrink](../../../raw/postgres-17/src/backend/access/hash/README#L31-L34)). So the only ground truth for "how many bytes would a rebuild return" is a rebuild.

**Each AM hands reclaimed space to a different registry, so "free" means three different things.** GiST and SP-GiST record a reusable [page](../../glossary.md#page) in the index [free space map](../../glossary.md#free-space-map), which stores only free-versus-in-use and writes `BLCKSZ - 1` for a free page ([gistvacuum.c#gistvacuumpage-classes](../../../raw/postgres-17/src/backend/access/gist/gistvacuum.c#L298-L309), [spgvacuum.c#spgvacuumpage-fsm](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L665-L683), [indexfsm.c#index-fsm-notes](../../../raw/postgres-17/src/backend/storage/freespace/indexfsm.c#L14-L20), [indexfsm.c#RecordFreeIndexPage](../../../raw/postgres-17/src/backend/storage/freespace/indexfsm.c#L47-L55)). BRIN uses the graduated heap-style API instead, recording the actual free space of every regular page ([brin_pageops.c#brin_page_cleanup](../../../raw/postgres-17/src/backend/access/brin/brin_pageops.c#L610-L661), [brin_pageops.c#br_page_get_freespace](../../../raw/postgres-17/src/backend/access/brin/brin_pageops.c#L913-L927)). Hash uses neither: a freed overflow page is re-initialized as `LH_UNUSED_PAGE` and its bit is cleared in the index's own bitmap pages, and the allocator finds it again by scanning those bits ([hashovfl.c#_hash_freeovflpage-bitmap](../../../raw/postgres-17/src/backend/access/hash/hashovfl.c#L601-L642), [hashovfl.c#_hash_getovflpage-bitmap](../../../raw/postgres-17/src/backend/access/hash/hashovfl.c#L222-L252), [README#page-kinds](../../../raw/postgres-17/src/backend/access/hash/README#L48-L52)).

**On BRIN the maintenance a real server performs makes the index bigger, by design.** `brinbulkdelete` removes nothing at all - it allocates a result struct and returns ([brin.c#brinbulkdelete](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1283-L1301)) - while `brinvacuumcleanup` scans every block and then summarizes **every** unsummarized range ([brin.c#brinvacuumcleanup](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1307-L1332), [brin.c#brin_vacuum_scan](../../../raw/postgres-17/src/backend/access/brin/brin.c#L2154-L2193)), which the documentation states as the normal way ranges get their first summary ([brin.sgml#summarization](../../../raw/postgres-17/doc/src/sgml/brin.sgml#L84-L95)). A BRIN index measured after the mandatory `VACUUM ANALYZE` therefore holds tuples the churned index did not, and a method that reads growth as waste will read deferred summarization as waste.

**A hash index's file grows in splitpoint batches written as a hole.** `_hash_alloc_buckets` extends the logical end of file to the end of the new splitpoint by writing one initialized page at the last block and expecting the intervening pages to read as zeroes, and its comment says the file may end up more fragmented than if it had been fully allocated ([hashpage.c#_hash_alloc_buckets](../../../raw/postgres-17/src/backend/access/hash/hashpage.c#L967-L1037)). `pg_relation_size` sums the `stat` sizes of the [fork](../../glossary.md#fork)'s segments ([dbsize.c#calculate_relation_size](../../../raw/postgres-17/src/backend/utils/adt/dbsize.c#L302-L343)), so a size reading and an allocation reading can differ on hash for reasons that have nothing to do with bloat.

**A rebuild is not a function of the data alone, and the dependency differs per AM.** `hashbuild` sizes the index from `estimate_rel_size` on the *[heap](../../glossary.md#heap)* ([hash.c#hashbuild-estimate](../../../raw/postgres-17/src/backend/access/hash/hash.c#L133-L137)), which for a table AM [relation](../../glossary.md#relation) derives a density from [`pg_class.relpages`](../../glossary.md#pg_class) and `reltuples` and applies a ten-page floor when the table was never vacuumed ([plancat.c#estimate_rel_size](../../../raw/postgres-17/src/backend/optimizer/util/plancat.c#L1064-L1078), [heapam_handler.c#heapam_estimate_rel_size](../../../raw/postgres-17/src/backend/access/heap/heapam_handler.c#L2104-L2113), [tableam.c#table_block_relation_estimate_size](../../../raw/postgres-17/src/backend/access/table/tableam.c#L653-L700)); the bucket count then follows `num_tuples / ffactor`, rounded up to a splitpoint total ([hashpage.c#_hash_init_metabuffer](../../../raw/postgres-17/src/backend/access/hash/hashpage.c#L509-L523)). A GiST build chooses between a [sorted build](../../glossary.md#gist-build-method), a buffered build and plain inserts, and the sorted path packs pages full with `fillfactor ignored` in as many words ([gistbuild.c#build-strategy](../../../raw/postgres-17/src/backend/access/gist/gistbuild.c#L209-L247), [gistbuild.c#fillfactor](../../../raw/postgres-17/src/backend/access/gist/gistbuild.c#L250-L254), [gistbuild.c#sortbuild-ignores-fillfactor](../../../raw/postgres-17/src/backend/access/gist/gistbuild.c#L466-L469)). A BRIN rebuild's shape follows `pages_per_range` ([brin.c#brinoptions](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1334-L1349)). An unlabelled oracle number is therefore not reproducible.

**A deleted page is not a free page until the horizon moves, and on GiST a deleted page still looks like a leaf.** `gistdeletepage` stamps the next [transaction id](../../glossary.md#transaction-id) into the page and counts it deleted ([gistvacuum.c#gistdeletepage-mark](../../../raw/postgres-17/src/backend/access/gist/gistvacuum.c#L640-L658)), `gistPageRecyclable` accepts it only once `GlobalVisCheckRemovableFullXid` has passed that id ([gistutil.c#gistPageRecyclable](../../../raw/postgres-17/src/backend/access/gist/gistutil.c#L885-L908)), and `GistPageSetDeleted` only ORs in `F_DELETED`, leaving `F_LEAF` set ([gist.h#GistPageSetDeleted](../../../raw/postgres-17/src/include/access/gist.h#L190-L212), [gist.h#GistPageIsLeaf](../../../raw/postgres-17/src/include/access/gist.h#L169-L172)). `pgstattuple`'s GiST arm has no deleted-page test, so it accounts a deleted page as an empty leaf ([pgstattuple.c#pgstat_gist_page](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple.c#L497-L529)).

**SP-GiST waste is mostly placeholders, and placeholders are not free space.** `vacuumRedirectAndPlaceholder` turns expired redirects into placeholders and can physically remove only the placeholders that form a run at the end of the page, because removing an earlier one would change the offset numbers of live tuples ([spgvacuum.c#placeholders-at-end](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L569-L590)). With no SP-GiST decoder in `pageinspect` and a refusal from `pgstattuple`, an SP-GiST page census has to come out of raw bytes or out of `VACUUM`'s own counters.

**What the catalog says about the index depends on which command ran last, and on hash it can say nothing at all.** `hashvacuumcleanup` returns NULL when `hashbulkdelete` did not run, which is also how it covers the ANALYZE-only case ([hash.c#hashvacuumcleanup](../../../raw/postgres-17/src/backend/access/hash/hash.c#L647-L663)); `VACUUM`'s `VERBOSE` output skips an index whose stats are NULL ([vacuumlazy.c#verbose-index-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L718-L732)) and `update_relstats_all_indexes` skips it too ([vacuumlazy.c#update_relstats_all_indexes](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L3073-L3096)). Meanwhile [`ANALYZE`](../../glossary.md#statistics) rewrites every index's [`relpages`](../../glossary.md#reltuples-and-relpages) and `reltuples` from a live block count and a scaled estimate ([analyze.c#index-relstats](../../../raw/postgres-17/src/backend/commands/analyze.c#L647-L662)), and a rebuild writes the build's own count, or `-1` for an empty index ([index.c#index_update_stats](../../../raw/postgres-17/src/backend/catalog/index.c#L2809-L2842), [relcache.c#RelationSetNewRelfilenumber-reltuples](../../../raw/postgres-17/src/backend/utils/cache/relcache.c#L3943-L3953)).

**An unmaintained table is not a state the default configuration leaves behind.** Autovacuum is on by default, and each worker checks every table in its database and runs `VACUUM` and/or `ANALYZE` as needed ([guc_tables.c#autovacuum](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L1450-L1457), [maintenance.sgml#autovacuum-daemon](../../../raw/postgres-17/doc/src/sgml/maintenance.sgml#L853-L860), [autovacuum.c#do_autovacuum-census](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2021-L2033)). A fixture that churns an index and never maintains it scores a method against a fault in operations rather than against the index, which is why the maintenance step is mandatory.

**A maintenance command can run to completion and still do nothing to the index, and its exit status does not say so.** `VACUUM` takes its removal horizon from `GetOldestNonRemovableTransactionId` ([vacuum.c#vacuum_get_cutoffs-OldestXmin](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1109-L1122), [procarray.c#GetOldestNonRemovableTransactionId](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L2005-L2026)), and that computation folds in every backend's `xmin`, skipping only a backend that is itself vacuuming or decoding ([procarray.c#ComputeXidHorizons-backend-xmin](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L1792-L1815), [procarray.c#skip-vacuum-and-decoding](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L1817-L1832)). Anything the horizon still covers stays [`HEAPTUPLE_RECENTLY_DEAD`](../../glossary.md#dead-tuple) and is only counted ([vacuumlazy.c#recently_dead_tuples](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L208-L212), [vacuumlazy.c#lazy_scan_noprune-recently-dead](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1770-L1776)), and [index vacuuming](../../glossary.md#index-vacuuming) happens only when dead [TIDs](../../glossary.md#tid) were collected ([vacuumlazy.c#lazy_vacuum-gate](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1047-L1052)), so a held [snapshot](../../glossary.md#snapshot) turns a successful `VACUUM` into a cleanup-only call that removes no index entry at all. The command can equally be skipped before it starts or killed while it runs ([vacuum.c#skip-lock-not-available](../../../raw/postgres-17/src/backend/commands/vacuum.c#L828-L855), [autovacuum.c#worker-timeouts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L1462-L1470)). That is why the maintenance step carries a prohibition as well as an obligation.

## How It Works

### The four access methods this page scores

The protocol scores an index whose `pg_class.relam` is `hash`, `gist`, `spgist` or `brin`. B-tree and GIN are out of scope and have their own pages; see [Interactions with Other Concepts](#interactions-with-other-concepts).

Each AM is reached through its own `ambulkdelete` and `amvacuumcleanup` pair, and those two callbacks are where every space-reclaiming decision this protocol measures is made ([amapi.h#vacuum-callbacks](../../../raw/postgres-17/src/include/access/amapi.h#L124-L135), [amapi.h#IndexAmRoutine-vacuum](../../../raw/postgres-17/src/include/access/amapi.h#L275-L276), [indexam.c#index_bulk_delete](../../../raw/postgres-17/src/backend/access/index/indexam.c#L747-L760), [indexam.c#index_vacuum_cleanup](../../../raw/postgres-17/src/backend/access/index/indexam.c#L767-L778)).

| AM | Registered callbacks | What the pair does to space |
|---|---|---|
| hash | [hash.c#hashhandler-vacuum](../../../raw/postgres-17/src/backend/access/hash/hash.c#L78-L89) | `hashbulkdelete` walks every bucket, removes matching entries and squeezes chains, updating `hashm_ntuples` ([hash.c#hashbulkdelete-stats](../../../raw/postgres-17/src/backend/access/hash/hash.c#L631-L639)); freed overflow pages go back to the bitmap ([hashovfl.c#_hash_freeovflpage-bitmap](../../../raw/postgres-17/src/backend/access/hash/hashovfl.c#L601-L642)); cleanup only fills `num_pages`, or returns NULL ([hash.c#hashvacuumcleanup](../../../raw/postgres-17/src/backend/access/hash/hash.c#L647-L663)) |
| GiST | [gist.c#gisthandler-vacuum](../../../raw/postgres-17/src/backend/access/gist/gist.c#L80-L91) | `gistvacuumscan` visits every block, records recyclable pages in the FSM, counts deleted ones, and then deletes empty leaves in a second stage ([gistvacuum.c#gistvacuumscan-loop](../../../raw/postgres-17/src/backend/access/gist/gistvacuum.c#L209-L227), [gistvacuum.c#gistvacuumscan-fsm-and-second-stage](../../../raw/postgres-17/src/backend/access/gist/gistvacuum.c#L229-L251), [gistvacuum.c#gistvacuumpage-classes](../../../raw/postgres-17/src/backend/access/gist/gistvacuum.c#L298-L309)) |
| SP-GiST | [spgutils.c#spghandler-vacuum](../../../raw/postgres-17/src/backend/access/spgist/spgutils.c#L63-L76) | `spgvacuumscan` visits every block but the metapage, converts redirects to placeholders, frees empty and new pages into the FSM, refreshes the metapage cache and does not truncate ([spgvacuum.c#spgvacuumscan-loop](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L828-L857), [spgvacuum.c#metapage-and-fsm](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L859-L875), [spgvacuum.c#final-stats](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L902-L905)) |
| BRIN | [brin.c#brinhandler-vacuum](../../../raw/postgres-17/src/backend/access/brin/brin.c#L266-L279) | bulk delete is a no-op; cleanup refreshes the FSM for every regular page and summarizes all unsummarized ranges ([brin.c#brinbulkdelete](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1283-L1301), [brin.c#brinvacuumcleanup](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1307-L1332)) |

Two structural consequences hold for all four and are used throughout this page: the result struct's `pages_deleted` and `pages_free` describe free space *inside* the index file, not returned bytes ([genam.h#IndexBulkDeleteResult](../../../raw/postgres-17/src/include/access/genam.h#L56-L84)); and none of the four declares `amusemaintenanceworkmem`, whose only consumer is [parallel vacuum](../../glossary.md#parallel-vacuum)'s memory split ([vacuumparallel.c#amusemaintenanceworkmem](../../../raw/postgres-17/src/backend/commands/vacuumparallel.c#L343-L360)).

### Admitting a non-core access method

A fifth AM - `contrib/bloom`, or one installed with `CREATE ACCESS METHOD ... TYPE INDEX` - is scored under this protocol only when a run states four things. `CREATE ACCESS METHOD` records the AM in `pg_am` against a handler function, and the handler must return `index_am_handler` for an index AM ([amcmds.c#CreateAccessMethod](../../../raw/postgres-17/src/backend/commands/amcmds.c#L42-L108), [amcmds.c#lookup_am_handler_func](../../../raw/postgres-17/src/backend/commands/amcmds.c#L233-L256)).

| Requirement | What the run must state | Evidence for the shipped example, `bloom` |
|---|---|---|
| the vacuum pair | which functions the AM registers as `ambulkdelete` and `amvacuumcleanup` | [blutils.c#blhandler-vacuum](../../../raw/postgres-17/contrib/bloom/blutils.c#L105-L140) |
| the ANALYZE-only behavior | that the cleanup callback is a no-op in ANALYZE-only mode, or else which stand-in the run used instead | [blvacuum.c#blvacuumcleanup](../../../raw/postgres-17/contrib/bloom/blvacuum.c#L168-L217) returns at once when `analyze_only` is set, which is what `indexam.sgml` recommends ([indexam.sgml#analyze_only](../../../raw/postgres-17/doc/src/sgml/indexam.sgml#L438-L445)) |
| the reclaim registry | where a reclaimed page is recorded, and whether the file can shrink | `blbulkdelete` compacts each page in place, marks an emptied page deleted and adjusts `pd_lower` ([blvacuum.c#blbulkdelete-compaction](../../../raw/postgres-17/contrib/bloom/blvacuum.c#L112-L131)); `blvacuumcleanup` records new and deleted pages in the index FSM and vacuums it ([blvacuum.c#blvacuumcleanup](../../../raw/postgres-17/contrib/bloom/blvacuum.c#L168-L217)) |
| the instruments | which readers accept the AM, and which refuse it | `pgstattuple`'s dispatch has no arm for a non-core AM and raises "unknown index" ([pgstattuple.c#pgstat_relation-dispatch](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple.c#L260-L297)); `pageinspect` ships no decoder for it ([pageinspect.sgml#hash-funcs](../../../raw/postgres-17/doc/src/sgml/pageinspect.sgml#L814-L815)) |

A non-core AM that fails the second requirement is not excluded; it is scored the way the GIN page scores GIN, with the difference named and a stand-in filed. An AM with no shipped instrument at all may still be scored on the oracle and on `VACUUM`'s own counters, and every page-class quantity on it is a level; see [How a published quantity is declared and scored](#how-a-published-quantity-is-declared-and-scored).

### The five phases of a run

Every scored fixture passes through the same five phases, in order, on one isolated cluster.

| Phase | What happens | Why it is a separate phase |
|---|---|---|
| build | create the table, load it, `ANALYZE`, create the index that is scored | the as-built state is the only state in which the index is known to be dense, and on hash and GiST it is the state the oracle will try to reproduce |
| baseline | record `pg_relation_size(index, 'main')`, the table's `reltuples`, the index's own `reltuples`, and the AM's page census | a before-and-after claim has nothing to compare against otherwise |
| churn | run the recipe's own writes, then the maintenance step, then the census | this is the state the method is asked about, and it is a maintained state |
| decide | run the method under test, unmodified, under the measurement lock | the text that is scored must be the text that is published |
| oracle | `REINDEX INDEX`, then read the size again | the only ground truth for "how many bytes would a rebuild return" |

The churn phase ends in a fixed order, and a run states that it followed it: the recipe's writes, then the maintenance step of [The maintenance assumption](#the-maintenance-assumption), then [The simulated auto-analyze census](#the-simulated-auto-analyze-census). Nothing but the method under test runs in the decide phase.

A BRIN fixture whose point is unsummarized ranges is the one case that must also be measured **before** the maintenance step, because the maintenance step summarizes them; see [The BRIN summarization stand-in](#the-brin-summarization-stand-in).

### Proving the index work actually ran

A `VACUUM` that returned is not evidence that the index was touched, and on these AMs the failure is silent. `do_index_cleanup` starts true and is forced false when [`INDEX_CLEANUP`](../../glossary.md#index_cleanup) is disabled ([vacuumlazy.c#do_index_cleanup-init](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L387-L397)); the cleanup call is made only while that flag is set ([vacuumlazy.c#lazy_cleanup_all_indexes-gate](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1064-L1066)); the [wraparound failsafe](../../glossary.md#vacuum-failsafe) clears it mid-run ([vacuumlazy.c#failsafe-disables-cleanup](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L2320-L2326)); and the small-dead-tuple bypass turns off index *vacuuming* while explicitly keeping index cleanup ([vacuumlazy.c#bypass-keeps-cleanup](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1899-L1941)).

What "cleanup ran" is worth differs per AM, and a run records the right one:

| AM | What a cleanup-only call does when bulk delete never ran | What the run must assert instead of assuming |
|---|---|---|
| hash | nothing: cleanup returns NULL, so there is no `VERBOSE` index line and no index `relstats` write ([hash.c#hashvacuumcleanup](../../../raw/postgres-17/src/backend/access/hash/hash.c#L647-L663), [vacuumlazy.c#verbose-index-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L718-L732)) | that the bitmap and page-type census changed, read from `pgstathashindex` or `hash_bitmap_info` |
| GiST | a full scan happens anyway, for statistics and empty-page deletion ([gistvacuum.c#gistvacuumcleanup](../../../raw/postgres-17/src/backend/access/gist/gistvacuum.c#L74-L105)) | that `pages_free` is nonzero or that the census found no recyclable page |
| SP-GiST | a full scan with a no-delete callback happens, for placeholder and FSM housekeeping ([spgvacuum.c#spgvacuumcleanup](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L946-L985)) | that the metapage cache and the FSM were refreshed |
| BRIN | a full scan plus a summarization pass happens ([brin.c#brinvacuumcleanup](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1307-L1332)) | the index size before and after, because this call can grow the file |

`VACUUM`'s own per-index line is the cheapest proof, and its four fields are `num_pages`, `pages_newly_deleted`, `pages_deleted` and `pages_free` ([vacuumlazy.c#verbose-index-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L718-L732)). Read it with the per-AM caveats in [The mandatory cross-checks](#the-mandatory-cross-checks).

### The maintenance assumption

Every scored fixture assumes that normal autovacuum and auto-analyze maintain every table, and the run performs that maintenance itself. The assumption has three parts.

1. **After its churn, a fixture runs `VACUUM ANALYZE` on every table the churn touched, before the decide phase.** The tables the churn touched are the ones whose rows it inserted, updated or deleted. A fixture with no churn has nothing to maintain, and the `ANALYZE` of its build phase is what it carries into the decide phase.
2. **Turning autovacuum off does not exempt a table.** The run keeps `autovacuum` off for isolation, and a fixture may additionally set `autovacuum_enabled = false` on a table ([reloptions.c#autovacuum_enabled](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L105-L113)). Either setting stops the launcher's verdicts for that table, wraparound forcing aside ([autovacuum.c#AutoVacuumingActive](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3235-L3241), [autovacuum.c#av_enabled-return](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3048-L3054)); neither stops the fixture from running the maintenance the launcher would have run, because the assumption replaces the launcher rather than depending on it.
3. **No fixture may leave churn unmaintained.** A recipe that inserts, updates or deletes and then asks the method about the index with no `VACUUM ANALYZE` in between is not a fixture this protocol defines, and a number produced from one is not a scored number.

A foreground `VACUUM ANALYZE` is a faithful stand-in for the worker's command: `autovacuum_do_vac_analyze` builds one `VacuumRelation` and calls the same `vacuum()` the SQL command reaches from `ExecVacuum` ([autovacuum.c#autovacuum_do_vac_analyze](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3120-L3147), [vacuum.c#ExecVacuum-vacuum](../../../raw/postgres-17/src/backend/commands/vacuum.c#L450-L451)). Inside it each relation is vacuumed first and analyzed second when both options are set ([vacuum.c#vacuum-then-analyze](../../../raw/postgres-17/src/backend/commands/vacuum.c#L618-L650)), so `ANALYZE` is the last writer of every `reltuples` the fixture leaves behind: the sampled estimate, not `VACUUM`'s count ([analyze.c#index-relstats](../../../raw/postgres-17/src/backend/commands/analyze.c#L647-L662), [vacuum.c#vac_update_relstats](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1400-L1416)). The `VACUUM` half reports its live and dead counts and zeroes the insert counter ([pgstat_relation.c#report_vacuum-reset](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L233-L246)); the `ANALYZE` half zeroes `mod_since_analyze` ([pgstat_relation.c#report_analyze-reset](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L331-L337)).

What the maintenance step costs the reading is different on each AM, and a run states it per fixture:

| AM | What the mandatory `VACUUM ANALYZE` changes in the index |
|---|---|
| hash | dead entries are removed and overflow pages may be squeezed out of their chains into the bitmap; the file never shrinks ([hash.c#hashbulkdelete-stats](../../../raw/postgres-17/src/backend/access/hash/hash.c#L631-L639), [README#no-shrink](../../../raw/postgres-17/src/backend/access/hash/README#L31-L34)) |
| GiST | entries whose TIDs were drained are removed, fully empty leaves become deleted pages, and recyclable ones enter the FSM; one empty leaf per parent survives because the last downlink is never removed ([gistvacuum.c#empty-leaf-remembered](../../../raw/postgres-17/src/backend/access/gist/gistvacuum.c#L388-L401), [gistvacuum.c#last-downlink](../../../raw/postgres-17/src/backend/access/gist/gistvacuum.c#L543-L548)) |
| SP-GiST | dead leaf tuples become placeholders, trailing placeholder runs disappear, interior ones stay, and the root is never freed ([spgvacuum.c#placeholders-at-end](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L569-L590), [spgvacuum.c#spgvacuumpage-fsm](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L665-L683)) |
| BRIN | nothing is removed, and every unsummarized range gains a summary tuple, so the index can grow ([brin.c#brinbulkdelete](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1283-L1301), [brin.c#brinvacuumcleanup](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1307-L1332)) |

**The launcher's verdicts are recorded here, not applied.** The run maintains after every churn whether or not the counters had crossed a threshold, so the protocol never reproduces the vacuum side, and a conforming run may not claim that it does. A launcher at the defaults wakes every `autovacuum_naptime` of 60 s ([guc_tables.c#autovacuum_naptime](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3339-L3348)), and its worker asks `relation_needs_vacanalyze` for a vacuum verdict and an analyze verdict at once for every table it walks ([autovacuum.c#do_autovacuum-census](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2021-L2033)).

| Launcher verdict | Engine test, on effective per-table values | At the defaults | Evidence |
|---|---|---|---|
| vacuum | `dead_tuples > vac_base_thresh + vac_scale_factor * reltuples` | `50 + 0.2 * reltuples` | [autovacuum.c#vacthresh-anlthresh](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3074-L3076), [autovacuum.c#verdicts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3092-L3095), [guc_tables.c#autovacuum_vacuum_threshold](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3349-L3357), [guc_tables.c#autovacuum_vacuum_scale_factor](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3886-L3894) |
| insert vacuum | `ins_since_vacuum > vac_ins_base_thresh + vac_ins_scale_factor * reltuples`, skipped entirely when that base threshold is negative | `1000 + 0.2 * reltuples` | [autovacuum.c#vacthresh-anlthresh](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3074-L3076), [autovacuum.c#verdicts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3092-L3095), [guc_tables.c#autovacuum_vacuum_insert_threshold](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3358-L3366), [guc_tables.c#autovacuum_vacuum_insert_scale_factor](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3896-L3904) |
| analyze | `mod_since_analyze > anl_base_thresh + anl_scale_factor * reltuples` | `50 + 0.1 * reltuples` | [autovacuum.c#vacthresh-anlthresh](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3074-L3076), [autovacuum.c#verdicts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3092-L3095), [guc_tables.c#autovacuum_analyze_threshold](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3367-L3375), [guc_tables.c#autovacuum_analyze_scale_factor](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3906-L3914) |

Each parameter is the table's own [reloption](../../glossary.md#storage-parameter) whenever that reloption holds a non-negative value and the cluster [GUC](../../glossary.md#guc) only otherwise, on the vacuum side exactly as on the analyze side ([autovacuum.c#vac-effective-values](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2993-L3009), [autovacuum.c#anl-effective-values](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3011-L3017)). All five GUCs are [`PGC_SIGHUP`](../../glossary.md#guc-context), so a cluster-wide change is a reload, and each of the six matching reloptions is set by an `ALTER TABLE` taking [`ShareUpdateExclusiveLock`](../../glossary.md#shareupdateexclusivelock) ([reloptions.c#autovacuum_vacuum_threshold](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L225-L233), [reloptions.c#autovacuum_vacuum_insert_threshold](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L234-L242), [reloptions.c#autovacuum_analyze_threshold](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L243-L251), [reloptions.c#autovacuum_vacuum_scale_factor](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L399-L407), [reloptions.c#autovacuum_vacuum_insert_scale_factor](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L408-L416), [reloptions.c#autovacuum_analyze_scale_factor](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L417-L425)). The counters the launcher compares are `n_dead_tup`, `n_mod_since_analyze` and `n_ins_since_vacuum` in [`pg_stat_all_tables`](../../glossary.md#pg_stat_all_tables) ([system_views.sql#launcher-counters](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L688-L690)), and the documentation states the same formulas ([maintenance.sgml#vacuum-threshold](../../../raw/postgres-17/doc/src/sgml/maintenance.sgml#L899-L906), [maintenance.sgml#analyze-threshold](../../../raw/postgres-17/doc/src/sgml/maintenance.sgml#L946-L953)).

The assumption is deliberately stronger than the launcher: the maintenance step runs even where the counters sit far below every threshold, so the protocol builds no sub-threshold unmaintained index and scores no method against one. What the three parts do not cover on their own is a fixture that issues the maintenance and then prevents it from working; that is [The maintenance must not be defeated](#the-maintenance-must-not-be-defeated).

### The maintenance must not be defeated

**A fixture may not carry a state into the maintenance step that would have stopped a real server's autovacuum, `VACUUM`, `ANALYZE` or auto-analyze from doing the work this protocol credits it with.** [The maintenance assumption](#the-maintenance-assumption) says the command must run; this rule says it must have been effective. Every failure here is silent: the statement can be skipped before it starts, killed part-way, or stripped of its removal horizon and still return success, and what it leaves behind is the unmaintained index the assumption exists to forbid.

Five states are forbidden, on every table and index a fixture touches, from its first churn statement to the end of the census.

| Forbidden state | Why it defeats the maintenance step | Evidence |
|---|---|---|
| an open transaction or held snapshot anywhere in the cluster, other than a lazy `VACUUM` | `VACUUM`'s `OldestXmin` comes from `GetOldestNonRemovableTransactionId`, which folds in every backend's `xmin`, so nothing that horizon still covers is removable: the churn's dead rows stay `HEAPTUPLE_RECENTLY_DEAD`, no dead TIDs are collected, index vacuuming is never entered, and the AM's `ambulkdelete` never runs. A lazy `VACUUM` is the one exemption the engine itself grants, through the `PROC_IN_VACUUM` flag the [proc-array](../../glossary.md#procarray) scan skips | [vacuum.c#vacuum_get_cutoffs-OldestXmin](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1109-L1122), [procarray.c#ComputeXidHorizons-backend-xmin](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L1792-L1815), [vacuumlazy.c#lazy_vacuum-gate](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1047-L1052), [vacuum.c#PROC_IN_VACUUM](../../../raw/postgres-17/src/backend/commands/vacuum.c#L2006-L2029), [procarray.c#skip-vacuum-and-decoding](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L1817-L1832) |
| a [prepared transaction](../../glossary.md#two-phase-commit) | its dummy `PGPROC` is what keeps the xid considered running, so the horizon stays pinned after the session that prepared it is gone, with no live session to show for it | [twophase.c#dummy-pgproc](../../../raw/postgres-17/src/backend/access/transam/twophase.c#L24-L26) |
| a [replication slot](../../glossary.md#replication-slot) holding an `xmin` | the horizon computation takes the older of its own answer and the slot's `xmin`, for shared and non-shared relations alike | [procarray.c#slot-horizons](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L1896-L1902) |
| a lock on the table conflicting with `ShareUpdateExclusiveLock`, held while the maintenance step runs | that is the lock `VACUUM` and `ANALYZE` take, so a foreground maintenance statement blocks on it. A real non-wraparound worker does not block: it is given `VACOPT_SKIP_LOCKED`, takes the lock conditionally and gives up with `lock not available`, and a backend that queues behind one signals it to cancel | [vacuum.c#vacuum-lockmode](../../../raw/postgres-17/src/backend/commands/vacuum.c#L2049-L2056), [analyze.c#analyze-lockmode](../../../raw/postgres-17/src/backend/commands/analyze.c#L134-L145), [autovacuum.c#skip-locked](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2825-L2830), [vacuum.c#vacuum_open_relation-conditional](../../../raw/postgres-17/src/backend/commands/vacuum.c#L785-L800), [vacuum.c#skip-lock-not-available](../../../raw/postgres-17/src/backend/commands/vacuum.c#L828-L855), [proc.c#cancel-blocking-autovacuum](../../../raw/postgres-17/src/backend/storage/lmgr/proc.c#L1412-L1472) |
| a [`statement_timeout`](../../glossary.md#statement_timeout-and-lock_timeout), `transaction_timeout` or `lock_timeout` short enough to fire inside the maintenance step | the statement dies part-done, leaving a state that is neither the churned one nor the maintained one. All three are `PGC_USERSET`, so session or transaction scope, and an autovacuum worker forces each of them, plus `idle_in_transaction_session_timeout`, to `0` for this exact reason: "to avoid letting these settings prevent regular maintenance from being executed" | [guc_tables.c#statement_timeout](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L2611-L2620), [guc_tables.c#lock_timeout](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L2622-L2631), [guc_tables.c#idle_in_transaction_session_timeout](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L2633-L2642), [guc_tables.c#transaction_timeout](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L2644-L2653), [autovacuum.c#launcher-timeouts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L518-L526), [autovacuum.c#worker-timeouts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L1462-L1470) |

**A disabled launcher is not a defeat.** `autovacuum = off` and a per-table `autovacuum_enabled = false` stop the launcher's verdicts, and part 2 of the assumption already accounts for them: the fixture runs the maintenance the launcher would have run, so nothing is left undone ([autovacuum.c#AutoVacuumingActive](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3235-L3241), [autovacuum.c#av_enabled-return](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3048-L3054)). The five states above are different in kind: the maintenance statement runs and cannot do its work.

What a run records per fixture, beside the per-AM index proof:

| Proof | What it establishes |
|---|---|
| the maintenance statement completed, and no `skipping vacuum of ... --- lock not available` or `skipping analyze of ...` line names the fixture's relation | the command was neither skipped for want of the lock nor cut short |
| `VACUUM (VERBOSE)`'s `tuples: ... are dead but not yet removable` count for every churned table ([vacuumlazy.c#verbose-tuples-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L657-L663)) | a nonzero count on a fixture whose churn deleted or updated rows is a pinned horizon; the fixture is repaired and re-run, not scored |
| the horizon holders at that moment: [`pg_stat_activity`](../../glossary.md#pg_stat_activity)'s `xact_start` and `backend_xmin`, and `pg_replication_slots`' `xmin` ([system_views.sql#pg_stat_activity-xmin](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L878-L885), [system_views.sql#pg_replication_slots-xmin](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1006-L1017)) | which session or slot pinned it, when one did. These are reads, not interlocks; see [Open Questions](#open-questions) |
| the per-AM assertions of [Proving the index work actually ran](#proving-the-index-work-actually-ran) | a horizon-pinned `VACUUM` degenerates into exactly the cleanup-only call that table describes, so the same assertions decide it |

**Two exceptions are declared rather than forbidden**, because the protocol requires one of them and owns the other.

| Exception | What the run does instead |
|---|---|
| the GiST fixture that holds a snapshot across the maintenance step, required by [Coverage the protocol requires](#coverage-the-protocol-requires) | the snapshot is the point: declare it, report it beside the stuck pages as [The reading rules](#the-reading-rules) already demands, and publish the reading as a held-horizon reading, never as a maintained-state one ([gistutil.c#gistPageRecyclable](../../../raw/postgres-17/src/backend/access/gist/gistutil.c#L885-L908)) |
| the measurement lock, which excludes `VACUUM` and `ANALYZE` by design ([lock.c#LockConflicts](../../../raw/postgres-17/src/backend/storage/lmgr/lock.c#L64-L104)) | take it in the decide phase only, after the maintenance step and the census, and release it before any later maintenance; it may not be held across a maintenance step |

Nothing in this rule asks a run to switch the launcher on. `autovacuum` stays off for isolation, as [What the run fixes, and the apply scope of each setting](#what-the-run-fixes-and-the-apply-scope-of-each-setting) states; the rule binds what a fixture may do while it is off.

### The BRIN summarization stand-in

BRIN is the one AM in this set where an autovacuum worker does something no ordinary backend does for free, so it gets an explicit stand-in - the counterpart of the GIN page's pending-list flush.

- With the `autosummarize` reloption on, `brininsert` notices the first tuple of the first page of a new range and asks autovacuum for a targeted summarization work item, logging a `LOG` message when the request queue is full ([brin.c#brininsert-autosummarize](../../../raw/postgres-17/src/backend/access/brin/brin.c#L379-L411), [brin.h#BrinGetAutoSummarize](../../../raw/postgres-17/src/include/access/brin.h#L46-L51), [autovacuum.c#AutoVacuumRequestWork](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3243-L3256), [autovacuum.h#AVW_BRINSummarizeRange](../../../raw/postgres-17/src/include/postmaster/autovacuum.h#L19-L26)).
- A worker fulfils that item by calling `brin_summarize_range` for the recorded block ([autovacuum.c#perform_work_item-brin](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2635-L2641)), and the documentation states that this happens whenever autovacuum runs in the database, whether or not the table itself is processed ([brin.sgml#autosummarize-request](../../../raw/postgres-17/doc/src/sgml/brin.sgml#L114-L129)).
- With `autovacuum` off - which the isolation rule requires - no work item is ever fulfilled, so an `autosummarize` index in a run is an index whose requests were dropped.

**The rule.** A fixture that models an `autosummarize`-maintained BRIN index runs `brin_summarize_new_values()` on the index, or a targeted `brin_summarize_range()`, and declares that call as its maintenance beside the mandatory `VACUUM ANALYZE`. A fixture whose point is an *unsummarized* range must take its measurement before the maintenance step and say so, because the maintenance step summarizes every range that is left ([brin.c#brinvacuumcleanup](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1307-L1332), [brin.sgml#summarization](../../../raw/postgres-17/doc/src/sgml/brin.sgml#L84-L95)).

Three differences a run must state, because the stand-in is not the worker's path:

| Difference | What it costs the fixture |
|---|---|
| the worker fulfils one queued range per request, and a full queue drops the request with a `LOG` line, where the SQL function summarizes the range it was given, and `brin_summarize_new_values()` summarizes all of them ([brin.c#brininsert-autosummarize](../../../raw/postgres-17/src/backend/access/brin/brin.c#L379-L411), [brin.sgml#autosummarize-request](../../../raw/postgres-17/doc/src/sgml/brin.sgml#L114-L129)) | a stand-in fixture cannot reproduce a partially summarized index by accident; it must choose the ranges explicitly and record which ones it summarized |
| the SQL function takes `ShareUpdateExclusiveLock` on both table and index, requires index ownership, refuses during recovery, and is a `DEBUG1` no-op on an [index that is not valid](../../glossary.md#invalid-index) ([brin.c#brin_summarize_range-recovery](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1384-L1388), [brin.c#brin_summarize_range-guards](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1431-L1464)) | a run records which lock its maintenance took; unlike GIN's index-only flush this one is excluded by the measurement lock, so it cannot race a census |
| the worker switches to the table owner's userid, sets a security-restricted context and restricts `search_path`, which the SQL path does not need ([brin.c#brin_summarize_range-guards](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1431-L1464)) | a fixture whose summary values come from a user-defined expression may summarize under a different `search_path` than a worker would |

The inverse operation is available to a fixture that needs an unsummarized range after the fact: `brin_desummarize_range` removes one range's summary under the same locks, ownership and validity rules, and autovacuum never calls it ([brin.c#brin_desummarize_range](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1505-L1560), [brin.sgml#desummarize](../../../raw/postgres-17/doc/src/sgml/brin.sgml#L131-L137)).

### The auto-analyze stand-in is a plain ANALYZE

On these four access methods an `ANALYZE` touches no index page, so a foreground `ANALYZE` is a faithful stand-in for an auto-analyze and no extra call is needed. This is the one place where the protocol is simpler than the GIN page's.

- `analyze_rel` enters the index AM's ANALYZE-only cleanup only when the command is not a `VACUUM ANALYZE`, and the comment there states that most index AMs no-op in that mode, naming GIN as the only core exception ([analyze.c#analyze-only-cleanup](../../../raw/postgres-17/src/backend/commands/analyze.c#L694-L721)).
- Three of the four return immediately on the `analyze_only` flag: [gistvacuum.c#gistvacuumcleanup](../../../raw/postgres-17/src/backend/access/gist/gistvacuum.c#L74-L105), [spgvacuum.c#spgvacuumcleanup](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L946-L985), [brin.c#brinvacuumcleanup](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1307-L1332).
- Hash does not test the flag at all. It returns NULL whenever `hashbulkdelete` did not run, and its comment says this covers the ANALYZE-only case too ([hash.c#hashvacuumcleanup](../../../raw/postgres-17/src/backend/access/hash/hash.c#L647-L663)); an ANALYZE-only call always passes NULL stats ([analyze.c#analyze-only-cleanup](../../../raw/postgres-17/src/backend/commands/analyze.c#L694-L721), [indexam.sgml#amvacuumcleanup](../../../raw/postgres-17/doc/src/sgml/indexam.sgml#L424-L436)).
- `contrib/bloom` behaves like the three explicit ones ([blvacuum.c#blvacuumcleanup](../../../raw/postgres-17/contrib/bloom/blvacuum.c#L168-L217)).

**The rule.** A fixture that models a table maintained by auto-analyze alone - insert-heavy, past the analyze threshold, under both vacuum thresholds - runs `ANALYZE` and nothing else, and says so. What it must still declare is the catalog movement: the `ANALYZE` rewrites the measured index's `relpages` and `reltuples` from a live `RelationGetNumberOfBlocks` and a scaled row estimate ([analyze.c#index-relstats](../../../raw/postgres-17/src/backend/commands/analyze.c#L647-L662)), and on hash that also moves the heap statistics the oracle will read; see [The oracle, and what each rebuild depends on](#the-oracle-and-what-each-rebuild-depends-on).

### The simulated auto-analyze census

After the maintenance step and before the decide phase, the run recomputes the launcher's **analyze** verdict for every table in the fixture database and analyzes the tables it names. The maintenance step has already analyzed every churned table, so what the census decides are the tables no churn touched: one whose build phase left it past the threshold is analyzed here, and one whose build-phase `ANALYZE` still describes it is left alone. The census is also the recheck that the counters were published in the right order.

The rule is the engine's own test rather than a per-fixture annotation: `relation_needs_vacanalyze` sets `doanalyze` when the table's `mod_since_analyze` is **strictly greater** than `anl_base_thresh + anl_scale_factor * reltuples` ([autovacuum.c#vacthresh-anlthresh](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3074-L3076), [autovacuum.c#verdicts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3092-L3095)).

| Input | Effective value the census must use | Evidence |
|---|---|---|
| base threshold | `relopts->analyze_threshold` when `>= 0`, else `autovacuum_anl_thresh` | [autovacuum.c#anl-effective-values](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3011-L3017) |
| scale factor | `relopts->analyze_scale_factor` when `>= 0`, else `autovacuum_anl_scale` | [autovacuum.c#anl-effective-values](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3011-L3017) |
| row count | `pg_class.reltuples`, taken as 0 when it is negative | [autovacuum.c#census-inputs](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3063-L3072) |
| counter | `mod_since_analyze` from the table's shared statistics entry | [autovacuum.c#census-inputs](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3063-L3072) |
| comparison | strictly greater than, so a table landing exactly on its threshold is left alone | [autovacuum.c#verdicts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3092-L3095) |
| short circuit | `autovacuum_enabled = false` makes `doanalyze` false outright, wraparound forcing aside | [autovacuum.c#av_enabled-return](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3048-L3054) |

The reloptions arrive as the `AutoVacOpts` member of the table's `StdRdOptions`, decoded by `extract_autovac_opts`, and an unset member reads back below zero, which is exactly what makes the `>= 0` test the precedence rule ([autovacuum.c#extract_autovac_opts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2704-L2723), [rel.h#AutoVacOpts](../../../raw/postgres-17/src/include/utils/rel.h#L308-L326)). A census that reads `current_setting('autovacuum_analyze_threshold')` for every table computes the wrong threshold for any table carrying the reloption. At the shipped defaults of 50 and 0.1 the effective threshold is 50 rows plus a tenth of the estimated row count ([guc_tables.c#autovacuum_analyze_threshold](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3367-L3375), [guc_tables.c#autovacuum_analyze_scale_factor](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3906-L3914)).

**Two publication points, not one.** Running the phases in order does not put the churn into `mod_since_analyze`. A backend accumulates its table counts locally, and they reach the shared entry only when `pgstat_report_stat` flushes them, which it does between transactions and, unforced, at most once per `PGSTAT_MIN_INTERVAL` of 1000 ms ([pgstat.c#PGSTAT_MIN_INTERVAL](../../../raw/postgres-17/src/backend/utils/activity/pgstat.c#L117-L122), [pgstat.c#pgstat_report_stat](../../../raw/postgres-17/src/backend/utils/activity/pgstat.c#L583-L600), [postgres.c#pgstat_report_stat-idle](../../../raw/postgres-17/src/backend/tcop/postgres.c#L4662-L4681)); only such a flush adds to the counter ([pgstat_relation.c#mod_since_analyze](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L857-L860)). Meanwhile the `ANALYZE` half of the maintenance step zeroes that counter and forgets what was committed while it ran ([pgstat_relation.c#report_analyze-reset](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L331-L337)).

| When | What must hold | How to get it |
|---|---|---|
| after the churn, before the maintenance `VACUUM ANALYZE` and before the census reads the counter | every churn session's table counts are in the shared entry | `SELECT pg_stat_force_next_flush();` in each churn session ([pg_proc.dat#pg_stat_force_next_flush](../../../raw/postgres-17/src/include/catalog/pg_proc.dat#L5916-L5920)); or let each churn session exit; or wait out `PGSTAT_MIN_INTERVAL` |
| after the maintenance `ANALYZE`, before any recheck | nothing published after the reset is read as new churn | publish first, analyze second, then re-read; a recheck that still disagrees is recorded as a disagreement, not analyzed again |

The read side is a third hazard. The census reads `n_mod_since_analyze` from `pg_stat_all_tables` ([system_views.sql#launcher-counters](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L688-L690)), and `stats_fetch_consistency` - `PGC_USERSET`, so session or transaction scope, default `cache` ([guc_tables.c#stats_fetch_consistency](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L4966-L4974)) - decides whether a second read of the same entry returns the first answer again, so a census that reads, analyzes and re-reads inside one transaction discards the cached statistics with `pg_stat_clear_snapshot()` ([pg_proc.dat#pg_stat_clear_snapshot](../../../raw/postgres-17/src/include/catalog/pg_proc.dat#L5911-L5915)). The engine's own statistics test uses exactly this force-flush-then-read sequence under an explicit `stats_fetch_consistency = snapshot` ([stats.sql#force-flush](../../../raw/postgres-17/src/test/regress/sql/stats.sql#L101-L110)).

**What the census costs a fixture here.** Every churned table is analyzed by the maintenance step and every unchurned table past its threshold by the census, so a fixture whose point was a stale row count is scored against fresh statistics instead. On this protocol the cost lands in two specific places: a method that reads the *index's* `relpages` or `reltuples` is reading a value the maintenance step or the census has just rewritten, and on hash the *heap's* refreshed statistics change what the oracle builds.

### The measurement lock

When a census has to be compared with anything - an earlier census, a later rebuild, another index - it runs inside one transaction holding `SHARE ROW EXCLUSIVE` on the index's **table**. That mode conflicts with `ROW EXCLUSIVE`, `SHARE UPDATE EXCLUSIVE`, `SHARE`, itself, `EXCLUSIVE` and `ACCESS EXCLUSIVE` ([lock.c#LockConflicts](../../../raw/postgres-17/src/backend/storage/lmgr/lock.c#L64-L104), [mvcc.sgml#SHARE-ROW-EXCLUSIVE](../../../raw/postgres-17/doc/src/sgml/mvcc.sgml#L1023-L1032)). So it excludes writers, `VACUUM` and `ANALYZE`, both of which take `ShareUpdateExclusiveLock` ([vacuum.c#vacuum-lockmode](../../../raw/postgres-17/src/backend/commands/vacuum.c#L2049-L2056), [analyze.c#analyze-lockmode](../../../raw/postgres-17/src/backend/commands/analyze.c#L134-L145)), and both `REINDEX` forms - while leaving ordinary readers alone.

Three rules follow from the source, and a run may not weaken them:

- **`SHARE` is one step weaker and not enough.** A plain `REINDEX INDEX` takes `ShareLock` on the table, which is self-compatible, so it would proceed and swap the index's storage under a running census ([indexcmds.c#RangeVarCallbackForReindexIndex](../../../raw/postgres-17/src/backend/commands/indexcmds.c#L2857-L2872), [indexcmds.c#ReindexIndex-dispatch](../../../raw/postgres-17/src/backend/commands/indexcmds.c#L2824-L2849)).
- **The lock is taken on the table, never on the index.** `LOCK TABLE` refuses anything but a plain table, a partitioned table or a view ([lockcmds.c#RangeVarCallbackForLockTable](../../../raw/postgres-17/src/backend/commands/lockcmds.c#L70-L107)). On this protocol that is sufficient, unlike on GIN: the index-only maintenance functions in scope here, `brin_summarize_range`, `brin_summarize_new_values` and `brin_desummarize_range`, all take `ShareUpdateExclusiveLock` on the **table** as well as the index, so the measurement lock excludes them ([brin.c#brin_summarize_range-guards](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1431-L1464), [brin.c#brin_desummarize_range](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1505-L1560)).
- **The privilege is not `SELECT`.** `LockTableAclCheck` accepts `MAINTAIN`, `UPDATE`, `DELETE` or `TRUNCATE` for every mode above `ROW EXCLUSIVE`, and adds `SELECT` only at `ACCESS SHARE` ([lockcmds.c#LockTableAclCheck](../../../raw/postgres-17/src/backend/commands/lockcmds.c#L277-L299)). A raw-page census already needs superuser ([rawpage.c#get_raw_page_internal](../../../raw/postgres-17/contrib/pageinspect/rawpage.c#L141-L199)), so this binds a method built on `pgstattuple` or `pgstathashindex`, whose execute privilege is granted to `pg_stat_scan_tables` ([pgstattuple--1.4--1.5.sql#pgstathashindex](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple--1.4--1.5.sql#L121-L136)).

The lock is a cost, not a default: it blocks every writer on the table for the duration of the census, so a run reports the interval it held and pairs it with `lock_timeout`.

### The oracle, and what each rebuild depends on

The oracle is a measured `REINDEX INDEX` on the maintained fixture, with `pg_relation_size(index, 'main')` read immediately before and after. `reindex_index` suppresses the target index, gives it a new [relfilenode](../../glossary.md#relfilenumber) and calls `index_build`, so the after-reading is a new physical file rather than a compacted old one ([index.c#reindex_index-rebuild](../../../raw/postgres-17/src/backend/catalog/index.c#L3781-L3789)); the blocking form is reached from `ReindexIndex`'s final branch under `ShareLock` on the table ([indexcmds.c#ReindexIndex-dispatch](../../../raw/postgres-17/src/backend/commands/indexcmds.c#L2824-L2849)). `pg_relation_size` with an explicit fork sums that fork's segments ([dbsize.c#pg_relation_size](../../../raw/postgres-17/src/backend/utils/adt/dbsize.c#L345-L371), [dbsize.c#calculate_relation_size](../../../raw/postgres-17/src/backend/utils/adt/dbsize.c#L302-L343)), which is the right denominator because a page census counts main-fork blocks and nothing else.

**The oracle measures returned filesystem bytes, not waste.** All four AMs reclaim pages inside the file and none of them truncates it, so a page census and the oracle answer different questions by construction ([spgvacuum.c#truncation-disabled](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L877-L900), [README#no-shrink](../../../raw/postgres-17/src/backend/access/hash/README#L31-L34), [gistutil.c#gistNewBuffer](../../../raw/postgres-17/src/backend/access/gist/gistutil.c#L822-L883), [spgutils.c#SpGistNewBuffer](../../../raw/postgres-17/src/backend/access/spgist/spgutils.c#L379-L420), [brin_pageops.c#brin_getinsertbuffer-fsm](../../../raw/postgres-17/src/backend/access/brin/brin_pageops.c#L706-L710)).

A run reports, per AM, the inputs its own oracle depended on:

| AM | What the rebuilt size is a function of | Evidence |
|---|---|---|
| hash | the heap's estimated row count at rebuild time, through `estimate_rel_size` and then `num_tuples / ffactor` rounded up to a splitpoint total; so the maintenance step's heap statistics move the oracle, and a never-vacuumed small table is floored at ten pages | [hash.c#hashbuild-estimate](../../../raw/postgres-17/src/backend/access/hash/hash.c#L133-L137), [hashpage.c#_hash_init_metabuffer](../../../raw/postgres-17/src/backend/access/hash/hashpage.c#L509-L523), [plancat.c#estimate_rel_size](../../../raw/postgres-17/src/backend/optimizer/util/plancat.c#L1064-L1078), [tableam.c#table_block_relation_estimate_size](../../../raw/postgres-17/src/backend/access/table/tableam.c#L653-L700) |
| GiST | the build strategy: sorted when every key [opclass](../../glossary.md#operator-class) has a `GIST_SORTSUPPORT_PROC` and buffering was not forced on, and that path packs pages full and ignores `fillfactor`; otherwise the fillfactor-derived free space is left on every page | [gistbuild.c#build-strategy](../../../raw/postgres-17/src/backend/access/gist/gistbuild.c#L209-L247), [gistbuild.c#fillfactor](../../../raw/postgres-17/src/backend/access/gist/gistbuild.c#L250-L254), [gistbuild.c#sortbuild-ignores-fillfactor](../../../raw/postgres-17/src/backend/access/gist/gistbuild.c#L466-L469) |

| BRIN | `pages_per_range` and the heap's block count, since the rebuild re-summarizes every range and re-extends the revmap | [brin.c#brinoptions](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1334-L1349), [brin.c#brinvacuumcleanup](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1307-L1332) |

One consequence is worth stating on its own, because it has no counterpart on the B-tree or GIN pages: on hash the oracle is **not** a function of the index alone, and a fixture that measures a rebuild without recording the heap's `relpages` and `reltuples` at that moment has recorded an unreproducible number.

### How a published quantity is declared and scored

Before the run, every column the method publishes is declared as exactly one of three kinds. The declaration is filed with the fixture plan and may not be rewritten afterwards.

| Declared kind | What it claims against the oracle | Verdicts |
|---|---|---|
| lower bound | the quantity never exceeds the bytes a rebuild returns | `HELD`, `VIOLATED` |
| upper bound | the quantity is never less than the bytes a rebuild returns | `HELD`, `VIOLATED` |
| level | the quantity has no relation to what a rebuild returns | `DECLARED` - never scored as a bound, and never published as reclaimable space |

Two columns are mandatory for a run to be readable: `truth_pct`, the oracle's own fraction of the maintained file, computed from the two size readings and nothing else; and `declared_kind` per published quantity, filed before the run. A `VIOLATED` verdict is corrected in the method or moved to a `level`, not annotated away.

A method that also makes a **decision** - rebuild, or leave alone - declares its own threshold, because the protocol fixes the oracle and not the threshold. The decision is then scored `PASS`, `FALSE POSITIVE` (rebuilt, and the rebuild returned less than the method's own threshold) or `FALSE NEGATIVE` (not rebuilt, and a rebuild would have returned more). A run reports the threshold beside the score; a threshold chosen after the results is not a scored run.

Two per-AM constraints bind the declaration:

- Any quantity a method derives from an SP-GiST page's contents is a `level`, unless it came from `VACUUM`'s own counters, because no shipped function decodes an SP-GiST page.
- Any BRIN quantity that mixes summarized and unsummarized ranges is a `level`, because the mandatory maintenance step changes which ranges exist ([brin.c#brinvacuumcleanup](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1307-L1332)).

Four reading consequences follow, and a run applies them rather than discovering them:

- **`pgstattuple`'s free space is not comparable across these AMs.** Its generic page accounting adds `PageGetFreeSpace`, which charges a [line pointer](../../glossary.md#line-pointer), and it counts only the page classes each arm passes through ([pgstattuple.c#pgstat_index_page](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple.c#L575-L601)). On hash it adds a whole [`BLCKSZ`](../../glossary.md#blcksz) for a new page and for an `LH_UNUSED_PAGE`, and ignores bitmap and metapages entirely ([pgstattuple.c#pgstat_hash_page](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple.c#L449-L495)); on GiST it counts leaves only, and a deleted leaf still counts as a leaf ([pgstattuple.c#pgstat_gist_page](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple.c#L497-L529), [gist.h#GistPageSetDeleted](../../../raw/postgres-17/src/include/access/gist.h#L190-L212)).
- **A `pgstattuple` scan is not isolated by its own lock.** It holds the relation open with `AccessShareLock` across the whole scan and re-reads the relation length as it goes ([pgstattuple.c#pgstat_index](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple.c#L531-L573)), and `AccessShareLock` conflicts only with `ACCESS EXCLUSIVE` ([lock.c#LockConflicts](../../../raw/postgres-17/src/backend/storage/lmgr/lock.c#L64-L104)), so a concurrent `VACUUM` is not excluded. Use the measurement lock.
- **A `pageinspect` census releases its lock between pages.** `get_raw_page_internal` opens the relation, copies one page and closes it per call ([rawpage.c#get_raw_page_internal](../../../raw/postgres-17/contrib/pageinspect/rawpage.c#L141-L199)), so a multi-page census is a sequence of instants.
- **An invalid index is refused by both `pgstattuple` entry points.** The dispatch raises on `!indisvalid` before it reaches any AM arm ([pgstattuple.c#pgstat_relation-dispatch](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple.c#L260-L297)).

### The concurrency rules

- **Flag what the progress views can see.** A census records whether [`pg_stat_progress_vacuum`](../../glossary.md#progress-reporting), `pg_stat_progress_analyze` or `pg_stat_progress_create_index` showed work on the relation at either end of its scan ([system_views.sql#pg_stat_progress_analyze](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1188-L1207), [system_views.sql#pg_stat_progress_vacuum](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1209-L1227), [system_views.sql#pg_stat_progress_create_index](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1256-L1289)).
- **The flag is not a guarantee.** A maintenance command that starts and finishes between the two progress reads leaves no trace in either, so a flagged census is unreliable and an unflagged one is only unrefuted. Where a comparison must be exact, take the lock instead of reading the flags.
- **Read a busy index twice.** Two censuses that disagree on an unchanging file size are evidence of a mixed-instant reading.
- **Do not measure a relation while an index-extension race is possible.** Both `gistvacuumscan` and `spgvacuumscan` take the relation-extension lock momentarily just to read the current length, precisely because a concurrently extended, still-zero page would otherwise look recyclable ([gistvacuum.c#gistvacuumscan-loop](../../../raw/postgres-17/src/backend/access/gist/gistvacuum.c#L209-L227), [spgvacuum.c#spgvacuumscan-loop](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L828-L857)); a SQL census has no such interlock and must hold the measurement lock instead.

### The reading rules

These decide which numbers may be published, and as what.

- **Report page classes separately, per AM.** Whole-page waste, live-page slack and structural pages (metapage, bitmap pages, revmap pages, the SP-GiST root) have different relations to a rebuild. A single combined percentage is page accounting and must be declared a `level` unless it is scored as a bound and holds.
- **Compare an index to its own history or to a rebuilt twin, never to another opclass or another AM.** Only hash, GiST and SP-GiST have a `fillfactor` at all, BRIN has none, and on GiST the fillfactor is a build-time input that the page-fit test ignores and that later inserts do not apply ([gistutil.c#gistfitpage](../../../raw/postgres-17/src/backend/access/gist/gistutil.c#L77-L88), [gist.c#gistinsert-freespace](../../../raw/postgres-17/src/backend/access/gist/gist.c#L184-L185)).
- **On hash, an unused page is capacity, not waste.** A splitpoint allocation writes one page and leaves a hole, and freed overflow pages are returned to the bitmap for reuse in other buckets ([hashpage.c#_hash_alloc_buckets](../../../raw/postgres-17/src/backend/access/hash/hashpage.c#L967-L1037), [hashovfl.c#_hash_getovflpage-bitmap](../../../raw/postgres-17/src/backend/access/hash/hashovfl.c#L222-L252)). A split only happens once the metapage's tuple count passes `ffactor * (maxbucket + 1)` ([hashpage.c#_hash_expandtable-split-test](../../../raw/postgres-17/src/backend/access/hash/hashpage.c#L645-L653)).
- **On BRIN, growth after a `VACUUM` is not waste.** Separate the two by measuring before and after the maintenance step ([brin.c#brinvacuumcleanup](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1307-L1332)).
- **On SP-GiST, a placeholder is not free space and the metapage's free-space cache may be stale.** The cache is per-backend, written back to the metapage occasionally, and its own comment says the recorded free space could be obsolete ([spgist_private.h#SpGistLastUsedPage](../../../raw/postgres-17/src/include/access/spgist_private.h#L94-L126), [spgvacuum.c#metapage-and-fsm](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L859-L875)).
- **On GiST, dead pages that will not go away may be waiting on a transaction, not on `VACUUM`.** The horizon test is in `gistPageRecyclable`, so a run that reports stuck pages also reports whether a snapshot was held ([gistutil.c#gistPageRecyclable](../../../raw/postgres-17/src/backend/access/gist/gistutil.c#L885-L908)).
- **Treat an all-zero page as reclaimable whole-page capacity, not as zero slack.** Every AM's allocator accepts a `PageIsNew` page ([gistutil.c#gistNewBuffer](../../../raw/postgres-17/src/backend/access/gist/gistutil.c#L822-L883), [spgutils.c#SpGistNewBuffer](../../../raw/postgres-17/src/backend/access/spgist/spgutils.c#L379-L420), [brin_pageops.c#brin_page_cleanup](../../../raw/postgres-17/src/backend/access/brin/brin_pageops.c#L610-L661)), and `pageinspect`'s decoders reject or refuse a page whose special area does not match ([hashfuncs.c#verify_hash_page](../../../raw/postgres-17/contrib/pageinspect/hashfuncs.c#L60-L95)).
- **Never publish `pg_relation_size` as allocated bytes on hash.** It is the logical end of file, and the splitpoint hole may not be allocated ([hashpage.c#_hash_alloc_buckets](../../../raw/postgres-17/src/backend/access/hash/hashpage.c#L967-L1037), [dbsize.c#calculate_relation_size](../../../raw/postgres-17/src/backend/utils/adt/dbsize.c#L302-L343)).

### What the protocol does not cover

Named limits, so a consumer page does not claim more than the protocol gives.

- **It scores the number, not the instrument.** Whether a method reads raw pages, `pgstattuple`, `pgstathashindex`, the FSM or the catalogs is out of scope; the declared kind and the oracle are what is checked. A method that cannot run on a required behavior records that it skipped it.
- **No structural verifier exists for any of the four AMs.** `contrib/amcheck` 1.4 ships B-tree and heap verifiers only, so a page census is checked only against readings that share its assumptions ([amcheck--1.3--1.4.sql#bt-only](../../../raw/postgres-17/contrib/amcheck/amcheck--1.3--1.4.sql#L13-L25)).
- **SP-GiST page classes are not decodable from SQL.** `pageinspect` has no SP-GiST section or function, so such a fixture leans on `VACUUM`'s counters and the FSM ([pageinspect.sgml#gist-funcs](../../../raw/postgres-17/doc/src/sgml/pageinspect.sgml#L724-L725), [pageinspect.sgml#hash-funcs](../../../raw/postgres-17/doc/src/sgml/pageinspect.sgml#L814-L815)).
- **Hash's FSM behavior is not cross-checked.** The protocol defines no FSM check for hash because the AM's free-page registry is its bitmap; it makes no claim about what `pg_freespace` returns for a hash index.
- **Allocated bytes are out of scope.** Every size reading is `pg_relation_size`, the logical end of file ([dbsize.c#calculate_relation_size](../../../raw/postgres-17/src/backend/utils/adt/dbsize.c#L302-L343)).
- **One block size and one platform.** Every page constant derives from `BLCKSZ` and `MAXALIGN`; the protocol fixes no second build.
- **The vacuum side of the launcher is recorded, not simulated.** The dead-tuple and insert thresholds are stated under [The maintenance assumption](#the-maintenance-assumption) and never applied, so no fixture builds an index whose dead entries were never vacuumed.
- **A `VACUUM` whose index cleanup did not run is not required coverage.** A conforming run does not have to reach one, and [The maintenance must not be defeated](#the-maintenance-must-not-be-defeated) declares no exception for one. Such a `VACUUM` still returns success: `INDEX_CLEANUP` off and the wraparound failsafe each clear `do_index_cleanup`, and the AM's `amvacuumcleanup` is reached only while it is set ([vacuumlazy.c#do_index_cleanup-init](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L387-L397), [vacuumlazy.c#failsafe-disables-cleanup](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L2320-L2326), [vacuumlazy.c#lazy_cleanup_all_indexes-gate](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1064-L1066)). [Proving the index work actually ran](#proving-the-index-work-actually-ran) therefore still binds every run, but no required fixture shows that proof catching such a `VACUUM`.
- **No fixture overrides the four vacuum-side reloptions.** The census applies the reloption-over-GUC precedence to the analyze parameters only, though the same selection exists for the vacuum and insert-vacuum pairs ([autovacuum.c#vac-effective-values](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2993-L3009)).
- **A [standby](../../glossary.md#hot-standby) is not a scored environment.** `VACUUM` is refused during recovery, and so are the BRIN control functions ([brin.c#brin_summarize_range-recovery](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1384-L1388)).
- **Cross-AM comparison is undefined.** Four AMs run under one protocol so that their claims are produced the same way, not so that their numbers can be compared; the reading rules forbid it explicitly.
- **Parallel vacuum is not part of the protocol.** The four AMs declare different parallel-vacuum options, so a parallel run would reach the same callbacks from a different process ([brin.c#brinhandler-vacuum](../../../raw/postgres-17/src/backend/access/brin/brin.c#L266-L279), [vacuumparallel.c#amusemaintenanceworkmem](../../../raw/postgres-17/src/backend/commands/vacuumparallel.c#L343-L360)); a run states that it measured the serial path.

## Interactions with Other Concepts

- **VACUUM.** The protocol depends on `VACUUM` for every state transition it cannot make itself, and the transition differs per AM: entries removed and overflow pages squeezed on hash, empty leaves deleted on GiST, placeholders trimmed on SP-GiST, and ranges *summarized* on BRIN. It makes four boundaries explicit - it never reproduces the launcher's vacuum verdicts; it does not assume a `VACUUM` that returned actually reached the index; it forbids a fixture from defeating the maintenance it just issued, and names the two cases where defeating it is the declared point; and it treats "the maintenance made the index bigger" as a correct BRIN outcome rather than a fixture error.
- **Autovacuum and auto-analyze.** The protocol assumes both ran and stands in for them rather than modelling an unmaintained database: the maintenance step is the worker's command, the census is the worker's analyze verdict recomputed per table, and the launcher's vacuum-side thresholds are recorded so the gap is visible. The one worker-only behavior in this set is BRIN's summarization work item, which is why that has its own stand-in ([The BRIN summarization stand-in](#the-brin-summarization-stand-in)). How to tune autovacuum for these AMs is not a bloat question and is not decided here.
- **[Cumulative statistics](../../glossary.md#cumulative-statistics).** The census is the only part of the protocol that reads a statistics view rather than a page or a catalog, and it inherits that subsystem's timing: counts are published by a flush and not by a commit, and a view read may be served from a cached snapshot. The protocol fixes the publication points and the fetch consistency and then reads; it makes no claim about the subsystem beyond the counter it uses.
- **The free space map.** The FSM is a cross-check, not a source of truth, and it means different things here: free-versus-in-use for GiST and SP-GiST, graduated free space for BRIN, and nothing at all for hash, which keeps its own bitmap.
- **REINDEX.** The oracle is the blocking `REINDEX INDEX` form. Lock levels, the concurrent form's behavior and failure outcomes belong to the method or to a `REINDEX` question page, not here.
- **B-tree and GIN bloat measurement.** Those two AMs are out of scope and have their own pages, with different contracts: [Mandatory B-Tree Bloat Tests](mandatory-btree-bloat-tests.md) defines a numbered fixture corpus and decision bands, and [Mandatory GIN Bloat Tests](mandatory-gin-bloat-tests.md) defines a protocol with a settle step and a pending list. Both are navigation links; no claim on this page rests on either.
- **The measurement interface.** `pageinspect`, `pgstattuple`, `pg_freespacemap` and `amcheck` are inputs whose refusals shape what a run can say. The protocol scores the number a method publishes, not the extension it came from.

## Open Questions

- **The protocol fixes no fixture corpus, so coverage is self-reported.** [Coverage the protocol requires](#coverage-the-protocol-requires) lists behaviors, not fixtures, and a run says which of its own fixtures reached each one. Two consumer pages can therefore both conform while exercising very different shapes, and nothing here makes their scores comparable.
- **Four access methods under one protocol do not become comparable.** The declared kinds and the oracle are shared, but the page classes, the density references and even the availability of an instrument differ per AM, so a `FALSE NEGATIVE` on BRIN and one on hash are not the same event. Whether each AM should eventually get its own page, the way B-tree and GIN have, is the asker's call.
- **On BRIN the protocol cannot separate bloat from deferred summarization by reading alone.** The mandatory maintenance step summarizes every remaining range, so the only separation available is a before-and-after pair of measurements around the maintenance step ([brin.c#brinvacuumcleanup](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1307-L1332)). A method that runs once, on a maintained index, has no way to tell the two apart.
- **The BRIN stand-in is not the worker's path.** It reproduces the summarization but not the queueing, the drop-on-full-queue case, or the worker's userid and `search_path` switch ([brin.c#brin_summarize_range-guards](../../../raw/postgres-17/src/backend/access/brin/brin.c#L1431-L1464)). Reaching the worker's path at all means letting the launcher run, which the isolation rule forbids.
- **SP-GiST page classes are unverifiable from SQL.** With no `pageinspect` decoder and a `pgstattuple` refusal, an SP-GiST census rests on `VACUUM`'s own counters and the FSM - and those counters are not independent, because `pages_free` and `pages_newly_deleted` are copies of `pages_deleted` ([spgvacuum.c#final-stats](../../../raw/postgres-17/src/backend/access/spgist/spgvacuum.c#L902-L905)). A misclassification consistent with those two readings would pass every cross-check here.
- **Hash's FSM behavior is unresolved on this page.** The protocol defines no FSM cross-check for hash, on the grounds that the AM's free-page registry is its bitmap ([hashovfl.c#_hash_freeovflpage-bitmap](../../../raw/postgres-17/src/backend/access/hash/hashovfl.c#L601-L642)). What `pg_freespace` returns for a hash index in this build has not been established here, and a run that wants that check must establish it first.
- **`pg_relation_size` on hash is a logical size.** The splitpoint hole may never be allocated ([hashpage.c#_hash_alloc_buckets](../../../raw/postgres-17/src/backend/access/hash/hashpage.c#L967-L1037)), so a hash oracle reports returned logical bytes. Whether a run should also report allocated blocks, and with what SQL, is undecided.
- **The hash `VACUUM`-written index count is unreachable under this protocol.** When `hashbulkdelete` did not run, cleanup returns NULL and no index statistics are written; when it did run, the mandatory `ANALYZE` overwrites the count immediately afterwards ([hash.c#hashvacuumcleanup](../../../raw/postgres-17/src/backend/access/hash/hash.c#L647-L663), [analyze.c#index-relstats](../../../raw/postgres-17/src/backend/commands/analyze.c#L647-L662)). No fixture therefore scores a method against the number `VACUUM` alone would have left.
- **GiST's fillfactor is a build-time input only, so "its own fillfactor" is not a density target.** The page-fit test carries a `TODO: Consider fillfactor` and later inserts pass zero free space ([gistutil.c#gistfitpage](../../../raw/postgres-17/src/backend/access/gist/gistutil.c#L77-L88), [gist.c#gistinsert-freespace](../../../raw/postgres-17/src/backend/access/gist/gist.c#L184-L185)). What a "healthy" GiST density is, against a rebuild that may have been sorted, is not settled by this page.
- **The vacuum side of the launcher is assumed, never simulated.** [The maintenance assumption](#the-maintenance-assumption) records the dead-tuple and insert thresholds and then runs the maintenance step regardless of them, so the protocol has no counterpart to the census on the vacuum side, and no sub-threshold unmaintained fixture exists.
- **The effectiveness proof of [The maintenance must not be defeated](#the-maintenance-must-not-be-defeated) is one-sided.** A nonzero `dead but not yet removable` count proves the horizon was pinned ([vacuumlazy.c#verbose-tuples-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L657-L663)), but a zero count proves only that nothing was pinned for that table at that moment, and a fixture whose churn deleted and updated nothing produces no signal at all. Nothing in the engine reports "no session or slot held the horizon for the duration of this command": `pg_stat_activity` and `pg_replication_slots` are reads taken beside the maintenance step, not interlocks around it ([system_views.sql#pg_stat_activity-xmin](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L878-L885), [system_views.sql#pg_replication_slots-xmin](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1006-L1017)). On such a fixture the rule rests on the per-AM index proof alone.
- **The census's second publication point has no proof.** A run can force a flush and then read, but nothing in the engine reports "every pending count for this relation is published", so a partial flush under lock contention looks identical to having had nothing pending ([pgstat.c#pgstat_report_stat](../../../raw/postgres-17/src/backend/utils/activity/pgstat.c#L583-L600)).
- **Parallel vacuum is excluded by rule, not by evidence.** The four AMs advertise different parallel-vacuum options ([brin.c#brinhandler-vacuum](../../../raw/postgres-17/src/backend/access/brin/brin.c#L266-L279)), and whether a parallel run would leave a different page census has not been checked here.
- **No filed run has ever been produced under this protocol.** It is new on this page, so every number currently filed for a hash, GiST, SP-GiST or BRIN index in this wiki predates it, including the non-core AM admission rule, which no run has exercised at all.
