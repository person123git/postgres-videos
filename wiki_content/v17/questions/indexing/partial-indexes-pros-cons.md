## Question

What are the pros and cons of partial indexes in PostgreSQL 17? Include a section on statistics generated and used by the query planner. Consider partial indexes on expressions and ordinary expression indexes too.

## Answer

A PostgreSQL 17 partial index is an index with a `WHERE` predicate; it contains entries only for table rows that satisfy that predicate.[indices.sgml#Partial-Indexes](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L801-L816) [create_index.sgml#partial-index-description](../../../../raw/postgres-17/doc/src/sgml/ref/create_index.sgml#L66-L86)

The main benefit is a smaller, more focused access path for rows that matter to a workload. The main cost is that the planner can use the index only when it can prove, at planning time, that the query condition implies the index predicate.[indices.sgml#partial-index-benefit](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L818-L899) [indices.sgml#partial-index-matching](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L943-L969) [indxpath.c#check_index_predicates](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3243-L3350)

Ordinary expression indexes are the baseline: the key is a function or scalar expression, not a simple table column. They can speed reads by storing computed values, but they compute those values during writes.[indices.sgml#indexes-expressional](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L732-L786) [indices.sgml#index-expression-maintenance](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L787-L798)

### Short answer

| Area | Benefit | Cost or caveat |
| --- | --- | --- |
| Size and write cost | Excluding common or uninteresting rows reduces index size and can avoid index updates for rows outside the predicate.[indices.sgml#exclude-common-values](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L818-L828) | Index build and executor index maintenance still evaluate the predicate before they decide to skip the index entry.[heapam_handler.c#partial-index-build-filter](../../../../raw/postgres-17/src/backend/access/heap/heapam_handler.c#L1631-L1644) [execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-17/src/backend/executor/execIndexing.c#L368-L397) |
| Read performance | Queries whose `WHERE` clauses imply the predicate can use the smaller index, even when the indexed column and predicate column differ.[indices.sgml#partial-index-column-vs-predicate](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L900-L953) | Queries that do not imply the predicate cannot use that partial index; parameterized clauses such as `x < ?` do not prove a fixed predicate for all parameter values.[indices.sgml#partial-index-matching](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L943-L969) |
| Conditional uniqueness | A unique partial index enforces uniqueness only for predicate-satisfying rows.[indices.sgml#partial-unique-index](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L971-L1005) | A partial or expression index cannot be adopted as a primary-key or unique table constraint through `ALTER TABLE ... ADD CONSTRAINT ... USING INDEX`.[parse_utilcmd.c#constraint-using-index-rejects-exprs-predicates](../../../../raw/postgres-17/src/backend/parser/parse_utilcmd.c#L2286-L2313) |
| Expression keys | An ordinary expression index stores computed key values, can enforce computed uniqueness, and lets searches compare against stored expression values.[indices.sgml#indexes-expressional](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L740-L786) | Expression keys are computed for each insertion and non-HOT update that needs an index entry.[indices.sgml#index-expression-maintenance](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L787-L798) [index.c#FormIndexDatum](../../../../raw/postgres-17/src/backend/catalog/index.c#L2730-L2777) |
| Planner statistics | `ANALYZE` estimates partial-index row counts from sampled rows that pass the predicate and stores expression-index statistics in `pg_statistic` with `starelid` pointing to the index.[analyze.c#compute_index_stats](../../../../raw/postgres-17/src/backend/commands/analyze.c#L828-L977) [catalogs.sgml#pg-statistic-index-expressions](../../../../raw/postgres-17/doc/src/sgml/catalogs.sgml#L7409-L7417) | Default selectivity code uses expression statistics from non-partial expression indexes as whole-relation stats, but not from partial expression indexes unless an index statistics hook supplies them.[selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L5193-L5216) |

### How PostgreSQL stores partial and expression indexes

The SQL surface is `CREATE INDEX` with index keys that may be column names or parenthesized expressions, plus an optional trailing `WHERE predicate`.[create_index.sgml#synopsis](../../../../raw/postgres-17/doc/src/sgml/ref/create_index.sgml#L23-L31) The documentation defines a partial index as the case where that `WHERE` clause is present, and says that predicate and expression definitions can refer only to columns of the indexed table, cannot use subqueries or aggregate expressions, and must use immutable functions and operators.[create_index.sgml#partial-index-description](../../../../raw/postgres-17/doc/src/sgml/ref/create_index.sgml#L66-L96)

Parse analysis transforms the predicate as `EXPR_KIND_INDEX_PREDICATE` and index expressions as `EXPR_KIND_INDEX_EXPRESSION`; the source notes that expression transformation should already reject subqueries, aggregates, window functions, and set-returning functions for index expressions.[parse_utilcmd.c#transformIndexStmt](../../../../raw/postgres-17/src/backend/parser/parse_utilcmd.c#L2799-L2874) `DefineIndex()` calls `CheckPredicate()` for a predicate, and `CheckPredicate()` rejects mutable functions in the predicate while leaving broad predicate forms for `indxpath.c` to reason about later.[indexcmds.c#CheckPredicate-call](../../../../raw/postgres-17/src/backend/commands/indexcmds.c#L888-L892) [indexcmds.c#CheckPredicate](../../../../raw/postgres-17/src/backend/commands/indexcmds.c#L1798-L1823) Expression columns are marked with `ii_IndexAttrNumbers[attn] = 0`, stored in `ii_Expressions`, and checked for mutable functions in `ComputeIndexAttrs()`.[indexcmds.c#index-expression-validation](../../../../raw/postgres-17/src/backend/commands/indexcmds.c#L1920-L1968)

The generated catalog header for `pg_index` defines `indkey`, `indexprs`, and `indpred`: `indkey` stores column numbers or zero for expression columns, `indexprs` stores expression trees for zero `indkey` entries, and `indpred` stores the partial-index predicate or null.[pg_index.h#pg_index-fields](../../../../raw/postgres-17/src/include/catalog/pg_index.h#L24-L62) The catalog documentation says the same thing in SQL terms.[catalogs.sgml#pg-index-expressions-and-predicate](../../../../raw/postgres-17/doc/src/sgml/catalogs.sgml#L4498-L4575)

`index_create()` serializes expression and predicate trees with `nodeToString()` into the `pg_index.indexprs` and `pg_index.indpred` columns, storing nulls when those parts are absent.[index.c#index_create-serialize-exprs-predicate](../../../../raw/postgres-17/src/backend/catalog/index.c#L596-L660) `BuildIndexInfo()` later reconstructs executable `IndexInfo` from the index relation by calling `RelationGetIndexExpressions()` and `RelationGetIndexPredicate()`.[index.c#BuildIndexInfo](../../../../raw/postgres-17/src/backend/catalog/index.c#L2420-L2451) `IndexInfo` then carries `ii_IndexAttrNumbers`, `ii_Expressions`, `ii_ExpressionsState`, `ii_Predicate`, and `ii_PredicateState` for build and executor paths.[execnodes.h#IndexInfo](../../../../raw/postgres-17/src/include/nodes/execnodes.h#L183-L211)

The relcache path converts stored text back to node trees. For expression indexes, `RelationGetIndexExpressions()` reads `pg_index.indexprs`, runs `eval_const_expressions()`, fixes operator function IDs, and caches a copy in the relcache.[relcache.c#RelationGetIndexExpressions](../../../../raw/postgres-17/src/backend/utils/cache/relcache.c#L5052-L5110) For partial indexes, `RelationGetIndexPredicate()` reads `pg_index.indpred`, runs constant simplification and qual canonicalization, converts the result to implicit-AND form, fixes operator function IDs, and caches it in the relcache.[relcache.c#RelationGetIndexPredicate](../../../../raw/postgres-17/src/backend/utils/cache/relcache.c#L5164-L5230)

### Build and DML maintenance

During a heap index build, the heap access method stores each candidate heap tuple in the executor slot, evaluates the partial-index predicate if one exists, and skips the tuple before forming index values when `ExecQual()` returns false.[heapam_handler.c#partial-index-build-filter](../../../../raw/postgres-17/src/backend/access/heap/heapam_handler.c#L1631-L1644) For executor-side index maintenance, `ExecInsertIndexTuples()` skips indexes not ready for inserts, prepares the partial-index predicate state if needed, evaluates it, and skips the index update before calling `FormIndexDatum()` when the predicate is false.[execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-17/src/backend/executor/execIndexing.c#L339-L397)

`FormIndexDatum()` prepares expression states on first use and evaluates expression-key columns with `ExecEvalExprSwitchContext()` when the index attribute number is zero.[index.c#FormIndexDatum](../../../../raw/postgres-17/src/backend/catalog/index.c#L2730-L2777) Therefore a partial expression index checks the predicate before expression-key computation in the executor maintenance path, but rows that pass the predicate pay the normal expression-index computation cost.[execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-17/src/backend/executor/execIndexing.c#L368-L397) [index.c#FormIndexDatum](../../../../raw/postgres-17/src/backend/catalog/index.c#L2730-L2777)

### Planner matching and plan shape

The planner stores per-index metadata in `IndexOptInfo`. The struct comments say zero `indexkeys[]` entries represent expression columns, `indexprs` holds one expression per zero entry, `indpred` is in implicit-AND form, `indrestrictinfo` is the table restriction list after partial-index predicate reasoning, and `predOK` records whether the predicate matches the query.[pathnodes.h#IndexOptInfo](../../../../raw/postgres-17/src/include/nodes/pathnodes.h#L1068-L1181)

`get_relation_info()` ignores invalid indexes for planner purposes, reads index keys/opfamilies/collations, loads `indexprs` and `indpred` through the relcache, rewrites varnos when needed, builds the index target list, and initializes `predOK = false`.[plancat.c#get_relation_info-index-metadata](../../../../raw/postgres-17/src/backend/optimizer/util/plancat.c#L240-L267) [plancat.c#get_relation_info-index-predicate](../../../../raw/postgres-17/src/backend/optimizer/util/plancat.c#L441-L459) For non-partial physical indexes it sets `IndexOptInfo.tuples` to the parent table row estimate, while for partial physical indexes it estimates the index relation's own size and caps the tuple estimate at the table row estimate.[plancat.c#get_relation_info-index-size](../../../../raw/postgres-17/src/backend/optimizer/util/plancat.c#L463-L507)

`check_index_predicates()` constructs a proof context from base restriction clauses, movable join clauses, and equivalence-derived join clauses, then sets `predOK` when `predicate_implied_by(index->indpred, clauselist, false)` succeeds.[indxpath.c#check_index_predicates](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3243-L3350) `predicate_implied_by()` implements strong implication for proving that rows satisfying one `WHERE` clause or index predicate must satisfy another; it assumes the predicate contains only immutable functions and operators.[predtest.c#predicate_implied_by](../../../../raw/postgres-17/src/backend/optimizer/util/predtest.c#L115-L180)

Plain index-path creation skips a partial index when `index->indpred != NIL && !index->predOK`.[indxpath.c#create_index_paths](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L252-L280) Bitmap-OR path generation has a separate path: `check_index_predicates()` still computes `indrestrictinfo` for non-`predOK` partial indexes because `generate_bitmap_or_paths()` may be able to use them inside OR arms.[indxpath.c#check_index_predicates-indrestrictinfo](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3333-L3379) [indxpath.c#generate_bitmap_or_paths](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L1169-L1249)

For non-target relations, `check_index_predicates()` removes base restrictions implied by the partial-index predicate from `indrestrictinfo`, so an index-scan plan using that index need not retest those implied quals. It keeps them for UPDATE, DELETE, MERGE, and `SELECT FOR UPDATE` target relations so EvalPlanQual can recheck them.[indxpath.c#check_index_predicates-target-rel](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3318-L3331) [indxpath.c#check_index_predicates-indrestrictinfo](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3356-L3379) Bitmap heap scans are different: `create_bitmap_subplan()` includes partial-index predicates in bitmap quals when they are not already implied by the bitmap subqual, because lossy bitmap scans must recheck predicates as well as index conditions.[createplan.c#create_bitmap_subplan](../../../../raw/postgres-17/src/backend/optimizer/plan/createplan.c#L3316-L3321) [createplan.c#create_bitmap_subplan-predicate](../../../../raw/postgres-17/src/backend/optimizer/plan/createplan.c#L3504-L3531)

Expression-key matching is a separate gate. `match_clause_to_indexcol()` accepts operator, function, scalar-array, row-comparison, boolean, and supported null-test clauses when they match the index key, operator family, and collation rules.[indxpath.c#match_clause_to_indexcol](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L2138-L2252) In the common operator case, `match_opclause_to_indexcol()` requires either `indexkey operator constant` or `constant operator indexkey`, checks the operator family and collation, and commutes the clause when needed.[indxpath.c#match_opclause_to_indexcol](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L2388-L2477) `match_index_to_operand()` handles expression keys by locating the matching `indexprs` entry for a zero `indexkeys[]` position and testing `equal(indexkey, operand)` after stripping a relabel node.[indxpath.c#match_index_to_operand](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3667-L3744)

### Ordinary expression indexes as the baseline

An ordinary expression index is a non-partial index whose key is a function or scalar expression computed from table columns; the documentation gives `lower(col1)` and `(first_name || ' ' || last_name)` examples.[indices.sgml#indexes-expressional](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L732-L786) PostgreSQL stores expression keys in the same `pg_index.indexprs` mechanism used by partial expression indexes, but `pg_index.indpred` is null for a non-partial expression index.[pg_index.h#pg_index-fields](../../../../raw/postgres-17/src/include/catalog/pg_index.h#L48-L62) [index.c#index_create-serialize-exprs-predicate](../../../../raw/postgres-17/src/backend/catalog/index.c#L596-L660)

Planner matching for an ordinary expression index does not need a predicate implication proof because `indpred` is null. It still needs clause-to-key matching through `match_clause_to_indexcol()` and `match_index_to_operand()`.[indxpath.c#create_index_paths](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L260-L266) [indxpath.c#match_clause_to_indexcol](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L2138-L2252) [indxpath.c#match_index_to_operand](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3667-L3744)

`ANALYZE` treats ordinary expression-index columns as possible whole-relation expression-statistics sources. It creates `VacAttrStats` entries only for expression index columns where `ii_IndexAttrNumbers[i] == 0`, and selectivity code later searches matching expression index columns for `pg_statistic` rows only when `index->indpred == NIL` unless a hook takes control.[analyze.c#do_analyze_rel-indexdata](../../../../raw/postgres-17/src/backend/commands/analyze.c#L445-L479) [selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L5134-L5235)

### Partial indexes on expressions

PostgreSQL 17 can combine both features: the index key can be an expression and the index can also have a partial predicate. The syntax permits expression keys and a trailing `WHERE predicate`, and the catalog stores expression keys and predicates independently in `indexprs` and `indpred`.[create_index.sgml#synopsis](../../../../raw/postgres-17/doc/src/sgml/ref/create_index.sgml#L23-L31) [catalogs.sgml#pg-index-expressions-and-predicate](../../../../raw/postgres-17/doc/src/sgml/catalogs.sgml#L4498-L4575)

A partial expression index has two planner gates. First, the query must imply the predicate so `predOK` can become true, except for special bitmap-OR handling. Second, the query clause must match the expression key.[indxpath.c#check_index_predicates](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3243-L3350) [indxpath.c#create_index_paths](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L260-L266) [indxpath.c#match_index_to_operand](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3667-L3744)

`ANALYZE` also combines both features. `compute_index_stats()` evaluates the partial predicate against each sampled heap row, counts only rows that pass, estimates `tupleFract`, and computes expression-column statistics from only those predicate-passing sample rows.[analyze.c#compute_index_stats](../../../../raw/postgres-17/src/backend/commands/analyze.c#L879-L971) Those expression statistics are stored with `starelid` referencing the index, but the default expression-stat lookup path does not use partial expression-index statistics as whole-relation statistics because the source says partial indexes probably do not reflect whole-relation statistics.[catalogs.sgml#pg-statistic-index-expressions](../../../../raw/postgres-17/doc/src/sgml/catalogs.sgml#L7409-L7417) [selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L5193-L5216)

`ON CONFLICT` unique-index inference can match expression indexes and partial indexes, but partial unique indexes require the `ON CONFLICT ... WHERE` clause to imply the index predicate.[plancat.c#infer_arbiter_indexes](../../../../raw/postgres-17/src/backend/optimizer/util/plancat.c#L850-L950) Regression coverage includes a partial expression unique index that is not inferred without an inference predicate, expression unique indexes that are inferred or rejected by expression match, and a partial unique index inferred only when the `ON CONFLICT` predicate covers the index predicate.[insert_conflict.sql#partial-and-expression-inference](../../../../raw/postgres-17/src/test/regress/sql/insert_conflict.sql#L148-L232) [insert_conflict.out#partial-and-expression-inference](../../../../raw/postgres-17/src/test/regress/expected/insert_conflict.out#L311-L402)

### Pros

- **Smaller index and less write maintenance for excluded rows.** The documentation names avoiding common values as a major reason for partial indexes and says this reduces index size, speeds queries that use the index, and speeds many table updates because the index need not be updated in all cases.[indices.sgml#exclude-common-values](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L818-L828)
- **Focused access path for hot subsets.** The documentation's unbilled-orders example indexes only unbilled rows and says this can be useful even when the query predicate does not constrain the indexed key column, provided the partial-index predicate is present.[indices.sgml#partial-index-unbilled-example](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L900-L941)
- **Conditional uniqueness.** A unique partial index enforces uniqueness among rows that satisfy the predicate without constraining rows outside the predicate.[indices.sgml#partial-unique-index](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L971-L1005)
- **Computed-key access and uniqueness.** Expression indexes can store computed keys such as `lower(col1)` or `(first_name || ' ' || last_name)`, and a unique expression index can enforce a computed uniqueness rule that is not a simple unique constraint.[indices.sgml#indexes-expressional](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L740-L786)
- **Planner steering for unusual distributions.** The documentation says a partial index can make an index unavailable to an offending query when peculiar distributions cause a bad plan choice.[indices.sgml#partial-index-plan-steering](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L1007-L1018)
- **Useful with `ON CONFLICT` when the predicate is covered.** `infer_arbiter_indexes()` accepts a matching partial unique index only after proving that the arbiter `WHERE` clause implies the index predicate.[plancat.c#infer_arbiter_indexes](../../../../raw/postgres-17/src/backend/optimizer/util/plancat.c#L928-L939)

### Cons and restrictions

- **Predicate matching is limited and planning-time only.** PostgreSQL 17 recognizes simple implications such as `x < 1` implying `x < 2`, but otherwise needs the predicate condition to match the query's `WHERE` condition, and parameterized query clauses do not imply fixed predicates for all parameter values.[indices.sgml#partial-index-matching](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L943-L969)
- **The predicate can become a poor fit as data distribution changes.** The documentation says partial indexes that exclude common values require those values to be predetermined, work best when distributions do not change, and may need recreation as distributions shift.[indices.sgml#partial-index-distribution-maintenance](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L880-L886)
- **Excluded rows cannot use that index.** The documentation warns that excluding uninteresting values prevents those values from being accessed through that index, even if an index scan might otherwise be profitable.[indices.sgml#exclude-uninteresting-values](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L889-L899)
- **Predicate checks remain write-time work.** Build and executor maintenance paths evaluate the partial-index predicate before skipping excluded rows.[heapam_handler.c#partial-index-build-filter](../../../../raw/postgres-17/src/backend/access/heap/heapam_handler.c#L1631-L1644) [execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-17/src/backend/executor/execIndexing.c#L368-L397)
- **Expression keys remain write-time work for included rows.** Expression values are computed on insertion and non-HOT update, and `FormIndexDatum()` evaluates expression-key states for zero `ii_IndexAttrNumbers` entries.[indices.sgml#index-expression-maintenance](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L787-L798) [index.c#FormIndexDatum](../../../../raw/postgres-17/src/backend/catalog/index.c#L2730-L2777)
- **Existing partial or expression indexes cannot be converted into primary-key or unique table constraints.** The `USING INDEX` constraint path rejects indexes with expressions and rejects partial indexes.[parse_utilcmd.c#constraint-using-index-rejects-exprs-predicates](../../../../raw/postgres-17/src/backend/parser/parse_utilcmd.c#L2286-L2313)
- **Replica identity rejects expression and partial indexes.** `ALTER TABLE ... REPLICA IDENTITY USING INDEX` rejects expression indexes and predicate indexes before checking nullable columns.[tablecmds.c#ATExecReplicaIdentity](../../../../raw/postgres-17/src/backend/commands/tablecmds.c#L16837-L16902) The regression suite covers both errors.[replica_identity.sql#expression-and-partial-replica-identity](../../../../raw/postgres-17/src/test/regress/sql/replica_identity.sql#L13-L40) [replica_identity.out#expression-and-partial-replica-identity](../../../../raw/postgres-17/src/test/regress/expected/replica_identity.out#L49-L55)
- **`CLUSTER` rejects partial indexes.** `check_index_is_clusterable()` rejects any index whose `pg_index.indpred` is not null because it might not index every row of the relation.[cluster.c#check_index_is_clusterable](../../../../raw/postgres-17/src/backend/commands/cluster.c#L500-L549)
- **`REFRESH MATERIALIZED VIEW CONCURRENTLY` needs a complete plain-column unique index.** The documentation requires at least one unique index that uses only column names and includes all rows, meaning no expression index and no `WHERE` clause.[refresh_materialized_view.sgml#CONCURRENTLY-index-requirement](../../../../raw/postgres-17/doc/src/sgml/ref/refresh_materialized_view.sgml#L54-L73) The implementation's `is_usable_unique_index()` requires a unique, immediate, valid, non-partial B-tree index and rejects expression columns by requiring positive `indkey` values.[matview.c#RefreshMatViewByOid-concurrent-index-check](../../../../raw/postgres-17/src/backend/commands/matview.c#L243-L272) [matview.c#is_usable_unique_index](../../../../raw/postgres-17/src/backend/commands/matview.c#L902-L936)
- **Some uniqueness deductions are predicate-gated.** `has_unique_index()` uses a single-column unique partial index only when `predOK` is true, and it ignores expression indexes for that whole-relation attribute distinctness proof.[plancat.c#has_unique_index](../../../../raw/postgres-17/src/backend/optimizer/util/plancat.c#L2212-L2236)
- **`ON CONFLICT` partial inference needs a covered predicate.** `infer_arbiter_indexes()` rejects a partial unique index when the `ON CONFLICT` arbiter `WHERE` clause does not imply the index predicate.[plancat.c#infer_arbiter_indexes](../../../../raw/postgres-17/src/backend/optimizer/util/plancat.c#L928-L950)
- **Creating the index requires `USAGE` on every type the predicate depends on.** Since PostgreSQL 17.11, commit `d1c8aa0b09f` (CVE-2026-6470, back-patched through v14), `DefineIndex()` walks the predicate's type dependencies and checks `USAGE` for the invoking role before it calls `index_create()`, so a role that lacks `USAGE` on a predicate type cannot create the partial index.[indexcmds.c#predicate-type-usage-check](../../../../raw/postgres-17/src/backend/commands/indexcmds.c#L941-L944) [dependency.c#CheckUsageOnTypesInSingleRelExpr](../../../../raw/postgres-17/src/backend/catalog/dependency.c#L1741-L1767) The same check covers index expressions, and the regression suite exercises the expression form.[privileges.sql:959](../../../../raw/postgres-17/src/test/regress/sql/privileges.sql#L959) [privileges.out#create-index-type-usage](../../../../raw/postgres-17/src/test/regress/expected/privileges.out#L1357-L1358)

### Statistics generated by `ANALYZE`

`ANALYZE` collects table-content statistics into `pg_statistic`, and the query planner uses those statistics to choose execution plans.[analyze.sgml#description](../../../../raw/postgres-17/doc/src/sgml/ref/analyze.sgml#L42-L57) The documentation says the collected statistics usually include most-common values and histograms, and that large tables are sampled rather than fully scanned, so the statistics are approximate.[analyze.sgml#notes-statistics](../../../../raw/postgres-17/doc/src/sgml/ref/analyze.sgml#L219-L268) `pg_statistic` has fixed fields for null fraction, width, and distinct-value estimates, plus slot fields for statistics kinds, operators, collations, numbers, and values.[pg_statistic.h#pg_statistic-fields](../../../../raw/postgres-17/src/include/catalog/pg_statistic.h#L35-L109)

For index statistics, `do_analyze_rel()` builds `AnlIndexData`, initializes `tupleFract = 1.0`, and creates `VacAttrStats` only for index expression columns when no explicit column list was supplied.[analyze.c#do_analyze_rel-indexdata](../../../../raw/postgres-17/src/backend/commands/analyze.c#L445-L479) It later writes table stats and each index's expression stats through `update_attstats()`.[analyze.c#do_analyze_rel-write-stats](../../../../raw/postgres-17/src/backend/commands/analyze.c#L580-L602) `update_attstats()` writes `starelid`, `staattnum`, `stainherit`, `stanullfrac`, `stawidth`, `stadistinct`, and the slot fields into `pg_statistic`.[analyze.c#update_attstats](../../../../raw/postgres-17/src/backend/commands/analyze.c#L1587-L1671)

For a partial index, `compute_index_stats()` creates executor state, prepares the predicate, evaluates it for each sampled heap row, skips rows that fail, counts `numindexrows`, computes `tupleFract = numindexrows / numrows`, and estimates `totalindexrows = ceil(tupleFract * totalrows)`.[analyze.c#compute_index_stats](../../../../raw/postgres-17/src/backend/commands/analyze.c#L828-L977) For expression columns, it calls `FormIndexDatum()` for predicate-passing sample rows and computes expression-column statistics from `numindexrows` and `totalindexrows`.[analyze.c#compute_index_stats](../../../../raw/postgres-17/src/backend/commands/analyze.c#L910-L971)

`ANALYZE` also updates `pg_class` row-count and page-count estimates for index relations. For each index, it computes `totalindexrows = ceil(tupleFract * totalrows)` and calls `vac_update_relstats()` with `RelationGetNumberOfBlocks(Irel[ind])` and that row estimate.[analyze.c#do_analyze_rel-index-relstats](../../../../raw/postgres-17/src/backend/commands/analyze.c#L647-L663) `vac_update_relstats()` writes whole-relation `pg_class` statistics such as `relpages` and `reltuples` for heap and index relations.[vacuum.c#vac_update_relstats](../../../../raw/postgres-17/src/backend/commands/vacuum.c#L1370-L1456)

`pg_statistic` stores statistics for index expressions with `starelid` referencing the index and does not store redundant rows for ordinary non-expression index columns.[catalogs.sgml#pg-statistic-index-expressions](../../../../raw/postgres-17/doc/src/sgml/catalogs.sgml#L7409-L7417) `examine_attribute()` uses an expression tree's type, typmod, and collation when analyzing an expression index column.[analyze.c#examine_attribute](../../../../raw/postgres-17/src/backend/commands/analyze.c#L999-L1078)

### How the planner uses those statistics

For a simple table column, `examine_variable()` calls `has_unique_index()` for uniqueness information and then `examine_simple_variable()` to find the column's statistics.[selfuncs.c#examine_variable-simple-var](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L5056-L5076) Equality selectivity uses `stanullfrac`, a unique-index shortcut, and MCV statistics when a statistics tuple is present.[selfuncs.c#var_eq_const](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L306-L360) Inequality selectivity falls back to defaults without statistics, otherwise combines MCV and histogram evidence.[selfuncs.c#scalarineqsel](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L592-L687) [selfuncs.c#mcv_selectivity](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L738-L790) [selfuncs.c#histogram_selectivity](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L792-L847) That fallback is stricter since PostgreSQL 17.11: the one exception, a `ctid` variable estimated from the table size, now also requires the comparison constant to be of type `tid`, so a `ctid` inequality against a constant of any other type takes the default estimate (commit `0ebf896f44d`, CVE-2026-14668).[selfuncs.c#scalarineqsel-ctid-guard](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L599-L601)

For expression clauses, `examine_variable()` searches expression-index columns on the same base relation. If the expression matches an index expression, it can mark the expression unique when the index is unique, single-key, first-column, and either non-partial or `predOK`.[selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L5134-L5191) It only reads `pg_statistic` for non-partial expression indexes by default; the source says partial indexes probably do not reflect whole-relation statistics and leaves partial-index decisions to `get_index_stats_hook` if one is installed.[selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L5193-L5216)

For index path costing, `genericcostestimate()` adds the partial-index predicate to the explicit index quals through `add_predicate_to_index_quals()`, estimates `indexSelectivity` with `clauselist_selectivity()`, estimates visited index tuples from `indexSelectivity * index->rel->tuples`, bounds that by `index->tuples`, and estimates visited index pages as a pro-rata fraction of index pages.[selfuncs.c#genericcostestimate](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L6626-L6828) `btcostestimate()` does the same predicate addition for B-tree boundary quals before estimating `numIndexTuples`, then delegates to `genericcostestimate()`.[selfuncs.c#btcostestimate-partial-selectivity](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L6989-L7073)

`add_predicate_to_index_quals()` adds only predicate clauses that are not already implied by the explicit index quals, because redundant clauses can make `clauselist_selectivity()` estimate selectivity too low.[selfuncs.c#add_predicate_to_index_quals](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L6831-L6867) This means the planner can cost a partial index with its predicate included in selectivity, even though default expression-stat lookup does not treat partial expression-index statistics as whole-relation expression statistics.[selfuncs.c#genericcostestimate](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L6650-L6715) [selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L5193-L5216)

### What changed from PostgreSQL 12

The core partial-index machinery is still recognizable from the PostgreSQL 12 baseline: PostgreSQL 17 still stores the predicate in `pg_index.indpred`, filters build and DML maintenance through `ii_Predicate`, proves planner usability with `predOK`/`predicate_implied_by()`, and estimates partial-index row counts during `ANALYZE` by evaluating the predicate on sampled heap rows.[pg_index.h#pg_index-fields](../../../../raw/postgres-17/src/include/catalog/pg_index.h#L48-L62) [execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-17/src/backend/executor/execIndexing.c#L368-L397) [indxpath.c#check_index_predicates](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3243-L3379) [analyze.c#compute_index_stats](../../../../raw/postgres-17/src/backend/commands/analyze.c#L828-L977) For the PostgreSQL 12 companion baseline, see [Pros and Cons of Partial Indexes in PostgreSQL 12](../../../v12/questions/indexing/partial-indexes-pros-cons.md).

The important changes and additions in PostgreSQL 17 relative to that baseline are these:

1. **The documentation now explicitly warns against “partial-index partitioning”.** A post-v12 documentation change, commit `6a8e5605b53`, added the `Do Not Use Partial Indexes as a Substitute for Partitioning` example. PostgreSQL 17 says that a large set of non-overlapping partial indexes is usually worse than one composite non-partial index or real partitioning, because the planner does not understand relationships among those partial indexes and must test each one for applicability.[indices.sgml#partial-indexes-not-partitioning](../../../../raw/postgres-17/doc/src/sgml/indices.sgml#L1031-L1070)

2. **Concurrent builds gained a safe-snapshot optimization, but partial and expression indexes are excluded from it.** PostgreSQL 14 commit `c98763bf51b` added `PROC_IN_SAFE_IC` so some concurrent index builds can be ignored by other concurrent index operations' old-snapshot waits. PostgreSQL 17 marks an index as safe only when it has no expression columns and no predicate, calls `set_indexsafe_procflags()` only for such safe indexes during `CREATE INDEX CONCURRENTLY`, and excludes `PROC_IN_SAFE_IC` backends from `WaitForOlderSnapshots()`.[indexcmds.c#safe-index-test](../../../../raw/postgres-17/src/backend/commands/indexcmds.c#L1144-L1146) [indexcmds.c#create-index-concurrently-safe-flag-phase2](../../../../raw/postgres-17/src/backend/commands/indexcmds.c#L1621-L1623) [indexcmds.c#create-index-concurrently-safe-flag-phase3](../../../../raw/postgres-17/src/backend/commands/indexcmds.c#L1693-L1695) [indexcmds.c#WaitForOlderSnapshots](../../../../raw/postgres-17/src/backend/commands/indexcmds.c#L433-L463)

3. **`MERGE` joined the target-relation partial-index recheck rule.** PostgreSQL 15 commit `7103ebb7aae` added `MERGE`. In PostgreSQL 17, `check_index_predicates()` explicitly treats UPDATE, DELETE, MERGE, and `SELECT FOR UPDATE` target relations as relations whose partial-index-implied quals must remain in `indrestrictinfo` for EvalPlanQual rechecks; it now detects target relations through `root->all_result_relids` plus rowmarks.[indxpath.c#check_index_predicates-target-rel](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3318-L3331)

4. **Expression statistics no longer require an expression index.** PostgreSQL 14 commit `a4d75c86bf1` added extended statistics on expressions. PostgreSQL 17 documents that `CREATE STATISTICS` can collect univariate statistics for one expression with benefits similar to an expression index but without index-maintenance overhead, and that multivariate statistics can include columns and/or expressions.[create_statistics.sgml#expression-statistics](../../../../raw/postgres-17/doc/src/sgml/ref/create_statistics.sgml#L46-L56) This does not change the partial-expression-index rule described above: default selectivity code still avoids using partial expression-index statistics as whole-relation expression statistics unless a hook supplies them.[selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-17/src/backend/utils/adt/selfuncs.c#L5193-L5216)

5. **Unique indexes gained `NULLS NOT DISTINCT`.** PostgreSQL 15 commit `94aa7cc5f70` added the unique-index null-treatment option. PostgreSQL 17 `CREATE INDEX` syntax has `[ NULLS [ NOT ] DISTINCT ]` before the optional `WHERE predicate`, the docs say the option controls whether null values are considered distinct for a unique index, and `pg_index` stores the choice in `indnullsnotdistinct`.[create_index.sgml#synopsis](../../../../raw/postgres-17/doc/src/sgml/ref/create_index.sgml#L23-L31) [create_index.sgml#nulls-not-distinct](../../../../raw/postgres-17/doc/src/sgml/ref/create_index.sgml#L339-L349) [pg_index.h#pg_index-fields](../../../../raw/postgres-17/src/include/catalog/pg_index.h#L33-L40)

6. **Partial unique indexes no longer prove relation uniqueness for join planning.** PostgreSQL 16 commit `7fcd7ef2a9c` changed `relation_has_unique_index_for()` so it skips all partial indexes, even when `predOK` is true. The source explains that `predOK` may have been proven using join predicates, while this uniqueness proof must hold before joins are evaluated.[indxpath.c#relation_has_unique_index_for-partial](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3509-L3518)

7. **Partial indexes on non-optional-key access methods have a planning fix.** In the pinned PostgreSQL 17 stable checkout, commit `e79b2766216` makes `check_index_predicates()` keep `indrestrictinfo` unchanged for `!amoptionalkey` indexes, avoiding removal of every first-key qual and failure to generate an index scan. The regression suite now creates a partial hash index and verifies an index scan for `WHERE seqno = 9999`.[indxpath.c#check_index_predicates-amoptionalkey](../../../../raw/postgres-17/src/backend/optimizer/path/indxpath.c#L3352-L3364) [hash_index.sql#partial-hash-index](../../../../raw/postgres-17/src/test/regress/sql/hash_index.sql#L56-L65) [hash_index.out#partial-hash-index](../../../../raw/postgres-17/src/test/regress/expected/hash_index.out#L139-L153)
