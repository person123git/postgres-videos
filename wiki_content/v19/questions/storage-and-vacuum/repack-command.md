## Short Answer

`REPACK` is a new top-level SQL command in PostgreSQL 19 that rewrites a table into a fresh relfilenode to reclaim dead-tuple space, optionally clustering rows by an index. It **absorbs the functionality of `VACUUM FULL` and `CLUSTER`** into one command: physical-order rewrite (like `VACUUM FULL`) and index-order rewrite (like `CLUSTER`) are just two modes of `REPACK`, and the two legacy commands are kept but de-emphasized [repack.c#overview](../../../../raw/postgres-19/src/backend/commands/repack.c#L1-L22) [ac58465e commit message](#feature-scope-commits). The command is documented as "rewrite a table to reclaim disk space" [ref/repack.sgml#refpurpose](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L17-L20).

`REPACK` has two execution modes:

- **Blocking (default).** Takes `AccessExclusiveLock`, builds a new heap, copies live tuples in the chosen order, rebuilds indexes via `REINDEX`, then swaps relfilenodes. This is the classic `CLUSTER`/`VACUUM FULL` path, now reached through `repack.c` [repack.c#rebuild_relation](../../../../raw/postgres-19/src/backend/commands/repack.c#L1209-L1234).
- **`CONCURRENTLY`.** Takes only `ShareUpdateExclusiveLock` for almost all of the work, so readers and writers keep using the table. It captures concurrent DML with **logical decoding** through a dedicated background worker and a temporary replication slot, replays those changes onto the new heap, and only upgrades to `AccessExclusiveLock` for the brief final relfilenode swap [repack.c#overview](../../../../raw/postgres-19/src/backend/commands/repack.c#L7-L21) [ref/repack.sgml#CONCURRENTLY](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L226-L239).

On the follow-up question: **`REPACK` cannot be throttled.** It has no cost-based delay, no I/O-related option, and no dedicated GUC; the only levers are the ones that make it move less data, keep it out of shared buffers, or split it into smaller pieces you schedule yourself. See [I/O Impact and Throttling](#io-impact-and-throttling).

This page tracks **79 feature-scope commits (2026-03-10 to 2026-09-24)**: commits whose subject/body explicitly references REPACK, adjacent prerequisite/support commits used by that history, and tree-wide fixes that changed REPACK-specific code or text. Álvaro Herrera committed most of them, and the commit-message `Author:` trailers credit most of the code to Antonin Houska and to Herrera himself, building on Houska's `pg_squeeze` extension. The tables under [Feature-Scope Commits](#feature-scope-commits) name each commit's **committer**, adding "patch by …" where the commit message names a different author.

## Syntax and Modes

The grammar produces a single `RepackStmt` node for `REPACK` and `CLUSTER`, distinguished by a `RepackCommand` tag [parsenodes.h#RepackStmt](../../../../raw/postgres-19/src/include/nodes/parsenodes.h#L3986-L4001) [gram.y#RepackStmt](../../../../raw/postgres-19/src/backend/parser/gram.y#L12080-L12173). `VACUUM (FULL)` still parses as `VacuumStmt`; when the `FULL` option is present, `vacuum.c` routes execution into the same rewrite engine with `REPACK_COMMAND_VACUUMFULL` [gram.y#VacuumStmt](../../../../raw/postgres-19/src/backend/parser/gram.y#L12193-L12225) [vacuum.c#VACUUMFULL-repack](../../../../raw/postgres-19/src/backend/commands/vacuum.c#L2302-L2305):

```
REPACK [ ( option [, ...] ) ] [ table [ ( column [, ...] ) ] [ USING INDEX [ index_name ] ] ]
REPACK [ ( option [, ...] ) ] USING INDEX
```

where `option` is `VERBOSE`, `ANALYZE`, or `CONCURRENTLY` for `REPACK`; `CLUSTER` accepts only `VERBOSE` [ref/repack.sgml#synopsis](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L22-L36) [repack.c#ANALYZE-option](../../../../raw/postgres-19/src/backend/commands/repack.c#L269-L278).

The table name is a plain `qualified_name` plus an optional column list. Until `f23de46e15b` the production reused `vacuum_relation`, so the parser silently accepted `REPACK ONLY t` and `REPACK t *` even though neither is documented and neither changed what the command did; the production now spells out `qualified_name opt_name_list` and builds the `VacuumRelation` itself, so both spellings are syntax errors [gram.y#RepackStmt](../../../../raw/postgres-19/src/backend/parser/gram.y#L12080-L12173) [ref/repack.sgml#synopsis](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L22-L36). `VACUUM`'s own grammar still takes `vacuum_relation`, so `VACUUM (FULL) ONLY t` is unaffected [gram.y#vacuum_relation](../../../../raw/postgres-19/src/backend/parser/gram.y#L12273-L12278).

Key forms:

| Form | Effect |
|---|---|
| `REPACK t` | Rewrite `t` in physical order (like `VACUUM FULL`) [ref/repack.sgml#Description](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L42-L50). |
| `REPACK t USING INDEX idx` | Rewrite `t` ordered by `idx`, and mark `idx` as the clustered index (like `CLUSTER`) [ref/repack.sgml#clustering](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L79-L137). |
| `REPACK t USING INDEX` | Use the table's already-clustered index; error if none [repack.c#determine_clustered_index](../../../../raw/postgres-19/src/backend/commands/repack.c#L2620-L2661). |
| `REPACK` (no table) | Process every table/matview the caller has `MAINTAIN` on; not allowed in a transaction block or with `CONCURRENTLY` [ref/repack.sgml#no-table](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L52-L60). |
| `REPACK USING INDEX` (no table) | Process all tables that have a clustering index configured [ref/repack.sgml#no-table-using-index](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L139-L143). |
| `REPACK (CONCURRENTLY) t` | Online rewrite; requires an explicit single non-partitioned table [repack.c#multi-table-guard](../../../../raw/postgres-19/src/backend/commands/repack.c#L358-L374). |

`utility.c` dispatches `T_RepackStmt` to `ExecRepack()`, and reports the command tag as `REPACK` unless the statement is a legacy `CLUSTER` [utility.c#ExecRepack](../../../../raw/postgres-19/src/backend/tcop/utility.c#L863-L864) [utility.c#CMDTAG](../../../../raw/postgres-19/src/backend/tcop/utility.c#L2892-L2896). `VACUUM (FULL)` reaches the same engine by calling `cluster_rel(REPACK_COMMAND_VACUUMFULL, …)` from `vacuum.c` [vacuum.c#cluster_rel](../../../../raw/postgres-19/src/backend/commands/vacuum.c#L2303-L2305). To run `REPACK`, the caller needs the `MAINTAIN` privilege on the table [repack.c#repack_is_permitted_for_relation](../../../../raw/postgres-19/src/backend/commands/repack.c#L2463-L2514) [ref/repack.sgml#Notes](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L382-L385).

The generic privilege reference now lists `REPACK` among the commands authorized by `MAINTAIN`, and the predefined `pg_maintain` role grants that right on all relations [ddl.sgml#MAINTAIN](../../../../raw/postgres-19/doc/src/sgml/ddl.sgml#L2540-L2552) [user-manag.sgml#pg_maintain](../../../../raw/postgres-19/doc/src/sgml/user-manag.sgml#L655-L670). At runtime, membership in `pg_maintain` adds `ACL_MAINTAIN` when the relation ACL is checked [aclchk.c#pg_class_aclmask_ext](../../../../raw/postgres-19/src/backend/catalog/aclchk.c#L3385-L3394).

## Source Layout

```text
src/backend/commands/repack.c            ExecRepack, cluster_rel, the rewrite engine
                                         (formerly cluster.c; renamed in c0b53ec0)
src/backend/commands/repack_worker.c     background worker that does the logical decoding
src/backend/replication/pgrepack/        "pgrepack" logical-decoding output plugin
  pgrepack.c                             change_cb spills tuples to per-relation files
src/include/commands/repack.h            ExecRepack/cluster_rel API, CLUOPT_* flags
src/include/commands/repack_internal.h   ConcurrentChangeKind, RepackDecodingState,
                                         DecodingWorkerShared
doc/src/sgml/ref/repack.sgml             REPACK reference page
```

The output plugin is built as `pgrepack` and linked into the backend (`backend_targets += pgrepack`), not shipped as a `contrib` extension; the worker loads it by the fixed name `"pgrepack"` [pgrepack/meson.build](../../../../raw/postgres-19/src/backend/replication/pgrepack/meson.build#L13-L18) [repack_worker.c#PGREPACK_PLUGIN](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L33). The plugin refuses any use outside the REPACK worker, and since `5d47df21e89` the user-visible rejection happens **before the plugin library is loaded**. `StartupDecodingContext()` special-cases the plugin name `"pgrepack"` and, unless the caller passed `for_repack` and `AmRepackWorker()` is true, errors with `unsupported use of logical decoding plugin "pgrepack"` / `DETAIL: This plugin can only be used by REPACK (CONCURRENTLY).`; only then does it call `LoadOutputPlugin()` [logical.c#StartupDecodingContext-plugin-check](../../../../raw/postgres-19/src/backend/replication/logical/logical.c#L179-L259) [logical.c#pgrepack-special-case](../../../../raw/postgres-19/src/backend/replication/logical/logical.c#L188-L203). `repack_startup()` keeps only a defensive `elog(FATAL, "unexpected pgrepack startup outside of repack worker")` for the case that check misses (commit `cd7b204b` introduced the original rejection there) [pgrepack.c#repack_startup](../../../../raw/postgres-19/src/backend/replication/pgrepack/pgrepack.c#L50-L80).

Every other output plugin must be named in the new `output_plugin_libraries` GUC or the same function errors with `library "%s" may not be used as an output plugin` [logical.c#StartupDecodingContext-plugin-check](../../../../raw/postgres-19/src/backend/replication/logical/logical.c#L179-L259). That GUC is `PGC_SUSET` with boot value `"pgoutput, test_decoding"`, so a superuser `SET` applies to the session/transaction with no restart or reload, while a `postgresql.conf` change needs a configuration reload [guc_parameters.dat#output_plugin_libraries](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2311-L2318). Despite the file/dir name `pgrepack`, the user-facing command is `REPACK`; the third-party extension is unrelated.

## Blocking REPACK (the simple rewrite)

`ExecRepack()` parses the option list (`VERBOSE`/`ANALYZE`/`CONCURRENTLY`), sets the `CLUOPT_*` bitmask in `ClusterParams`, picks the lock level, and either processes one relation or builds a work list for the multi-table forms [repack.c#ExecRepack](../../../../raw/postgres-19/src/backend/commands/repack.c#L252-L460) [repack.h#CLUOPT](../../../../raw/postgres-19/src/include/commands/repack.h#L24-L36). Since `d7db169fa13`, `ANALYZE` is accepted only for `REPACK` itself: `ExecRepack()` raises `ANALYZE option not supported for %s` for `CLUSTER (ANALYZE)`, exactly as it already did for `CONCURRENTLY`. `VACUUM (FULL, ANALYZE)` is unaffected because it does not pass through `ExecRepack()` [repack.c#ANALYZE-option](../../../../raw/postgres-19/src/backend/commands/repack.c#L269-L278) [vacuum.c#VACUUMFULL-repack](../../../../raw/postgres-19/src/backend/commands/vacuum.c#L2302-L2305). Since `24dd8c369e5`, `REPACK (ANALYZE)` without `CONCURRENTLY` also calls `PreventInTransactionBlock()`, because the single-relation path commits and restarts the transaction; the reference page adds that the option cannot run inside a transaction block, function, procedure, or `DO` block [repack.c#ANALYZE-PreventInTransactionBlock](../../../../raw/postgres-19/src/backend/commands/repack.c#L305-L329) [ref/repack.sgml#ANALYZE](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L351-L359). Multiple tables are each processed in their own transaction (like `VACUUM`) to avoid holding many strong locks at once, which is why the multi-table and `CONCURRENTLY` forms cannot run inside a transaction block [repack.c#per-table-txn](../../../../raw/postgres-19/src/backend/commands/repack.c#L229-L251).

`cluster_rel()` is the per-relation driver. It starts progress reporting, switches to the table owner's userid under a security-restricted context, sets `search_path` to `pg_catalog, pg_temp`, rechecks the relation in the multi-table case, validates the clustering index, and then calls `rebuild_relation()` [repack.c#cluster_rel](../../../../raw/postgres-19/src/backend/commands/repack.c#L502-L697) [ref/repack.sgml#search_path](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L393-L397). The lock level is [`AccessExclusiveLock`](../../../glossary.md#accessexclusivelock) for blocking mode and [`ShareUpdateExclusiveLock`](../../../glossary.md#shareupdateexclusivelock) for concurrent mode [repack.c#RepackLockLevel](../../../../raw/postgres-19/src/backend/commands/repack.c#L469-L476).

Before progress reporting starts, `cluster_rel()` also refuses a table that carries an [invalid index](../../../glossary.md#invalid-index), but only for the `REPACK` command: `check_index_requirements()` scans `pg_index` for the table and raises `cannot execute REPACK on relation "…"` with `DETAIL: An invalid index cannot be processed correctly: …` and `HINT: Use DROP INDEX or REINDEX.` for any index with `indisvalid = false` [repack.c#check_index_requirements-call](../../../../raw/postgres-19/src/backend/commands/repack.c#L532-L538) [repack.c#check_index_requirements](../../../../raw/postgres-19/src/backend/commands/repack.c#L887-L948) [ref/repack.sgml#invalid-index](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L387-L391). `CLUSTER` and `VACUUM FULL` skip the check and still try to rebuild such indexes. The check arrived in two steps: `e14a2354d9f` rejected only `!indisready` indexes, and `0cabab44f12` widened it to every `!indisvalid` index, because an index whose validation phase failed is also not safe to rebuild.

`rebuild_relation()` (blocking path):

1. If an index was given, mark it `indisclustered` [repack.c#mark_index_clustered](../../../../raw/postgres-19/src/backend/commands/repack.c#L1154-L1156).
2. `make_new_heap()` creates a transient `pg_temp_<oid>` heap with the old heap's tuple descriptor, reloptions, access method, and (if needed) a TOAST table [repack.c#make_new_heap](../../../../raw/postgres-19/src/backend/commands/repack.c#L1248-L1322).
3. `copy_table_data()` copies live tuples into the new heap. It chooses **sequential-scan-and-sort** vs **index scan** vs **plain seqscan** via `plan_cluster_use_sort()` for a btree clustering index, computes freeze/multixact cutoffs, and hands the actual copy to the table AM's `table_relation_copy_for_cluster()` [repack.c#copy_table_data](../../../../raw/postgres-19/src/backend/commands/repack.c#L1510-L1545).
4. `finish_heap_swap()` swaps the relfilenodes of old and new heaps, rebuilds the indexes (`reindex = true`), applies the new `relfrozenxid`/`relminmxid`, and drops the transient heap [repack.c#finish_heap_swap-call](../../../../raw/postgres-19/src/backend/commands/repack.c#L1225-L1233).

Predicate (SSI) locks on tuples/pages are promoted to a relation lock before the rewrite, because tuples move [repack.c#TransferPredicateLocks](../../../../raw/postgres-19/src/backend/commands/repack.c#L655-L666).

### Multi-table discovery and recheck

The no-table forms and partition fan-out first collect lightweight `RelToCluster { tableOid, indexOid }` records. They do **not** retain a lock on each target while building that list, so each OID pair is only a candidate and may become stale before its turn [repack.c#RelToCluster](../../../../raw/postgres-19/src/backend/commands/repack.c#L86-L96) [repack.c#get_tables_to_repack](../../../../raw/postgres-19/src/backend/commands/repack.c#L2229-L2332) [repack.c#get_tables_to_repack_partitioned](../../../../raw/postgres-19/src/backend/commands/repack.c#L2334-L2460).

For each candidate, `ExecRepack()` starts a new transaction and obtains the final mode from `RepackLockLevel()` with `try_relation_open()`. It silently skips an OID that was dropped or now names something other than a plain table or materialized view. With that target locked, `cluster_rel_recheck()` checks the caller's `MAINTAIN` privilege, remote-temporary-table status, index existence, and — where required — whether the index is still marked `indisclustered` [repack.c#per-table-open](../../../../raw/postgres-19/src/backend/commands/repack.c#L419-L452) [repack.c#cluster_rel_recheck](../../../../raw/postgres-19/src/backend/commands/repack.c#L699-L753).

`repack_is_permitted_for_relation()` runs on both sides of that boundary, and since `9bb8e16bd53` it takes an `already_locked` flag that says which side is calling. The two unlocked discovery loops pass `false`, so `pg_class_aclcheck_ext()`'s `is_missing` result still means "dropped meanwhile" and the candidate is dropped from the list silently. `cluster_rel_recheck()`, which already holds the operation lock, passes `true`; the function then asserts `CheckRelationOidLockedByMe(relid, AccessShareLock, true)` on entry and asserts `!already_locked` if the relation turns up missing, so a vanished relation under a held lock is a bug rather than a skip. Either way, an existing relation the caller lacks `MAINTAIN` on still produces the `permission denied to execute %s on "%s", skipping it` WARNING [repack.c#repack_is_permitted_for_relation](../../../../raw/postgres-19/src/backend/commands/repack.c#L2463-L2514) [repack.c#cluster_rel_recheck-permission](../../../../raw/postgres-19/src/backend/commands/repack.c#L709-L716). The commit follows the same fix made for `vacuum_is_permitted_for_relation()` in `824d5f6241ea`, and also names REPACK in `RangeVarCallbackMaintainsTable`'s comment [tablecmds.c#RangeVarCallbackMaintainsTable](../../../../raw/postgres-19/src/backend/commands/tablecmds.c#L20115-L20126).

Commit `133eba078f7` made these rules consistent. The earlier whole-database list path briefly acquired transaction-scoped `AccessShareLock`s, but the database transaction committed immediately after list construction and therefore released them before processing. The commit removed those ineffective locks and hardened the locked per-table path against drops and OIDs that now identify a non-table relkind. It added no direct test or documentation change.

Commit `69fe2514fdd` then moved partitioned-table and partitioned-index resolution into `get_tables_to_repack_partitioned()`. The caller passes the already-open, `AccessExclusiveLock`-protected parent; the helper resolves `USING INDEX`, collects leaf candidates without locking them, closes and unlocks the parent, and returns the list [repack.c#get_tables_to_repack_partitioned](../../../../raw/postgres-19/src/backend/commands/repack.c#L2334-L2460). For a concurrently disappearing leaf index, it now calls `IndexGetRelation(..., true)` and silently skips an invalid result instead of raising a cache-lookup error [repack.c#partition-index-disappearance](../../../../raw/postgres-19/src/backend/commands/repack.c#L2412-L2427). This remains discovery-time hardening; each surviving table still undergoes the locked per-table recheck above.

## REPACK CONCURRENTLY (online rewrite via logical decoding)

The concurrent path keeps the table online by combining a low-strength lock with logical decoding. The cast of characters:

| Component | Role |
|---|---|
| **Leader backend** | Runs `REPACK`; holds `ShareUpdateExclusiveLock`, copies data, applies captured changes, does the final swap [repack.c#rebuild_relation](../../../../raw/postgres-19/src/backend/commands/repack.c#L1118-L1208). |
| **Decoding worker** | `bgworker` running `RepackWorkerMain`; owns a temporary logical slot and decodes WAL into spill files [repack_worker.c#RepackWorkerMain](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L58-L176). |
| **`pgrepack` output plugin** | Decoding callbacks; writes each insert/update/delete tuple of the target relation to the current spill file [pgrepack.c#change_cb](../../../../raw/postgres-19/src/backend/replication/pgrepack/pgrepack.c#L111-L180). |
| **Temporary replication slot** | `pg_repack_<pid>`, `RS_TEMPORARY` so it is dropped on error/exit; pins the WAL/snapshot start point [repack_worker.c#slot](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L245-L251). |
| **DSM + spill fileset** | `DecodingWorkerShared` in DSM coordinates the two processes; a `SharedFileSet` holds the exported snapshot and change files [repack_internal.h#DecodingWorkerShared](../../../../raw/postgres-19/src/include/commands/repack_internal.h#L61-L120). |

### Step by step

1. **Precondition checks.** `check_concurrent_repack_requirements()` enforces `wal_level >= replica` ([WAL level](../../../glossary.md#wal-level)); rejects a table whose table [access method](../../../glossary.md#access-method) routine is not heap's, system catalogs, tables marked `user_catalog_table`, TOAST tables, non-permanent (temp/unlogged) tables, materialized views, and `REPLICA IDENTITY NOTHING`/`FULL`; and obtains the **identity index** from `RelationGetReplicaIndex()`. Without a usable identity index, concurrent mode is refused [repack.c#check_concurrent_repack_requirements](../../../../raw/postgres-19/src/backend/commands/repack.c#L955-L1073). `RelationGetReplicaIndex()` returns the non-deferrable primary key under `REPLICA IDENTITY DEFAULT` and the `indisreplident` index under `REPLICA IDENTITY USING INDEX`; if that index was dropped, it returns nothing even when a usable primary key exists, and REPACK now refuses instead of falling back to the key, because logical decoding would not log usable tuple identity for it (`434bde9ce6b`) [repack.c#identity-index](../../../../raw/postgres-19/src/backend/commands/repack.c#L1046-L1070) [relcache.c#RelationGetReplicaIndex](../../../../raw/postgres-19/src/backend/utils/cache/relcache.c#L5068-L5094).
2. **Start the worker before any XID is assigned.** The leader becomes a lock-group leader, then `start_repack_decoding_worker()` sets up the [DSM](../../../glossary.md#dynamic-shared-memory), registers the [`bgworker`](../../../glossary.md#background-worker), and blocks until the worker reports `initialized` [repack.c#start_repack_decoding_worker](../../../../raw/postgres-19/src/backend/commands/repack.c#L1118-L1144) [repack.c#start_repack_decoding_worker-impl](../../../../raw/postgres-19/src/backend/commands/repack.c#L3742-L3839). Since `47b5b23a780` that wait has two stages. `wait_for_repack_decoding_worker()` first waits until the worker has started and attached to the error queue, and raises `REPACK decoding worker failed to start` if it stopped without attaching; only then does the leader sleep on the condition variable, so a worker that never starts no longer hangs the leader [repack.c#wait-call](../../../../raw/postgres-19/src/backend/commands/repack.c#L3805-L3816) [repack.c#wait_for_repack_decoding_worker](../../../../raw/postgres-19/src/backend/commands/repack.c#L3841-L3907). The worker connects as the table owner with both `BGWORKER_BYPASS_ALLOWCONN` and `BGWORKER_BYPASS_ROLELOGINCHECK`, so the owner needs neither `LOGIN` nor `CONNECT` (`CONNECT` since `9bf3a414560`), and it adopts the leader's `lock_timeout` and `transaction_timeout` values through `DecodingWorkerShared` (`746a507a391`), so a session-level `SET` reaches it and a role- or database-level setting for the owner does not override it [repack_worker.c#connect-and-timeouts](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L104-L118) [repack.c#timeouts](../../../../raw/postgres-19/src/backend/commands/repack.c#L3775-L3777) [repack_internal.h#DecodingWorkerShared](../../../../raw/postgres-19/src/include/commands/repack_internal.h#L61-L120). The worker creates the temporary slot, enables logical decoding, restricts decoding to the target relation (and its TOAST relation), builds an initial historic snapshot, and exports it to a file [repack_worker.c#setup](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L222-L319).
3. **Initial copy under the exported snapshot.** The leader reads the exported snapshot with `get_initial_snapshot()`, pushes it active, and runs `copy_table_data()` against that MVCC snapshot, so the initial copy is a consistent point-in-time image [repack.c#get_initial_snapshot](../../../../raw/postgres-19/src/backend/commands/repack.c#L1146-L1190) [repack.c#get_initial_snapshot-impl](../../../../raw/postgres-19/src/backend/commands/repack.c#L3989-L4037). The worker builds that snapshot with `SnapBuildInitialSnapshot()` [repack_worker.c#SnapBuildInitialSnapshot](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L154-L156). Since `4a4bf490dc5`, outside recovery, that function waits with `XactLockTableWait()` for every running top-level transaction that the snapshot already counts as committed. A transaction enters the snapshot when its commit record is decoded, but an MVCC reader may treat it as committed only after it leaves the procarray. Without the wait, the copy could set [hint bits](../../../glossary.md#hint-bits) as if such a transaction had aborted [snapbuild.c#SnapBuildInitialSnapshot-wait](../../../../raw/postgres-19/src/backend/replication/logical/snapbuild.c#L479-L510). Meanwhile the worker keeps decoding WAL in a loop, and later advances the slot's restart/confirmed LSN at WAL-segment boundaries so processed WAL can be recycled [repack_worker.c#decode_loop](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L164-L176) [repack_worker.c#WAL-recycling](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L402-L431).
4. **Build new indexes** on the new heap (instead of reindexing the old one), since this is slow and is done before the exclusive lock [repack.c#build_new_indexes](../../../../raw/postgres-19/src/backend/commands/repack.c#L3536-L3569).
5. **Catch-up #1 (still under `ShareUpdateExclusiveLock`).** `process_concurrent_changes()` tells the worker an `lsn_upto`, waits for the next spill file, and `apply_concurrent_changes()` replays it onto the new heap. Doing this first minimizes how long the exclusive lock is later held [repack.c#catch-up-1](../../../../raw/postgres-19/src/backend/commands/repack.c#L3389-L3402).
6. **Lock upgrade + catch-up #2.** The leader takes `AccessExclusiveLock` on the table, all its indexes, and its TOAST relation, transfers predicate locks, flushes WAL, and applies the remaining changes with `done = true` so the worker exits [repack.c#lock-upgrade](../../../../raw/postgres-19/src/backend/commands/repack.c#L3405-L3459).
7. **Swap.** `swap_relation_files()` swaps each index's storage, then `finish_heap_swap()` swaps the heap (and TOAST), dropping the transient relation. The old OID, grants, and dependencies are preserved [repack.c#swap](../../../../raw/postgres-19/src/backend/commands/repack.c#L3472-L3523).

### How concurrent changes are captured and replayed

The `pgrepack` plugin's `change_cb` only ever sees the target relation (other relations are filtered out during decoding by `change_useless_for_repack()`), and writes a compact record per change: a one-byte kind (`i`/`u`/`U`/`d`), the heap tuple bytes, and any out-of-line external attributes spilled separately to stay under `MaxAllocSize` [pgrepack.c#repack_store_change](../../../../raw/postgres-19/src/backend/replication/pgrepack/pgrepack.c#L191-L306) [repack_worker.c#change_useless_for_repack](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L527-L564) [repack_internal.h#ConcurrentChangeKind](../../../../raw/postgres-19/src/include/commands/repack_internal.h#L24-L32).

`apply_concurrent_changes()` reads the spill file and replays each change onto the new heap, bumping the command counter between dependent changes [repack.c#apply_concurrent_changes](../../../../raw/postgres-19/src/backend/commands/repack.c#L2681-L2801):

- **INSERT** → `table_tuple_insert(..., TABLE_INSERT_NO_LOGICAL)` plus index maintenance. The `NO_LOGICAL` flag stops these replayed rows from being decoded again [repack.c#apply_concurrent_insert](../../../../raw/postgres-19/src/backend/commands/repack.c#L2807-L2822).
- **UPDATE/DELETE** → locate the existing tuple in the new heap via the identity index (`find_target_tuple()`), then `table_tuple_update`/`table_tuple_delete` with `NO_LOGICAL`. For updates, unchanged TOAST pointers are re-pointed at the new relation's TOAST table via `adjust_toast_pointers()` [repack.c#apply_concurrent_update](../../../../raw/postgres-19/src/backend/commands/repack.c#L2828-L2892) [repack.c#toast-pointers](../../../../raw/postgres-19/src/backend/commands/repack.c#L2774-L2784).

Two fixes made that suppression complete for output plugins that ask for heap-rewrite changes, such as `test_decoding` with `include-rewrites`. `741f9d741e6` makes `heap_update()` pass `HEAP_INSERT_NO_LOGICAL` to the [TOAST](../../../glossary.md#toast) toaster when `TABLE_UPDATE_NO_LOGICAL` is set; before it, replayed updates logged their TOAST chunks for decoding, and decoding could crash reassembling them [heapam.c#heap_update-toast-no-logical](../../../../raw/postgres-19/src/backend/access/heap/heapam.c#L3964-L3971). `7ed016a1de3` makes `DecodeUpdate()` skip update records without `XLH_UPDATE_CONTAINS_NEW_TUPLE`, as it already did for such inserts, so a suppressed update no longer surfaces as an empty `UPDATE` on the target table [decode.c#DecodeUpdate-no-new-tuple](../../../../raw/postgres-19/src/backend/replication/logical/decode.c#L967-L975).

The identity-index scan key is precomputed in `initialize_change_context()`, which resolves the equality strategy from the index's operator family (so it works for non-btree identity indexes too — see commit `36f52a59`) [repack.c#initialize_change_context](../../../../raw/postgres-19/src/backend/commands/repack.c#L3158-L3297). When replay reconstructs a spilled tuple, `restore_tuple()` checks that every separately stored varlena attribute is consumed and errors if the spill file contains too few or too many separately stored attributes; commit `e2a8cabc` added the leftover-attribute check [repack.c#restore_tuple](../../../../raw/postgres-19/src/backend/commands/repack.c#L2904-L2971).

### Error handling and worker teardown

The leader runs `rebuild_relation()` inside `PG_ENSURE_ERROR_CLEANUP(stop_repack_decoding_worker_cb)` so the worker and its slot are cleaned up even on `FATAL` exit (e.g. `pg_terminate_backend()`), and `stop_repack_decoding_worker()` terminates the worker, detaches the error queue if it is still attached, cancels CV sleeps, waits for the worker to exit, and only then detaches the DSM, because a worker still starting up may be attaching to the shared file set [repack.c#ensure-cleanup](../../../../raw/postgres-19/src/backend/commands/repack.c#L677-L685) [repack.c#stop_repack_decoding_worker](../../../../raw/postgres-19/src/backend/commands/repack.c#L3916-L3976). Worker errors are forwarded to the leader through a shared-memory message queue and re-thrown with a "REPACK decoding worker" context line, using the `PROCSIG_REPACK_MESSAGE` interrupt and `ProcessRepackMessages()` [repack.c#ProcessRepackMessages](../../../../raw/postgres-19/src/backend/commands/repack.c#L4071-L4217). Since `47b5b23a780`, a worker that finishes sends a `PqRepackMsg_Terminate` (`'X'`) message, on which the leader detaches the queue and stops reading; a queue that reports detached without that message now raises `lost connection to REPACK decoding worker`. On exit, `RepackWorkerShutdown()` detaches the DSM *before* signalling the leader, so the leader cannot read a queue that still looks attached and then sleep forever [repack_worker.c#Terminate](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L172-L175) [repack.c#ProcessRepackMessage-Terminate](../../../../raw/postgres-19/src/backend/commands/repack.c#L4203-L4211) [repack_worker.c#RepackWorkerShutdown](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L184-L207) [protocol.h#PqRepackMsg_Terminate](../../../../raw/postgres-19/src/include/libpq/protocol.h#L72-L74).

### WAL retention and `effective_wal_level`

Normally a replication slot pins `restart_lsn` so WAL can't be recycled. `REPACK` does not need crash-safe replay (a crash just restarts the whole operation), so the worker advances the slot's restart/confirmed LSN as it crosses each WAL-segment boundary, letting old WAL be recycled while `REPACK` runs (commit `45b02984`) [repack_worker.c#WAL-recycling](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L402-L431). Because the temporary slot is logical, the worker calls `EnsureLogicalDecodingEnabled()` at setup and `ReplicationSlotDropAcquired(true)` at teardown so `effective_wal_level` does not stay stuck at `logical` afterward (commit `2af1dc89`) [repack_worker.c#enable-decoding](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L239-L252) [repack_worker.c#cleanup](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L321-L332).

Commit `10389a7e15e` does not change that recycling behavior. It fixes the worker's `DEBUG1` message to print the confirmed LSN with the standard `%X/%08X` shape through `LSN_FORMAT_ARGS()`, including zero-padding the low half [repack_worker.c#confirmed-LSN-debug](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L422-L430).

At `wal_level = replica`, the worker can also be one of two backends concurrently trying to enable logical decoding: every concurrent REPACK creates its temporary slot and calls `EnsureLogicalDecodingEnabled()` [repack_worker.c#enable-decoding](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L238-L252). Commit `99e47536bbf` closes the activation race by checking `logical_decoding_enabled` again after the process-signal barrier and after reacquiring `LogicalDecodingControlLock`; a backend that lost the race returns without writing a redundant status-change WAL record [logicalctl.c#EnableLogicalDecoding](../../../../raw/postgres-19/src/backend/replication/logical/logicalctl.c#L342-L426). Without that recheck, another logical-slot creator could enable decoding while the REPACK worker waited, and the redundant record could later reach `xlog_decode()`, which treats a decoded status change as an error [decode.c#xlog_decode](../../../../raw/postgres-19/src/backend/replication/logical/decode.c#L153-L172). The injection-point test pauses one activation, lets another create a slot, resumes the first, and verifies that decoding from the second slot succeeds [051_effective_wal_level.pl#concurrent-activation](../../../../raw/postgres-19/src/test/recovery/t/051_effective_wal_level.pl#L385-L426).

Commit `6a80179f6b0` then closed the opposite race, a *deactivation* that interleaves with slot creation. `EnsureLogicalDecodingEnabled()`'s recovery branch no longer asserts that decoding is still enabled; it re-checks after the slot exists — so a concurrent deactivation can see the slot's `in_use` flag — and raises `logical decoding on standby requires "effective_wal_level" >= "logical" on the primary` with detail `Logical decoding was concurrently disabled during the logical replication slot creation.` [logicalctl.c#EnsureLogicalDecodingEnabled](../../../../raw/postgres-19/src/backend/replication/logical/logicalctl.c#L287-L336). Slot synchronization takes a separate path: `update_and_persist_local_synced_slot()` keeps the temporary slot, logs `could not synchronize replication slot "%s"`, and lets the next cycle retry [slotsync.c#update_and_persist_local_synced_slot](../../../../raw/postgres-19/src/backend/replication/logical/slotsync.c#L712-L745). Scope matters here: that branch runs only while `RecoveryInProgress()`, i.e. for slot creation on a standby, and a REPACK worker rewrites a table and so runs only on a writable server — the error is therefore not on the worker's path, even though the worker calls the same `EnsureLogicalDecodingEnabled()` [repack_worker.c#enable-decoding](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L239-L252). The commit also adds a recovery-race block to the same TAP test, driven by the new `replication-slot-create-begin` injection point [051_effective_wal_level.pl#deactivation-races](../../../../raw/postgres-19/src/test/recovery/t/051_effective_wal_level.pl#L515-L671) [slot.c:423](../../../../raw/postgres-19/src/backend/replication/slot.c#L423).

## Restrictions on CONCURRENTLY

`REPACK (CONCURRENTLY)` is rejected for any of: a relation that is not a table, such as a materialized view; an `UNLOGGED` or temporary table; a partitioned table; a table without a primary key or index-based replica identity (including deferrable PKs, and a table whose `REPLICA IDENTITY USING INDEX` index was dropped); a system catalog or TOAST table; a table whose access method is not `heap`; a table declared with `user_catalog_table`; execution inside a transaction block; or when `max_repack_replication_slots` leaves no slot free [ref/repack.sgml#cannot-use](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L264-L327) [repack.c#check_concurrent_repack_requirements](../../../../raw/postgres-19/src/backend/commands/repack.c#L955-L1073). The reference page does not list the dropped-identity-index case.

Five of these checks are new since the 2026-09-01 pin, all backpatched to 19:

| Commit | Rejects | Why | Source |
|---|---|---|---|
| `fe7b6072342` | Any table whose `rd_tableam` is not `GetHeapamTableAmRoutine()` | A table AM without logical decoding support would lose the concurrent changes silently. Comparing the routine, not the AM OID, keeps AMs that reuse heap's handler working | [repack.c#heap-am-check](../../../../raw/postgres-19/src/backend/commands/repack.c#L969-L981) |

| `0cabab44f12` (after `e14a2354d9f`) | Any table with an `!indisvalid` index, in both modes of `REPACK` | Rebuilding an index that never finished building can fail | [repack.c#check_index_requirements](../../../../raw/postgres-19/src/backend/commands/repack.c#L887-L948) |

## GUC: `max_repack_replication_slots`

Concurrent `REPACK` consumes a logical replication slot for its lifetime. Rather than forcing users to inflate `max_replication_slots`, v19 adds a dedicated pool sized by `max_repack_replication_slots` (default `5`, min `0`) [guc_parameters.dat#max_repack_replication_slots](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2108-L2114) [slot.c#decl](../../../../raw/postgres-19/src/backend/replication/slot.c#L163-L164). `ReplicationSlotCreate(..., repack = true, ...)` allocates from the extra `[max_replication_slots, max_replication_slots + max_repack_replication_slots)` band of the slot array, so REPACK slots never compete with ordinary replication slots [slot.c#ReplicationSlotCreate](../../../../raw/postgres-19/src/backend/replication/slot.c#L372-L465).

**Scope:** `max_repack_replication_slots` is `PGC_POSTMASTER` — it **requires a server restart** [guc_parameters.dat#context](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2108-L2108). The decoding worker also needs a free `max_worker_processes` slot, or `REPACK (CONCURRENTLY)` errors out [repack.c#worker-slots](../../../../raw/postgres-19/src/backend/commands/repack.c#L3800-L3804).

## I/O Impact and Throttling

**PostgreSQL 19 gives `REPACK` no throttle.** No command option, no reloption, and no GUC makes it pause or rate-limit itself. `ExecRepack()` accepts exactly three options — `VERBOSE`, `ANALYZE`, `CONCURRENTLY` — and none of them concerns I/O [repack.c#ExecRepack-options](../../../../raw/postgres-19/src/backend/commands/repack.c#L264-L299).

Unlike lazy (non-`FULL`) `VACUUM`, the rewrite path has **no cost-based delay**. `vacuum_delay_point()` [vacuum.h#vacuum_delay_point](../../../../raw/postgres-19/src/include/commands/vacuum.h#L390) is called from `vacuumlazy.c` [vacuumlazy.c:1333](../../../../raw/postgres-19/src/backend/access/heap/vacuumlazy.c#L1333), `analyze.c` [analyze.c:940](../../../../raw/postgres-19/src/backend/commands/analyze.c#L940) and the index AMs' vacuum routines [nbtree.c:1725](../../../../raw/postgres-19/src/backend/access/nbtree/nbtree.c#L1725), and from nowhere in `repack.c` [repack.c#cluster_rel](../../../../raw/postgres-19/src/backend/commands/repack.c#L502-L697), the table-AM copy routine [heapam_handler.c#heapam_relation_copy_for_cluster](../../../../raw/postgres-19/src/backend/access/heap/heapam_handler.c#L593-L954), or `rewriteheap.c` [rewriteheap.c#raw_heap_insert](../../../../raw/postgres-19/src/backend/access/heap/rewriteheap.c#L596-L680). The only interruption point in the copy loop is `CHECK_FOR_INTERRUPTS()` [heapam_handler.c:713](../../../../raw/postgres-19/src/backend/access/heap/heapam_handler.c#L713). So `vacuum_cost_delay`, `vacuum_cost_limit` and the autovacuum cost knobs do nothing for `REPACK`, `CLUSTER` or `VACUUM FULL`.

Nothing schedules a rewrite for you either: the only callers of `cluster_rel()` are `ExecRepack()` [repack.c#cluster_rel-call](../../../../raw/postgres-19/src/backend/commands/repack.c#L2574-L2582) and `VACUUM (FULL)` [vacuum.c#VACUUMFULL-repack](../../../../raw/postgres-19/src/backend/commands/vacuum.c#L2302-L2305), and autovacuum never sets `VACOPT_FULL` [autovacuum.c#at_params.options](../../../../raw/postgres-19/src/backend/postmaster/autovacuum.c#L2913-L2923). What you *can* control is how much data the command moves, how much of it passes through shared buffers, how much WAL it writes, and when and in how many pieces it runs.

### Settings that change the load

The sequential scan of the old heap is the one part with built-in restraint. `initscan()` gives it a `BAS_BULKREAD` ring **and** enables synchronized scanning, but only when the relation is larger than `NBuffers / 4` [heapam.c#initscan](../../../../raw/postgres-19/src/backend/access/heap/heapam.c#L360-L411); `table_beginscan()` supplies the `SO_ALLOW_STRAT`/`SO_ALLOW_SYNC` flags that permit both [tableam.h#table_beginscan](../../../../raw/postgres-19/src/include/access/tableam.h#L942-L951). In v19 that ring is not a fixed 256 kB: it grows by `io_combine_limit * effective_io_concurrency` blocks, capped by the backend pin limit and by `NBuffers / 8` [freelist.c#GetAccessStrategy](../../../../raw/postgres-19/src/backend/storage/buffer/freelist.c#L425-L500) [freelist.c#GetAccessStrategyWithSize](../../../../raw/postgres-19/src/backend/storage/buffer/freelist.c#L511-L541). ### Recipes for a gentler REPACK

- **Do one table, or one partition, at a time.** The bare `REPACK;` form sweeps every table the caller has `MAINTAIN` on, one transaction each [repack.c#per-table-txn](../../../../raw/postgres-19/src/backend/commands/repack.c#L229-L251); naming a single relation lets you space the bursts out yourself, which is the only real pacing mechanism available.
- **Prefer physical order.** `REPACK t` with no `USING INDEX` resolves to no index at all [repack.c#determine_clustered_index](../../../../raw/postgres-19/src/backend/commands/repack.c#L2620-L2660), so it always takes the plain sequential path [repack.c#use_sort-choice](../../../../raw/postgres-19/src/backend/commands/repack.c#L1501-L1514) — the only path with a ring buffer and read-ahead.
- **If you must cluster on an index, force scan-and-sort** with a session-level `enable_indexscan = off`, and pay for it in temp space. The reverse trade — index scan to save temp space — costs you the ring buffer and adds pruning writes to the old heap.
- **Cap the index rebuild's concurrency** with `max_parallel_maintenance_workers = 0` if the parallel builds are what saturate the device.
- **Move temp files off the data device** with `temp_tablespaces`, which covers both the sort file and the `CONCURRENTLY` change spool.
- **Do not reach for `CONCURRENTLY` to reduce I/O.** It protects availability, and it lets old WAL recycle while it runs [repack_worker.c#WAL-recycling](../../../../raw/postgres-19/src/backend/commands/repack_worker.c#L402-L431), but it adds decoding, spilling and replay on top of the same rewrite, and it gives up both the buffer-bypassing write path and the TOAST swap-by-content shortcut.

### How to watch it

`pg_stat_progress_repack` reports the phase and the block and tuple counters (see [Progress reporting](#progress-reporting)), and `REPACK (VERBOSE)` prints the chosen method plus removable/nonremovable row counts and a `pg_rusage` line [repack.c#verbose-report](../../../../raw/postgres-19/src/backend/commands/repack.c#L1560-L1572).

`pg_stat_io` has a blind spot here. `IOOP_WRITE` and `IOOP_EXTEND` are only ever counted inside the buffer manager [bufmgr.c#IOOP_EXTEND](../../../../raw/postgres-19/src/backend/storage/buffer/bufmgr.c#L3040-L3046) [bufmgr.c#IOOP_WRITE](../../../../raw/postgres-19/src/backend/storage/buffer/bufmgr.c#L4607-L4626) [localbuf.c#IOOP_WRITE](../../../../raw/postgres-19/src/backend/storage/buffer/localbuf.c#L212-L217), so the blocking rewrite's heap and index writes — which go straight to `smgrextend()` — never appear there. Reads of the old heap do, under context `bulkread` or `normal`, and the `CONCURRENTLY` copy's writes appear under `bulkwrite`.

## Progress reporting

Each backend running `REPACK` reports through `pg_stat_progress_repack`, exposing the command, phase, clustering-index OID, heap tuples scanned/inserted/updated/deleted, block counts, and index-rebuild count [system_views.sql#pg_stat_progress_repack](../../../../raw/postgres-19/src/backend/catalog/system_views.sql#L1349-L1378) [progress.h#PROGRESS_REPACK](../../../../raw/postgres-19/src/include/commands/progress.h#L77-L106). ## Open Questions

- **Exact WAL/lock deadlock window.** The code comments warn that a concurrent `CREATE INDEX` (which conflicts with `ShareUpdateExclusiveLock`) can deadlock the worker against the leader's transaction; the precise reproduction and whether `deadlock.c` always detects it via the lock group is asserted in comments but not proven by a test here [repack.c#deadlock-note](../../../../raw/postgres-19/src/backend/commands/repack.c#L1132-L1144).
- **`REPLICA IDENTITY FULL` support.** The code explicitly rejects `FULL` as "not implemented yet"; whether a later commit on `REL_19_STABLE` past this pin adds it is out of scope for this checkout [repack.c#replident](../../../../raw/postgres-19/src/backend/commands/repack.c#L1031-L1044).
- **The reference page's `enable_sort` advice appears stale, and source wins.** `ref/repack.sgml` says that if the scan-and-sort method's peak temporary space "is intolerable, you can disable this choice by temporarily setting `enable_sort` to `off`" [ref/repack.sgml#Notes-on-Resources](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L147-L172). In this checkout that setting cannot change the decision. `plan_cluster_use_sort()` compares only `total_cost` between the seqscan-and-sort path and the index path [planner.c#cost-comparison](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L7209-L7223), while `cost_sort()` records a disabled `enable_sort` in `disabled_nodes` and adds nothing to the cost [costsize.c#cost_sort](../../../../raw/postgres-19/src/backend/optimizer/path/costsize.c#L2200-L2226) — the representation Robert Haas introduced in `e22253467942fdb100087787c3e1e3a8620c54b2`, "Treat number of disabled nodes in a path as a separate cost metric" (2024-08-21), which is an ancestor of this pin. The wording predates `REPACK`: the identical paragraph is in `doc/src/sgml/ref/cluster.sgml` at `ac58465e061^`, and `ac58465e061` carried it into the new reference page. The only scan-method override that still bites is `enable_indexscan = off`, which `plan_cluster_use_sort()` short-circuits on explicitly [planner.c#enable_indexscan-shortcircuit](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L7136-L7138). Not verified against a running v19 server, and no search was made for an upstream report of the stale wording.
- **The reference page omits the dropped-identity-index rejection.** Since `434bde9ce6b`, `check_concurrent_repack_requirements()` refuses a table whose `REPLICA IDENTITY USING INDEX` index was dropped, even when a usable primary key exists [repack.c#identity-index](../../../../raw/postgres-19/src/backend/commands/repack.c#L1046-L1070). The `CONCURRENTLY` restriction list in `ref/repack.sgml` still says only "lacks a primary key and index-based replica identity" [ref/repack.sgml#cannot-use](../../../../raw/postgres-19/doc/src/sgml/ref/repack.sgml#L264-L327). Source wins. `RelationGetReplicaIndex()` carries a `FIXME someday` about the same surprise [relcache.c#RelationGetReplicaIndex](../../../../raw/postgres-19/src/backend/utils/cache/relcache.c#L5068-L5094), so this may change again before GA.
- **No measurements.** The [I/O Impact and Throttling](#io-impact-and-throttling) section is source-and-history only at the asker's chosen scope. The relative cost of the paths it names — hint-bit dirtying of the old heap, TOAST rewrite volume, the buffer-bypassing write path, `CONCURRENTLY`'s decode/spill/replay overhead — is not quantified here.
