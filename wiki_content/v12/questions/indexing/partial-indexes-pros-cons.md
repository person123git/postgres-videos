## Question

What are the pros and cons of partial indexes in PostgreSQL 12? Include a section on statistics generated and used by the query planner.

Prompt note: the original request had grammar and capitalization issues. The user approved correcting the prompt before filing this page.

Follow-up note: the user also approved correcting follow-up requests to “Consider partial indexes on expressions too.” and “Consider ordinary indexes on expressions too.” before this page was updated.

## Answer

A PostgreSQL 12 partial index is an index whose `WHERE` predicate selects only part of the table. The index stores entries only for rows that satisfy that predicate, so it can be smaller and cheaper to maintain than a full index when the predicate matches the workload.[indices.sgml#Partial-Indexes](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L765-L784) [create_index.sgml#partial-index-description](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L65-L84)

The main tradeoff is that PostgreSQL can use the index only when the planner proves that the query condition implies the index predicate. PostgreSQL 12 intentionally uses limited implication checks, not a general theorem prover, and matching happens at planning time rather than execution time.[indices.sgml#partial-index-matching](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L899-L925) [predtest.c#predicate_implied_by](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L113-L148) [indxpath.c#check_index_predicates](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3430-L3532)

### Short answer

| Area | Benefit | Cost or caveat |
| --- | --- | --- |
| Size and write cost | Excluding common or uninteresting values reduces index size and can avoid index updates for rows outside the predicate.[indices.sgml#exclude-common-values](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L774-L784) | The predicate still has to be evaluated during index build and DML index maintenance.[heapam_handler.c#partial-index-build-filter](../../../../raw/postgres-12/src/backend/access/heap/heapam_handler.c#L1198-L1211) [execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L303-L384) |
| Read performance | Queries whose `WHERE` clause implies the predicate can use the smaller index, including cases where the predicate column is not the indexed key column, and including expression index keys such as `lower(col)` or `(first_name || ' ' || last_name)`.[indices.sgml#exclude-uninteresting-values](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L845-L897) [indices.sgml#indexes-expressional](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L687-L753) | Queries that do not prove the predicate cannot use the index; parameterized clauses such as `x < ?` do not imply a fixed predicate for all parameter values, and expression index matching still requires the query operand to match the stored expression key.[indices.sgml#partial-index-matching](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L899-L925) [indxpath.c#match_index_to_operand](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3811-L3887) |
| Conditional uniqueness | A unique partial index enforces uniqueness only inside the predicate-selected subset.[indices.sgml#partial-unique-index](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L927-L968) | A partial index cannot be adopted as a primary-key or unique table constraint via the constraint-using-index path.[parse_utilcmd.c#partial-index-constraint-reject](../../../../raw/postgres-12/src/backend/parser/parse_utilcmd.c#L2076-L2093) |
| Planner control | A partial index can make an index unavailable for values or cases where the planner should not choose it.[indices.sgml#override-plan-choices](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L970-L981) | The documentation warns that you need to know at least as much as the planner, and that the advantage over a regular index is minimal in most cases.[indices.sgml#partial-index-warning](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L983-L989) |
| Statistics | `ANALYZE` estimates the partial index row count from sampled rows that satisfy the predicate, updates `pg_class.reltuples`, and can store `pg_statistic` rows for partial expression-index columns.[analyze.c#compute_index_stats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L694-L843) [analyze.c#index-relstats-update](../../../../raw/postgres-12/src/backend/commands/analyze.c#L613-L630) [catalogs.sgml#pg-statistic-index-expressions](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L6346-L6404) | Ordinary non-partial expression-index statistics can be used as whole-relation expression statistics; partial expression-index statistics are not used that way by the default planner path.[selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4527-L4602) |

### How PostgreSQL stores and maintains a partial index

The SQL surface is ordinary `CREATE INDEX` plus an optional `WHERE predicate` clause. The same syntax allows `UNIQUE`, `CONCURRENTLY`, an access method, expressions, included columns, storage parameters, tablespace, and then the partial-index predicate.[create_index.sgml#synopsis](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L24-L30)

`transformIndexStmt()` transforms the `WHERE` clause as `EXPR_KIND_INDEX_PREDICATE`; the `CREATE INDEX` documentation says the predicate can refer only to columns of the underlying table, forbids subqueries and aggregate expressions, and requires all functions and operators in the index definition to be immutable.[parse_utilcmd.c#transformIndexStmt](../../../../raw/postgres-12/src/backend/parser/parse_utilcmd.c#L2584-L2641) [create_index.sgml#partial-index-description](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L65-L94) `CheckPredicate()` repeats the source-side immutability check and notes that subqueries, aggregates, and window functions should already have been rejected by parse transformation.[indexcmds.c#CheckPredicate](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1503-L1530)

The catalog representation is `pg_index.indpred`, a `pg_node_tree` expression tree for a partial-index predicate, or null for a non-partial index.[catalogs.sgml#pg-index-indpred](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L3938-L3951) In memory, `IndexInfo` stores the executable predicate in `ii_Predicate`, and `IndexOptInfo` stores the planner predicate in `indpred` plus a `predOK` flag that records whether the predicate matched the current query.[execnodes.h#IndexInfo](../../../../raw/postgres-12/src/include/nodes/execnodes.h#L153-L177) [pathnodes.h#IndexOptInfo](../../../../raw/postgres-12/src/include/nodes/pathnodes.h#L746-L821)

During a normal index build, heap access-method code prepares the partial-index predicate with `ExecPrepareQual()` and discards heap tuples for which `ExecQual()` returns false before it forms the index datum.[heapam_handler.c#partial-index-build-filter](../../../../raw/postgres-12/src/backend/access/heap/heapam_handler.c#L1198-L1211) [heapam_handler.c#heapam_index_build_range_scan](../../../../raw/postgres-12/src/backend/access/heap/heapam_handler.c#L1604-L1626) During DML, `ExecInsertIndexTuples()` evaluates `ii_Predicate` for each ready index and skips the index update when the predicate is not satisfied.[execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L303-L384)

### Planner matching and plan shape

The planner retrieves `pg_index.indpred` through `RelationGetIndexPredicate()`, converts the stored expression to a node tree, simplifies and canonicalizes it, converts it to implicit-AND form, and caches the result in relcache.[relcache.c#RelationGetIndexPredicate](../../../../raw/postgres-12/src/backend/utils/cache/relcache.c#L4713-L4778) `get_relation_info()` loads index expressions and predicates into `IndexOptInfo`, fixes their varnos for the relation being planned, and initializes `predOK = false`.[plancat.c#get_relation_info-index-predicate](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L365-L406)

`check_index_predicates()` builds a clause list from base restriction clauses, movable join clauses, and equivalence-derived clauses, then sets `predOK` when `predicate_implied_by(index->indpred, clauselist, false)` succeeds.[indxpath.c#check_index_predicates](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3430-L3532) Plain index-path creation ignores a partial index when `index->indpred != NIL && !index->predOK`, though later bitmap-OR generation can still reason about non-`predOK` partial indexes in OR contexts.[indxpath.c#create_index_paths](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L250-L279) [indxpath.c#generate_bitmap_or_paths-partial](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L1188-L1222)

For a non-target relation, `check_index_predicates()` removes base restriction clauses that are implied by the index predicate from `indrestrictinfo`, so an index-scan plan does not have to retest them. It keeps those clauses for UPDATE, DELETE, and `SELECT FOR UPDATE` target relations so EvalPlanQual can recheck them.[indxpath.c#check_index_predicates](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3484-L3532) Bitmap heap scans handle predicates differently: `create_bitmap_subplan()` can add index predicate conditions to bitmap quals, because predicate conditions must be rechecked if the bitmap becomes lossy.[createplan.c#create_bitmap_scan_plan](../../../../raw/postgres-12/src/backend/optimizer/plan/createplan.c#L2968-L2987) [createplan.c#create_bitmap_subplan](../../../../raw/postgres-12/src/backend/optimizer/plan/createplan.c#L3228-L3253)

### Ordinary expression indexes as the baseline

An ordinary expression index is a non-partial index whose key is a function or scalar expression computed from table columns. PostgreSQL 12 documents these as useful for fast access by computed values, with examples such as `lower(col1)` for case-insensitive lookup and `(first_name || ' ' || last_name)` for full-name lookup.[indices.sgml#indexes-expressional](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L687-L753) The `CREATE INDEX` syntax accepts either a column name or a parenthesized expression in the key list, and the docs say functions and operators in an index definition must be immutable.[create_index.sgml#synopsis](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L24-L30) [create_index.sgml#partial-index-description](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L43-L94)

Catalog storage is the same expression-key storage used by partial expression indexes, just without `indpred`. `pg_index.indkey` stores zero for an expression key, `pg_index.indexprs` stores the expression tree for each zero entry, and `pg_index.indpred` stays null when the index is not partial.[catalogs.sgml#pg-index-expressions-and-predicate](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L3880-L3951) The planner loads expression keys into `IndexOptInfo.indexprs`, and for non-partial indexes `get_relation_info()` sets `IndexOptInfo.tuples` to the parent table row estimate rather than estimating a smaller predicate-selected index row count.[plancat.c#get_relation_info-index-predicate](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L365-L406)

Maintenance cost is the ordinary expression-index cost. `FormIndexDatum()` evaluates expression-key columns with `ExecEvalExprSwitchContext()` for each row that needs an index entry.[index.c#FormIndexDatum](../../../../raw/postgres-12/src/backend/catalog/index.c#L2578-L2648) The documentation describes the tradeoff: expression values are computed on insert and update, but searches do not recompute them because the values are already stored in the index.[indices.sgml#index-expression-maintenance](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L736-L753)

Planner matching does not need a predicate implication proof for an ordinary expression index. It only needs the query clause to match the expression key and operator semantics. `match_clause_to_indexcol()` accepts operator, function, scalar-array, row-comparison, boolean, and supported `IS NULL`/`IS NOT NULL` cases; `match_index_to_operand()` handles expression keys by comparing the query operand to the stored `indexprs` expression with `equal()` after stripping a relabel node.[indxpath.c#match_clause_to_indexcol](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L2317-L2425) [indxpath.c#match_index_to_operand](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3811-L3887)

`ANALYZE` treats ordinary expression indexes as whole-relation expression-stat sources. It initializes `tupleFract = 1.0`, creates `VacAttrStats` only for expression index attributes, and, when no predicate exists, evaluates expression values for every sampled row rather than filtering rows through a predicate. The predicate state is null for an empty qual list, and `compute_index_stats()` only filters rows when that predicate state is not null.[analyze.c#do_analyze_rel-indexdata](../../../../raw/postgres-12/src/backend/commands/analyze.c#L427-L468) [execExpr.c#ExecInitQual](../../../../raw/postgres-12/src/backend/executor/execExpr.c#L188-L215) [analyze.c#compute_index_stats-expression-values](../../../../raw/postgres-12/src/backend/commands/analyze.c#L730-L825) Default selectivity code can then look up the expression-index `pg_statistic` tuple when the matched index is non-partial (`index->indpred == NIL`).[selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4527-L4602)

The regression suite has direct ordinary expression-index coverage. `create_index.sql` creates unique functional and expression indexes (`textcat(f1,f2)` and `(f1 || f2)`), verifies duplicate-key errors, displays the expression-index metadata, and rejects an expression with pseudo-type `record`.[create_index.sql#functional-and-expression-index-tests](../../../../raw/postgres-12/src/test/regress/sql/create_index.sql#L390-L429) [create_index.out#functional-and-expression-index-tests](../../../../raw/postgres-12/src/test/regress/expected/create_index.out#L1270-L1344)

### Partial indexes on expressions

PostgreSQL 12 can combine ordinary expression-index behavior with a partial-index predicate: the index key can be an expression, and the index can also have a partial-index predicate. The `CREATE INDEX` syntax accepts either a column name or an expression in the key list, and accepts `WHERE predicate` after the index options.[create_index.sgml#synopsis](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L24-L30) The documentation describes expression indexes as indexes over a function or scalar expression computed from table columns, such as `lower(col1)` or `(first_name || ' ' || last_name)`, and separately describes a partial unique expression index that stores `(target IS NULL)` only for rows where `target IS NULL`.[indices.sgml#indexes-expressional](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L687-L753) [indices.sgml#partial-expression-one-null](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L959-L967)

The catalog stores these two parts independently. `pg_index.indkey` uses a zero entry for each expression index attribute, `pg_index.indexprs` stores one expression tree for each zero entry, and `pg_index.indpred` stores the partial-index predicate tree or null for a non-partial index.[catalogs.sgml#pg-index-expressions-and-predicate](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L3880-L3951) `IndexOptInfo` mirrors that split with `indexprs` for expression keys and `indpred`/`predOK` for the predicate.[pathnodes.h#IndexOptInfo](../../../../raw/postgres-12/src/include/nodes/pathnodes.h#L746-L821)

Build and DML maintenance evaluate the predicate first and form index datums only for rows that pass. For expression keys, `FormIndexDatum()` prepares expression states and calls `ExecEvalExprSwitchContext()` for key columns whose index attribute number is zero.[heapam_handler.c#heapam_index_build_range_scan](../../../../raw/postgres-12/src/backend/access/heap/heapam_handler.c#L1604-L1626) [execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L303-L384) [index.c#FormIndexDatum](../../../../raw/postgres-12/src/backend/catalog/index.c#L2578-L2648) That means a row outside the predicate avoids expression-key computation for that index, but a row inside the predicate pays the normal expression-index maintenance cost. The expression-index documentation describes that cost: derived expressions are computed on insertion and update, but not recomputed during an indexed search because the values are already stored in the index.[indices.sgml#index-expression-maintenance](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L736-L753)

Planner matching has two gates. First, the query must imply the partial-index predicate so `predOK` becomes true, except for special OR/bitmap handling described above.[indxpath.c#check_index_predicates](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3430-L3532) Second, the query clause must match the expression index key. `match_clause_to_indexcol()` accepts clauses in forms such as `indexkey operator constant`, `constant operator indexkey`, scalar-array, row-compare, boolean, and supported-function cases; `match_index_to_operand()` handles expression keys by retrieving the corresponding `indexprs` item and checking `equal(indexkey, operand)` after stripping a relabel node.[indxpath.c#match_clause_to_indexcol](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L2317-L2425) [indxpath.c#match_opclause_to_indexcol](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L2547-L2629) [indxpath.c#match_index_to_operand](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3811-L3887)

Statistics also combine both features. `ANALYZE` filters the sampled heap rows through the partial-index predicate, then computes expression-column statistics only from the sampled rows that passed the predicate.[analyze.c#compute_index_stats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L694-L843) Those expression statistics are stored with `pg_statistic.starelid` referencing the index, but default planner selectivity code does not use partial expression-index statistics as whole-relation expression statistics, because the source says partial indexes probably do not reflect whole-relation statistics.[catalogs.sgml#pg-statistic-index-expressions](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L6346-L6404) [selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4527-L4601)

Regression coverage includes both pieces together. The partitioned-index regression test creates a parent expression partial index `((b + a)) WHERE a > 1`, creates candidate child indexes with matching and non-matching expressions/predicates, and shows `ALTER INDEX ... ATTACH PARTITION` rejects the non-matching definitions while accepting the matching expression-plus-predicate definition.[indexing.sql#partial-expression-index-attach](../../../../raw/postgres-12/src/test/regress/sql/indexing.sql#L318-L338) [indexing.out#partial-expression-index-attach](../../../../raw/postgres-12/src/test/regress/expected/indexing.out#L638-L674)

### Pros

- **Smaller index and less write maintenance for excluded rows.** The documentation names avoiding common values as a major use case and says this reduces index size, speeds queries that use the index, and speeds many table updates because the index does not need to be updated in all cases.[indices.sgml#exclude-common-values](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L774-L784)
- **Focused access path for hot subsets.** Partial indexes can exclude values that the typical workload is not interested in, including the documented unbilled-orders case where the predicate column and the indexed column are different.[indices.sgml#exclude-uninteresting-values](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L845-L897)
- **Conditional uniqueness.** A unique partial index enforces uniqueness among rows satisfying the predicate and leaves rows outside the predicate unconstrained; the documentation uses this for one successful test per subject/target and for allowing only one null through an expression-plus-partial index.[indices.sgml#partial-unique-index](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L927-L968)
- **Planner steering for unusual distributions.** The documentation says a partial index can be used to make an index unavailable to an offending query when unusual distributions cause a bad index choice.[indices.sgml#override-plan-choices](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L970-L981)
- **Works with `ON CONFLICT` inference when the predicate is covered.** Unique-index inference can use a partial unique index only when the `ON CONFLICT` `WHERE` clause implies the index predicate.[plancat.c#infer_arbiter_indexes](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L792-L824)

### Cons and restrictions

- **Predicate matching is strict and planning-time only.** PostgreSQL 12 recognizes simple implications such as `x < 1` implying `x < 2`, but otherwise the predicate must match a query `WHERE` condition; parameterized clauses do not work because the implication has to hold for all parameter values at planning time.[indices.sgml#partial-index-matching](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L899-L925)
- **The predicate can go stale as data distribution changes.** The documentation says partial indexes that exclude common values require the common values to be predetermined, work best for data distributions that do not change, and may need recreation as distributions change.[indices.sgml#partial-index-distribution-maintenance](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L836-L842)
- **Excluded values cannot use that index.** The documentation warns that excluding uninteresting values prevents those values from being accessed by that index even if an index scan would be profitable for them.[indices.sgml#exclude-uninteresting-values](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L845-L854)
- **DML still pays predicate-evaluation cost.** `ExecInsertIndexTuples()` evaluates the predicate before deciding whether to skip the index update, so an excluded row avoids index insertion but not the predicate check.[execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L303-L384)
- **A partial index cannot become a primary-key or unique table constraint via an existing-index constraint.** The parser rejects `ALTER TABLE ... ADD CONSTRAINT ... USING INDEX` when `RelationGetIndexPredicate(index_rel) != NIL`.[parse_utilcmd.c#partial-index-constraint-reject](../../../../raw/postgres-12/src/backend/parser/parse_utilcmd.c#L2076-L2093)
- **A partial index cannot be a replica identity index.** `ALTER TABLE ... REPLICA IDENTITY USING INDEX` rejects predicate indexes with `cannot use partial index ... as replica identity`.[tablecmds.c#ATExecReplicaIdentity](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L13964-L13975)
- **`CLUSTER` cannot use a partial index.** `check_index_is_clusterable()` rejects indexes with `pg_index.indpred` because they may not index every row.[cluster.c#check_index_is_clusterable](../../../../raw/postgres-12/src/backend/commands/cluster.c#L469-L479)
- **Some planner deductions from uniqueness are gated by `predOK`.** `has_unique_index()` ignores a partial unique index for whole-relation uniqueness unless `predOK` is true, because an unmatched partial index cannot prove all attribute values are distinct.[plancat.c#has_unique_index](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L2039-L2051)

### Statistics generated by `ANALYZE`

`ANALYZE` collects table-content statistics into `pg_statistic`, and the planner later uses those statistics to choose execution plans.[analyze.sgml#description](../../../../raw/postgres-12/doc/src/sgml/ref/analyze.sgml#L41-L47) PostgreSQL 12 statistics normally include most-common values, histograms, null fraction, width, and distinct-value estimates, with the sample size and MCV/histogram limit controlled by the statistics target.[analyze.sgml#notes-statistics](../../../../raw/postgres-12/doc/src/sgml/ref/analyze.sgml#L188-L239) [pg_statistic.h#pg_statistic-fields](../../../../raw/postgres-12/src/include/catalog/pg_statistic.h#L36-L83)

For a partial index, `compute_index_stats()` evaluates the index predicate against each sampled heap tuple and counts only sampled rows that pass. It records `tupleFract = numindexrows / numrows`, estimates `totalindexrows = ceil(tupleFract * totalrows)`, and computes expression-column statistics from the predicate-passing sample rows.[analyze.c#compute_index_stats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L694-L843)

`ANALYZE` stores statistics for index expressions in `pg_statistic` with `starelid` referencing the index; it does not store redundant `pg_statistic` rows for ordinary non-expression index columns.[catalogs.sgml#pg-statistic-index-expressions](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L6346-L6404) The source follows that rule: `do_analyze_rel()` calls `examine_attribute()` only for index columns where `ii_IndexAttrNumbers[i] == 0`, meaning expression columns, and only when an explicit column list was not supplied.[analyze.c#do_analyze_rel-indexdata](../../../../raw/postgres-12/src/backend/commands/analyze.c#L427-L468) `examine_attribute()` uses the expression tree's type, typmod, and collation for expression-index statistics.[analyze.c#examine_attribute](../../../../raw/postgres-12/src/backend/commands/analyze.c#L870-L953)

`update_attstats()` writes `pg_statistic` rows with `starelid`, `staattnum`, `stainherit`, `stanullfrac`, `stawidth`, `stadistinct`, slot kinds, operators, collations, numbers, and values.[analyze.c#update_attstats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L1395-L1457) [analyze.c#update_attstats-slots](../../../../raw/postgres-12/src/backend/commands/analyze.c#L1469-L1543) Core scalar statistics can include MCV slots, histogram slots, and correlation slots; `pg_statistic.h` defines MCV frequency arrays, histogram bin values, and a single correlation coefficient ranging from -1 to +1.[analyze.c#std_typanalyze](../../../../raw/postgres-12/src/backend/commands/analyze.c#L1648-L1699) [analyze.c#compute_scalar_stats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L2328-L2649) [pg_statistic.h#statistic-kinds](../../../../raw/postgres-12/src/include/catalog/pg_statistic.h#L168-L209)

`ANALYZE` also updates whole-relation `pg_class` statistics for the index. It passes `RelationGetNumberOfBlocks(Irel[ind])` and `ceil(tupleFract * totalrows)` to `vac_update_relstats()`, which writes `pg_class.relpages` and `pg_class.reltuples` for both heap and index relations.[analyze.c#index-relstats-update](../../../../raw/postgres-12/src/backend/commands/analyze.c#L613-L630) [vacuum.c#vac_update_relstats](../../../../raw/postgres-12/src/backend/commands/vacuum.c#L1117-L1190) The catalog documentation describes `relpages` and `reltuples` as planner estimates updated by `VACUUM`, `ANALYZE`, and DDL such as `CREATE INDEX`.[catalogs.sgml#pg-class-relpages-reltuples](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L1759-L1781)

### How the planner uses those statistics

`get_relation_info()` uses relation metadata to fill `IndexOptInfo.pages` and `IndexOptInfo.tuples`. For non-partial indexes it sets `tuples` equal to the parent table estimate; for partial indexes it calls `estimate_rel_size()` for the index relation and caps the estimate at the parent table's tuple count.[plancat.c#get_relation_info-size](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L387-L406)

For index scan costing, `genericcostestimate()` adds non-redundant partial-index predicate clauses to the explicit index quals before estimating selectivity. It then estimates visited index tuples from `indexSelectivity * index->rel->tuples`, adjusts for scalar-array scans, clamps by `index->tuples`, and estimates index pages as a pro-rata fraction of total index pages.[selfuncs.c#genericcostestimate](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L5662-L5763) [selfuncs.c#add_predicate_to_index_quals](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L5878-L5916)

For base table column statistics, selectivity code looks up the table column's `pg_statistic` row through `SearchSysCache3(STATRELATTINH, rte->relid, varattno, rte->inh)`.[selfuncs.c#examine_simple_variable](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4708-L4737) Equality selectivity checks MCV entries and uses their frequencies when a constant matches one; otherwise it spreads the remaining non-null, non-MCV fraction over other distinct values.[selfuncs.c#var_eq_const](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L289-L420) Inequality selectivity combines MCV selectivity with histogram selectivity over the non-null, non-MCV remainder.[selfuncs.c#scalarineqsel](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L651-L686) [selfuncs.c#mcv_selectivity](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L716-L744) [selfuncs.c#histogram_selectivity](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L791-L828)

For expression statistics, `examine_variable()` tries to match a query expression to an expression index column. It uses statistics from non-partial expression indexes, but it does not use partial expression-index statistics for whole-relation selectivity unless an index statistics hook takes control; the source comment says partial indexes probably do not reflect whole-relation statistics.[selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4527-L4601)

For actual index-path selectivity, partial indexes are still costed with their predicate included in the selectivity qual list. This means a partial index can get a more accurate selectivity estimate for its own scan even though its expression statistics are not treated as whole-relation expression statistics.[selfuncs.c#genericcostestimate](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L5662-L5763) [selfuncs.c#add_predicate_to_index_quals](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L5878-L5916)

### Regression coverage

The v12 regression suite creates B-tree partial indexes on `onek2` with predicates on `unique1` and `stringu1`.[create_index.sql#btree-partial-indexes](../../../../raw/postgres-12/src/test/regress/sql/create_index.sql#L63-L72) The `select` regression test runs `ANALYZE onek2` before partial B-tree index tests because the planner probably will not pick an index scan without stats.[select.sql#partial-btree-indexes](../../../../raw/postgres-12/src/test/regress/sql/select.sql#L59-L91) [select.out#partial-btree-indexes](../../../../raw/postgres-12/src/test/regress/expected/select.out#L206-L293)

The same regression file covers a usable partial index, a predicate-implied scan with no filter retest, an update-target case that keeps the filter, a non-applicable partial index that falls back to a sequential scan, and bitmap scans that recheck the predicate.[select.sql#partial-index-planning](../../../../raw/postgres-12/src/test/regress/sql/select.sql#L191-L234) [select.out#partial-index-plans](../../../../raw/postgres-12/src/test/regress/expected/select.out#L737-L899)
