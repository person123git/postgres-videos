## Question

In PostgreSQL 12, what are the pros and cons of creating indexes only on the parent table versus only on the child tables of a declaratively partitioned table?

Prompt-hygiene note: the prompt as submitted read `follow agents.md, in postgresql 12, question: what are the pros and cons of having on a declarative partitioning indexes only on the parent table versus only on the child tables.` The asker chose "correct and restate", so the misplaced modifier, the lowercase product name, and the missing capitalization were fixed before drafting. The asker also scoped the page to the `CREATE INDEX ON parent` cascade versus per-partition `CREATE INDEX`, and asked for a source-only analysis with no server measurements.

## Answer

### Verdict

**A parent index manages a family of leaf indexes; it is not another physical index over all the rows.** `CREATE INDEX` on a partitioned table creates a storage-less index and recurses, adopting or building indexes below it. Intermediate partitioned indexes also have no storage; ordinary leaf partitions hold the physical indexes. A plain-index cascade skips foreign-table partitions, while a unique-index cascade rejects them ([indexcmds.c#DefineIndex-partitioned](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L595-L604), [indexcmds.c#recursion](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1041-L1105), [indexcmds.c#adopt-or-create](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1114-L1236)).

With the same usable leaf indexes, the parent index adds no scan path and no physical index to maintain per tuple. It does change DDL, locks, parent-level constraints, targeted conflict handling, and some index-opening work. The comparison below assumes ordinary leaf partitions; its qualifications are detailed in the following sections ([plancat.c#skip-partitioned-index](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L196-L220), [execPartition.c#leaf-indexes](../../../../raw/postgres-12/src/backend/executor/execPartition.c#L535-L545), [plancat.c#infer_arbiter_indexes](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L607-L615)).

| | `CREATE INDEX ON parent` (cascade) | `CREATE INDEX` per partition, no parent index |
|---|---|---|
| Future partitions indexed automatically | Match or create; check validity caveat below | No parent index to clone ([tablecmds.c#clone-parent-indexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L1057-L1110), [tablecmds.c#attach-existing-index](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15967-L16029)) |
| `CONCURRENTLY` available | No | Yes, per ordinary leaf ([indexcmds.c#lockmode-and-restriction](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L559-L616)) |
| Writes blocked during the build | Every partition, until the one transaction commits | One leaf per statement; `CONCURRENTLY` avoids the build-long `ShareLock` ([utility.c#prelock-index-hierarchy](../../../../raw/postgres-12/src/backend/tcop/utility.c#L1320-L1343), [indexcmds.c#keep-lock](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1167-L1176), [lock.c#LockConflicts](../../../../raw/postgres-12/src/backend/storage/lmgr/lock.c#L73-L87)) |
| Definition may vary per partition | Matching fields must agree; storage options and some other fields may differ | Independent definitions ([index.c#CompareIndexInfo](../../../../raw/postgres-12/src/backend/catalog/index.c#L2418-L2523)) |
| Drop an index on one partition only | Not while attached | Yes, subject to local constraint ownership ([dependency.c#partition-dependency-error](../../../../raw/postgres-12/src/backend/catalog/dependency.c#L1040-L1065), [dependency.c#owning-object-error](../../../../raw/postgres-12/src/backend/catalog/dependency.c#L807-L827)) |
| Parent-level `UNIQUE` / `PRIMARY KEY` | Yes, subject to partition-key restrictions | No ([indexcmds.c#unique-partition-key](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L823-L898)) |
| Parent table can be an FK target | Yes, via a suitable unique index | No ([tablecmds.c#transformFkeyCheckAttrs](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L9550-L9647)) |
| `ON CONFLICT` with a target on the parent | Requires a suitable parent arbiter index | No ([plancat.c#arbiter-inference](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L674-L746), [plancat.c#arbiter-error](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L819-L822)) |
| Untargeted `ON CONFLICT DO NOTHING` | Checks eligible leaf indexes | Also works with independent leaf indexes ([plancat.c#untargeted-do-nothing](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L607-L615), [execIndexing.c#ExecCheckIndexConstraints](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L523-L600)) |
| `REINDEX` the whole family in one command | No | No ([indexcmds.c#ReindexPartitionedIndex](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L3384-L3396), [index.c#reindex_relation-skip](../../../../raw/postgres-12/src/backend/catalog/index.c#L3686-L3700)) |
| Single `DROP INDEX` removes the family | Yes for a standalone parent index; drop the owning constraint for a PK/UNIQUE-backed index | No family to cascade through ([indexing.out#drop-parent](../../../../raw/postgres-12/src/test/regress/expected/indexing.out#L160-L177), [index.c#constraint-index-dependency](../../../../raw/postgres-12/src/backend/catalog/index.c#L1888-L1896)) |

Use the parent family for parent-level constraints and automated index propagation. Use independent leaf indexes when matched fields must differ or some leaves should have no corresponding index. Different storage options alone do not force that choice ([indexcmds.c#unique-partition-key](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L823-L898), [tablecmds.c#clone-parent-indexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L1057-L1110), [index.c#CompareIndexInfo](../../../../raw/postgres-12/src/backend/catalog/index.c#L2418-L2523)). For a parent-managed family without hierarchy-wide writer exclusion throughout the physical builds, use the documented `ON ONLY` + per-leaf `CONCURRENTLY` + index-attachment rollout. Metadata steps still take locks; multi-level validation can lock ancestors ([ddl.sgml#index-partitioning](../../../../raw/postgres-12/doc/src/sgml/ddl.sgml#L3973-L4009), [tablecmds.c#index-attach-locks](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L16514-L16541), [tablecmds.c#validate-recursion](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L16744-L16768)).

### What an index on the parent actually is

`DefineIndex` accepts `RELKIND_PARTITIONED_TABLE` as a target and sets a `partitioned` flag ([indexcmds.c#relkind-switch](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L568-L604)). From there:

1. It adds `INDEX_CREATE_SKIP_BUILD` and `INDEX_CREATE_PARTITIONED` to the flags, with the comment "or doing a partitioned index (because those don't have storage)" ([indexcmds.c#create-flags](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L962-L987)).
2. `index_create` gives the new relation `RELKIND_PARTITIONED_INDEX` ([index.c:735](../../../../raw/postgres-12/src/backend/catalog/index.c#L735)) and, because the build is skipped, only marks the table `relhasindex = true` ([index.c#skip-build](../../../../raw/postgres-12/src/backend/catalog/index.c#L1206-L1218)).
3. Unless `ONLY` was given, it walks `RelationGetPartitionDesc`, opens every partition, and for each one either **adopts** an existing index whose definition matches or **creates** a new one by calling itself recursively ([indexcmds.c#per-partition-loop](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1076-L1236)).
4. It then returns without building anything: "Indexes on partitioned tables are not themselves built, so we're done here" ([indexcmds.c#no-build](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1266-L1276)).

The parent row has no file. `index_drop` skips `RelationDropStorage` for it ([index.c#drop-storage](../../../../raw/postgres-12/src/backend/catalog/index.c#L2199-L2203)) and `pg_relation_filenode()` returns `NULL` for any relkind outside the storage list ([dbsize.c#pg_relation_filenode](../../../../raw/postgres-12/src/backend/utils/adt/dbsize.c#L877-L896)). The link between parent and child is a `pg_inherits` row plus two `pg_depend` rows of type `DEPENDENCY_PARTITION_PRI` and `DEPENDENCY_PARTITION_SEC` ([indexcmds.c#IndexSetParentIndex](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L3398-L3406), [indexcmds.c#partition-dependencies](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L3508-L3538), [index.c#index_create-dependencies](../../../../raw/postgres-12/src/backend/catalog/index.c#L1098-L1118)).

Adoption uses `CompareIndexInfo`. It compares uniqueness, access method, total and key-column counts, mapped columns, collations, operator families, expressions, and partial-index predicates; exclusion indexes are never matched. It compares operator-family OIDs, **not exact operator-class OIDs**. It does **not** compare names, storage options (`reloptions`), tablespaces, or sort-direction/NULL-order flags. A child differing only in `fillfactor` can therefore be adopted, and attachment is not proof of byte-for-byte identical definitions ([index.c#CompareIndexInfo](../../../../raw/postgres-12/src/backend/catalog/index.c#L2418-L2523), [index.c#BuildIndexInfo](../../../../raw/postgres-12/src/backend/catalog/index.c#L2294-L2355), [pg_index.h#indclass-and-indoption](../../../../raw/postgres-12/src/include/catalog/pg_index.h#L49-L76)).

There is a third spelling, `CREATE INDEX ON ONLY parent`, which really does index nothing: it skips the recursion, and if the table already has partitions the parent index is marked invalid ([indexcmds.c#ON-ONLY-invalid](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L988-L998), [create_index.sgml#ONLY](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L211-L219)). On a partitioned table with **no** partitions yet, that same statement leaves a valid parent index, because the `nparts != 0` test fails. This page treats `ON ONLY` as a build technique rather than a design, and covers it under [The hybrid the documentation recommends](#the-hybrid-the-documentation-recommends).

### What is identical in both designs

Hold the leaf indexes, their validity, data, and planner inputs fixed for this comparison. Matching on attachment alone is a weaker condition, as described above.

- **Leaf scan choices.** The planner skips partitioned indexes as scan candidates. Adding the parent index does not supply another index scan over the hierarchy; it still considers the leaf indexes ([plancat.c#skip-partitioned-index](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L205-L220)).
- **Partition pruning.** `prune_append_rel_partitions` derives pruning steps from clauses and partition bounds, not the index list ([partprune.c#prune_append_rel_partitions](../../../../raw/postgres-12/src/backend/partitioning/partprune.c#L653-L716), [ddl.sgml#pruning-and-indexes](../../../../raw/postgres-12/doc/src/sgml/ddl.sgml#L4541-L4549)).
- **Physical tuple maintenance.** Routed tuples use the leaf partition's index descriptors; insertion calls `index_insert` on those indexes, not a physical root index ([execPartition.c#ExecOpenIndices](../../../../raw/postgres-12/src/backend/executor/execPartition.c#L535-L545), [execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L383-L400)).
- **Physical size.** The parent contributes no index pages; `RELKIND_HAS_STORAGE` excludes partitioned indexes. Holding the physical leaf indexes fixed therefore holds their total size fixed ([pg_class.h#RELKIND_HAS_STORAGE](../../../../raw/postgres-12/src/include/catalog/pg_class.h#L154-L192)).

**Index-opening work is not identical.** For `INSERT` into the parent, the planner includes the named target in `ModifyTable`'s result relations. `ExecInitModifyTable` opens that target's indexes; `ExecOpenIndices` has no partitioned-index filter and opens each under `RowExclusiveLock`. Tuple routing then opens the leaf's indexes for actual insertion ([planner.c#insert-target](../../../../raw/postgres-12/src/backend/optimizer/plan/planner.c#L2315-L2374), [nodeModifyTable.c#open-result-rel-indices](../../../../raw/postgres-12/src/backend/executor/nodeModifyTable.c#L2321-L2349), [execIndexing.c#ExecOpenIndices](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L160-L217), [execPartition.c#leaf-indexes](../../../../raw/postgres-12/src/backend/executor/execPartition.c#L519-L545)).

Do not extend that executor claim to ordinary `UPDATE`. Its modification plans target leaf partitions: the planner skips partitioned intermediate targets, collects leaf targets, and the executor's index-opening loop follows those targets rather than its separate root descriptor ([planner.c#skip-partitioned-target](../../../../raw/postgres-12/src/backend/optimizer/plan/planner.c#L1523-L1541), [planner.c#resultRelations](../../../../raw/postgres-12/src/backend/optimizer/plan/planner.c#L1678-L1685), [nodeModifyTable.c#result-targets](../../../../raw/postgres-12/src/backend/executor/nodeModifyTable.c#L2293-L2349)). Separately, planning can open and lock a parent index **before** excluding it from scan candidates. Neither distinction establishes a measured timing penalty ([plancat.c#index-open-before-skip](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L193-L220)).

### What the parent index buys you

- **Automatic match-or-create on ordinary partitions.** `CREATE TABLE ... PARTITION OF` clones parent indexes; `ALTER TABLE ... ATTACH PARTITION` adopts a matching index or builds one. This does not guarantee that every adopted index is valid: see the table-attachment caveat under [Maintenance and lifecycle differences](#maintenance-and-lifecycle-differences) ([tablecmds.c#clone-parent-indexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L1057-L1110), [tablecmds.c#AttachPartitionEnsureIndexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15932-L16029)).
- **A shared definition for the fields actually compared.** `CompareIndexInfo` enforces the matching rules above, but does not enforce identical storage options, tablespaces, exact opclass OIDs, or sort flags ([index.c#CompareIndexInfo](../../../../raw/postgres-12/src/backend/catalog/index.c#L2418-L2523)).
- **One family-level drop operation.** For a standalone parent index, `DROP INDEX` removes its attached descendants. For an index owned by a `PRIMARY KEY` or `UNIQUE` constraint, drop the owning parent constraint instead: the index's internal dependency prevents dropping it directly ([indexing.out#drop-parent](../../../../raw/postgres-12/src/test/regress/expected/indexing.out#L160-L177), [index.c#constraint-index-dependency](../../../../raw/postgres-12/src/backend/catalog/index.c#L1888-L1896), [dependency.c#owning-object-error](../../../../raw/postgres-12/src/backend/catalog/dependency.c#L807-L827), [indexing.out#drop-parent-constraint](../../../../raw/postgres-12/src/test/regress/expected/indexing.out#L1031-L1050)).
- **A single handle for the family.** `pg_partition_tree()` accepts `RELKIND_PARTITIONED_INDEX` ([partitionfuncs.c#check_rel_can_be_partition](../../../../raw/postgres-12/src/backend/utils/adt/partitionfuncs.c#L43-L54)), which is what `\dPi+` uses to report a "Total size" summed over the whole index tree ([describe.c#dP-total-size](../../../../raw/postgres-12/src/bin/psql/describe.c#L3874-L3894), [describe.c#pg_partition_tree-size](../../../../raw/postgres-12/src/bin/psql/describe.c#L3929-L3940)).
- **Parent-level constraints.** See [Capabilities only a parent index can provide](#capabilities-only-a-parent-index-can-provide).

### What the parent index costs you

- **No `CONCURRENTLY`.** `DefineIndex` rejects it for a partitioned table, even a temporary one. This is not the first possible failure: the utility caller performs transaction-block checks and relation locking before `DefineIndex` ([indexcmds.c#no-concurrently](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L604-L616), [utility.c#T_IndexStmt](../../../../raw/postgres-12/src/backend/tcop/utility.c#L1301-L1373), [create_index.sgml#no-concurrent-partitioned](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L624-L631)).
- **A write outage across the whole hierarchy.** Detailed in [The lock footprint of each design](#the-lock-footprint-of-each-design).
- **All-or-nothing progress.** The non-concurrent path never splits transactions — the only `CommitTransactionCommand` calls in `DefineIndex` are on the concurrent path, which the partitioned case can never reach ([indexcmds.c#non-concurrent-return](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1266-L1288), [indexcmds.c#concurrent-commits](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1319-L1320)). A failure on the last partition discards every index built so far.
- **`REINDEX` does not work on the family.** `REINDEX INDEX parent_idx` raises `REINDEX is not yet implemented for partitioned indexes` ([indexcmds.c#ReindexPartitionedIndex](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L3384-L3396)), and `REINDEX TABLE parent` emits `REINDEX of partitioned tables is not yet implemented, skipping` and returns — in both the plain and the concurrent path ([index.c#reindex_relation-skip](../../../../raw/postgres-12/src/backend/catalog/index.c#L3686-L3700), [indexcmds.c#reindex-concurrently-skip](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L2917-L2923)). You still reindex partition by partition, exactly as in the per-partition design.
- **You cannot independently drop an attached child index.** Partition dependencies reject that operation. There is no `ALTER INDEX ... DETACH PARTITION` in v12; detaching the whole table partition removes its index-parent links. Dropping the parent index family, or its owning constraint when applicable, is the other family-level option. Rebuilding an attached leaf index with `REINDEX` remains supported; it is not an independent drop-and-redefine operation ([dependency.c#partition-dependency-error](../../../../raw/postgres-12/src/backend/catalog/dependency.c#L1040-L1065), [gram.y#index_partition_cmd](../../../../raw/postgres-12/src/backend/parser/gram.y#L2048-L2062), [tablecmds.c#detach-indexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L16327-L16351), [indexcmds.c#ReindexIndex](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L2366-L2382), [index.c#constraint-index-dependency](../../../../raw/postgres-12/src/backend/catalog/index.c#L1888-L1896)).
- **The matched fields cannot vary within the family.** Different access methods, key sets, expressions, or partial predicates cannot stand in for the corresponding parent definition. Missing indexes are cloned from the parent statement. But storage options and tablespaces may differ on adopted indexes, and the matcher does not compare exact opclass OIDs or sort flags ([index.c#CompareIndexInfo](../../../../raw/postgres-12/src/backend/catalog/index.c#L2418-L2523), [indexcmds.c#clone-child-stmt](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1178-L1236)).
- **`ATTACH PARTITION` may turn into an index build.** If the incoming table has no matching index, ATTACH builds one right there, while holding `AccessExclusiveLock` on that table ([tablecmds.c#attach-build-index](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L16012-L16029), [tablecmds.c#attach-lock](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15598-L15607)).
- **Two restrictions with no per-partition counterpart.** Exclusion constraints are rejected on a partitioned table ([indexcmds.c#no-exclusion](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L617-L621)), and an explicit `TABLESPACE` equal to the database default is rejected with `cannot specify default tablespace for partitioned relations` ([indexcmds.c#tablespace](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L662-L669)).
- **A partition that is a foreign table is skipped, or fatal.** The cascade skips foreign-table partitions for a plain index and errors for a unique one ([indexcmds.c#foreign-partition](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1088-L1105)).

### What per-partition indexes buy you

- **`CREATE INDEX CONCURRENTLY` works.** A leaf partition is an ordinary `RELKIND_RELATION`, so `DefineIndex` takes the concurrent path and locks that one table with `ShareUpdateExclusiveLock` instead of `ShareLock` ([indexcmds.c#lockmode](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L559-L564)). Detail on the concurrent path is on the dedicated page, [How CREATE INDEX CONCURRENTLY Is Implemented in PostgreSQL 12](create-index-concurrently.md).
- **Incremental rollout when each leaf build commits separately.** Do not put all plain builds in one transaction if you want earlier builds to survive a later failure. `CREATE INDEX CONCURRENTLY` cannot be grouped in a transaction block ([utility.c#T_IndexStmt](../../../../raw/postgres-12/src/backend/tcop/utility.c#L1301-L1309), [indexcmds.c#non-concurrent-return](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1266-L1288)).
- **Independent definitions.** Each leaf statement supplies its own access method, keys, predicate, and storage options. No parent-index matching step restricts that choice. Different `fillfactor` alone does not require this design, because attachment does not compare it ([gram.y#IndexStmt](../../../../raw/postgres-12/src/backend/parser/gram.y#L7341-L7367), [index.c#CompareIndexInfo](../../../../raw/postgres-12/src/backend/catalog/index.c#L2418-L2523)).
- **Independent drops, subject to other dependencies.** Unattached indexes have no index-partition dependency. Local `PRIMARY KEY` or `UNIQUE` constraint ownership still prevents a direct index drop. A standalone leaf index can use `DROP INDEX CONCURRENTLY`, which permits only one index and no `CASCADE` ([dependency.c#partition-dependency-error](../../../../raw/postgres-12/src/backend/catalog/dependency.c#L1040-L1065), [index.c#constraint-index-dependency](../../../../raw/postgres-12/src/backend/catalog/index.c#L1888-L1896), [dependency.c#owning-object-error](../../../../raw/postgres-12/src/backend/catalog/dependency.c#L807-L827), [tablecmds.c#drop-concurrently](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L1235-L1253)).
- **`ATTACH PARTITION` never turns into an index build.** With no partitioned index on the parent, `AttachPartitionEnsureIndexes` finds nothing to enforce — it only considers parent indexes whose relkind is `RELKIND_PARTITIONED_INDEX` ([tablecmds.c#ignore-plain-parent-indexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15945-L15953)).
- **`REINDEX` per partition works normally,** including `CONCURRENTLY`, because only `RELKIND_PARTITIONED_INDEX` is rejected ([indexcmds.c#ReindexIndex](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L2366-L2382), [index.c#reindex_index-relkind](../../../../raw/postgres-12/src/backend/catalog/index.c#L3476-L3482)). This is equally true of a child index that is attached to a parent.

### What per-partition indexes cost you

- **New partitions need separate index provisioning.** Independent indexes on sibling leaves are not templates: the clone and attachment loops use the parent's index list ([tablecmds.c#clone-parent-indexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L1057-L1110), [tablecmds.c#AttachPartitionEnsureIndexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15932-L15940)).
- **No parent-level `UNIQUE`, `PRIMARY KEY`, FK target, or targeted `ON CONFLICT`.** Untargeted `ON CONFLICT DO NOTHING` is the exception, detailed below. Per-partition unique indexes enforce uniqueness *within* each partition only ([ddl.sgml#unique-limitation](../../../../raw/postgres-12/doc/src/sgml/ddl.sgml#L4026-L4033), [plancat.c#untargeted-do-nothing](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L607-L615)).
- **Definition consistency is your responsibility.** The parent-index matching loop cannot enforce coverage when there is no parent index to iterate ([tablecmds.c#AttachPartitionEnsureIndexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15932-L15953)).
- **No index-family handle for DDL.** Independent leaf indexes have no index-parent links for a parent-index drop or tree walk to follow; family-level `REINDEX` is unavailable in either design ([indexcmds.c#IndexSetParentIndex](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L3398-L3406), [indexcmds.c#ReindexPartitionedIndex](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L3384-L3396)).
- **No parent-index handle in `\dPi`.** That command lists partitioned indexes, so independent leaf indexes supply no root entry ([describe.c#dPi](../../../../raw/postgres-12/src/bin/psql/describe.c#L3824-L3862)). Do not use `pg_tables.hasindexes` as an exact coverage test: it exposes `pg_class.relhasindex`, which can remain true even when no index exists ([system_views.sql#pg_tables](../../../../raw/postgres-12/src/backend/catalog/system_views.sql#L127-L139), [index.c#relhasindex-can-be-stale](../../../../raw/postgres-12/src/backend/catalog/index.c#L2698-L2708)).

### The lock footprint of each design

This is the dominant practical difference.

`CREATE INDEX ON parent` runs non-concurrently, so `lockmode` is `ShareLock`. **Before any recursive build starts**, `ProcessUtilitySlow` locks the target and calls `find_all_inheritors(relid, lockmode, NULL)` to lock the hierarchy ([utility.c#prelock-index-hierarchy](../../../../raw/postgres-12/src/backend/tcop/utility.c#L1320-L1373)). `DefineIndex` opens children with that same lock mode and closes them with `NoLock` to retain locks until transaction end ([indexcmds.c#child-open](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1076-L1086), [indexcmds.c#keep-lock](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1167-L1176)). `ShareLock` conflicts with writers' `RowExclusiveLock` ([lock.c#LockConflicts](../../../../raw/postgres-12/src/backend/storage/lmgr/lock.c#L73-L87)). Once those locks are acquired:

- Writes are blocked on **every partition** — including partitions already finished and partitions not yet started — until the single transaction commits.
- Reads are unaffected: `AccessShareLock` conflicts only with `AccessExclusiveLock` ([lock.c#LockConflicts](../../../../raw/postgres-12/src/backend/storage/lmgr/lock.c#L65-L101)).
- The lock count scales with the hierarchy: one `ShareLock` per partition plus one relation lock per new index, all held in one transaction, which is `max_locks_per_transaction` pressure on wide hierarchies.

Per-leaf `CREATE INDEX CONCURRENTLY` takes `ShareUpdateExclusiveLock`, which does not conflict with `RowExclusiveLock`. It avoids the build-long writer exclusion, not every possible wait or unique-index error. A plain leaf build takes `ShareLock` for that leaf until its transaction ends; this page makes no claim that the build is brief ([indexcmds.c#lockmode](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L559-L564), [lock.c#LockConflicts](../../../../raw/postgres-12/src/backend/storage/lmgr/lock.c#L78-L87), [create_index.sgml#concurrent-caveats](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L598-L621)).

The attach-side locks are worth knowing in both designs:

| Operation | Locks taken |
|---|---|
| `ALTER TABLE parent ATTACH PARTITION t` | `ShareUpdateExclusiveLock` on the parent ([tablecmds.c#attach-lock-level](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L3806-L3808)), `AccessExclusiveLock` on `t` ([tablecmds.c#attach-lock](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15598-L15607)), plus `AccessExclusiveLock` on the default partition if one exists |
| `ALTER TABLE parent DETACH PARTITION t` | `AccessExclusiveLock` on the parent ([tablecmds.c#detach-lock-level](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L3810-L3812)); `ShareUpdateExclusiveLock` on `t` and `AccessExclusiveLock` on the default partition when present ([tablecmds.c#detach-table-locks](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L16271-L16280)); `AccessExclusiveLock` on each of `t`'s attached indexes ([tablecmds.c#detach-indexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L16327-L16351)) |
| `ALTER INDEX parent_idx ATTACH PARTITION child_idx` | `ShareUpdateExclusiveLock` on `parent_idx`, `AccessExclusiveLock` on `child_idx`, `AccessShareLock` on both tables ([tablecmds.c#ATExecAttachPartitionIdx](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L16514-L16541)); in a multi-level hierarchy the validation step also takes `AccessExclusiveLock` on the grandparent index *and* the grandparent table ([tablecmds.c#validate-recursion](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L16744-L16768)) |

### Capabilities only a parent index can provide

Parent constraints and targeted conflict handling need suitable indexes on the named parent. Untargeted `ON CONFLICT DO NOTHING` follows a different path, described below.

**Parent-level `UNIQUE` and `PRIMARY KEY`.** They exist only as partitioned indexes, and every partition key column must appear in the key: otherwise `insufficient columns in %s constraint definition` with a detail naming the missing column. An expression partition key is refused outright with `unsupported %s constraint with partition key definition` ([indexcmds.c#unique-partition-key](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L823-L898)). The code comment explains the rule: "A partition-local index can enforce global uniqueness iff the PK value completely determines the partition that a row is in." There is no escape hatch through an existing index, because `ALTER TABLE ... ADD CONSTRAINT ... USING INDEX is not supported on partitioned tables` ([tablecmds.c#using-index-unsupported](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L7344-L7351)).

**Being the referenced side of a foreign key.** v12 lets `pkrel` be a partitioned table ([tablecmds.c#pkrel-relkind](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L7722-L7727)), but the matching index is found by scanning `RelationGetIndexList(pkrel)` for one that is unique, valid, immediate, non-partial, and non-expression; otherwise `there is no unique constraint matching given keys for referenced table` ([tablecmds.c#transformFkeyCheckAttrs](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L9550-L9647)). Only a parent-level unique index appears in that list.

**Targeted `INSERT ... ON CONFLICT` against the parent.** An arbiter index is an index chosen to detect conflicts for the clause. With a column/expression target or a named constraint, `infer_arbiter_indexes` searches the target relation's own indexes, including partitioned indexes, and errors when no suitable index matches. `DO UPDATE` requires a target. The executor maps each selected parent index to the leaf through index ancestry ([plancat.c#target-required-for-update](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L607-L615), [plancat.c#arbiter-inference](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L674-L746), [plancat.c#arbiter-error](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L819-L822), [execPartition.c#arbiter-mapping](../../../../raw/postgres-12/src/backend/executor/execPartition.c#L690-L728)).

**Exception: untargeted `ON CONFLICT DO NOTHING` needs no parent index.** Inference returns an empty arbiter list immediately. Tuple routing still opens the leaf's indexes. With an empty list, `ExecCheckIndexConstraints` checks the leaf's ready unique/exclusion indexes without an arbiter-ID filter; non-immediate (deferrable) arbiters raise an error. The insert path uses those checks to skip a conflicting row. Independent leaf indexes therefore support this form, although this does not create a parent-level uniqueness constraint ([plancat.c#untargeted-do-nothing](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L607-L615), [execPartition.c#open-leaf-indexes](../../../../raw/postgres-12/src/backend/executor/execPartition.c#L535-L545), [execIndexing.c#ExecCheckIndexConstraints](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L523-L600), [nodeModifyTable.c#ExecInsert-on-conflict](../../../../raw/postgres-12/src/backend/executor/nodeModifyTable.c#L468-L564)).

### Maintenance and lifecycle differences

- **Adopting existing per-partition indexes.** You are not locked into your first choice. If matching indexes already exist on the partitions, `CREATE INDEX ON parent` adopts them via `IndexSetParentIndex` instead of building duplicates ([indexcmds.c#adopt](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1114-L1173), [indexing.out#no-duplicate](../../../../raw/postgres-12/src/test/regress/expected/indexing.out#L125-L150)). Migrating from per-partition to parent-managed is therefore a metadata-only operation when the definitions already agree.
- **Cascading creation propagates an adopted child's invalid state.** `DefineIndex` tests `indisvalid` after adopting an existing child and sets the new parent invalid if needed ([indexcmds.c#adopt-invalid-child](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1156-L1164), [indexcmds.c#invalidate-parent](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1243-L1265)). See [All Outcomes That Leave an Invalid Index in PostgreSQL 12](invalid-index-outcomes.md).
- **Table attachment has a different invalid-index edge case at this pin.** `RelationGetIndexList` includes invalid indexes that are still live. `AttachPartitionEnsureIndexes` can adopt a matching unattached invalid index: its match branch does not test `indisvalid` or insertion readiness, and it neither invalidates an already-valid parent nor calls `validatePartitionedIndex`. Thus the parent's valid flag alone does not prove all adopted leaf indexes are valid. Check the leaves before treating attachment as successful usable coverage. This is a source-derived result, not a server measurement ([relcache.c#RelationGetIndexList](../../../../raw/postgres-12/src/backend/utils/cache/relcache.c#L4384-L4398), [index.c#CompareIndexInfo](../../../../raw/postgres-12/src/backend/catalog/index.c#L2418-L2523), [tablecmds.c#attach-existing-index](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15967-L16040), [indexcmds.c#IndexSetParentIndex](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L3398-L3543)).
- **Detaching removes index-partition dependencies.** `ALTER TABLE ... DETACH PARTITION` calls `IndexSetParentIndex(idx, InvalidOid)`, deleting the `pg_inherits` row and both partition dependencies. A later parent-index drop no longer removes those indexes. Local constraint ownership still applies to direct drops ([tablecmds.c#detach-indexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L16327-L16351), [indexcmds.c#partition-dependencies](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L3508-L3538), [indexing.out#detach-then-drop](../../../../raw/postgres-12/src/test/regress/expected/indexing.out#L442-L523), [index.c#constraint-index-dependency](../../../../raw/postgres-12/src/backend/catalog/index.c#L1888-L1896)).
- **Core table attachment matches or creates; it does not drop indexes.** This describes `AttachPartitionEnsureIndexes`, not arbitrary DDL issued by a utility hook or event trigger ([tablecmds.c#AttachPartitionEnsureIndexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15932-L16040), [utility.c#ProcessUtility-hook](../../../../raw/postgres-12/src/backend/tcop/utility.c#L350-L362), [utility.c#ddl-command-start](../../../../raw/postgres-12/src/backend/tcop/utility.c#L966-L975)). See [Can ALTER TABLE ... ATTACH PARTITION Drop Indexes in PostgreSQL 12?](attach-partition-index-drops.md).
- **Dump and restore still build leaf indexes.** For standalone partitioned indexes, `pg_get_indexdef` emits `ON ONLY` and `pg_dump` emits a post-data `ALTER INDEX ... ATTACH PARTITION` for each index-parent link. This gives separate leaf builds plus attachment work, not a physical build on the root. Equal elapsed restore cost is not established here ([ruleutils.c#ON-ONLY](../../../../raw/postgres-12/src/backend/utils/adt/ruleutils.c#L1287-L1298), [pg_dump.c#dumpIndexAttach](../../../../raw/postgres-12/src/bin/pg_dump/pg_dump.c#L16470-L16498)).

### The hybrid the documentation recommends

For a table that already has partitions, the documentation gives this workaround: create an invalid, storage-less parent index with `ON ONLY`, build each ordinary leaf's index with `CONCURRENTLY`, then attach valid indexes to complete the family. Multi-level trees need the corresponding intermediate partitioned indexes. An empty parent is the exception to the initial invalid state ([ddl.sgml#index-partitioning](../../../../raw/postgres-12/doc/src/sgml/ddl.sgml#L3973-L4009), [indexcmds.c#ON-ONLY-invalid](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L988-L998), [tablecmds.c#validatePartitionedIndex](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L16682-L16769)).

The `CREATE INDEX` reference also documents a different order: build matching leaf indexes concurrently **first**, then create the parent index without `ONLY` and let it adopt them. The final cascade is metadata-only if all matches exist, but still takes hierarchy-wide locks; this reduces their duration rather than removing them ([create_index.sgml#leaf-first-alternative](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L624-L631), [utility.c#prelock-index-hierarchy](../../../../raw/postgres-12/src/backend/tcop/utility.c#L1320-L1343), [indexcmds.c#adopt](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1114-L1176)).

Validation is `validatePartitionedIndex`: it counts valid attached children against `RelationGetPartitionDesc(parent)->nparts` and flips `indisvalid` only when they match, recursing upward for sub-partitioned hierarchies ([tablecmds.c#validatePartitionedIndex](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L16675-L16769)). Attaching an *invalid* child does not validate the parent ([indexing.out#validate-chain](../../../../raw/postgres-12/src/test/regress/expected/indexing.out#L400-L439)).

A skeleton for an existing one-level partitioned table, with the session-scoped guards this repository requires. The pinned documentation and grammar support the syntax; this block was not executed. Adjust timeouts to your build times and repeat the leaf steps for every partition ([ddl.sgml#index-partitioning](../../../../raw/postgres-12/doc/src/sgml/ddl.sgml#L3973-L4009), [gram.y#IndexStmt](../../../../raw/postgres-12/src/backend/parser/gram.y#L7341-L7367), [gram.y#index_partition_cmd](../../../../raw/postgres-12/src/backend/parser/gram.y#L2048-L2062)).

```sql
SET /* wiki_partitioned_index_rollout */ lock_timeout = '5s';
SET /* wiki_partitioned_index_rollout */ statement_timeout = '2h';

-- 1. Metadata-only: invalid parent, partitions untouched.
CREATE /* wiki_partitioned_index_rollout */ INDEX measurement_usls_idx
    ON ONLY measurement (unitsales);

-- 2. Per partition, writes stay available. Repeat for each partition.
CREATE /* wiki_partitioned_index_rollout */ INDEX CONCURRENTLY measurement_usls_200602_idx
    ON measurement_y2006m02 (unitsales);

-- 3. Metadata-only; the parent turns valid after the last attach.
ALTER /* wiki_partitioned_index_rollout */ INDEX measurement_usls_idx
    ATTACH PARTITION measurement_usls_200602_idx;
```

`CREATE INDEX CONCURRENTLY` cannot run inside a transaction block — `ProcessUtilitySlow` calls `PreventInTransactionBlock(isTopLevel, "CREATE INDEX CONCURRENTLY")` for any `IndexStmt` with `concurrent` set ([utility.c#T_IndexStmt](../../../../raw/postgres-12/src/backend/tcop/utility.c#L1301-L1310)) — so step 2 must be its own statement per partition. The step-by-step lock and wait behavior of that command is on [How CREATE INDEX CONCURRENTLY Is Implemented in PostgreSQL 12](create-index-concurrently.md).

Three caveats at the v12 pin:

- Once the parent index exists, even invalid, any partition created by `CREATE TABLE ... PARTITION OF` gets a matching index immediately and non-concurrently, because `RelationGetIndexList` returns invalid indexes too ([relcache.c#RelationGetIndexList](../../../../raw/postgres-12/src/backend/utils/cache/relcache.c#L4384-L4398), [ddl.sgml#index-partitioning](../../../../raw/postgres-12/doc/src/sgml/ddl.sgml#L3973-L4009)). The `ONLY` escape covers existing partitions, not future ones.
- The same applies to `ATTACH PARTITION`: `AttachPartitionEnsureIndexes` does not check the parent index's validity before enforcing coverage ([tablecmds.c#AttachPartitionEnsureIndexes](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15932-L15953)).
- Check candidate leaf indexes before table attachment: the match path can adopt an invalid one without invalidating an already-valid parent, unlike cascading creation. The source-derived case and its limits are described under [Maintenance and lifecycle differences](#maintenance-and-lifecycle-differences) ([tablecmds.c#attach-existing-index](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15967-L16040), [indexcmds.c#adopt-invalid-child](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1156-L1164)).

### Settings that matter

Lock-table capacity is the configuration concern directly affected by putting all partition builds in one transaction.

| GUC | Why it matters here | Context and apply scope |
|---|---|---|
| `max_locks_per_transaction` | The parent cascade holds one relation lock per partition plus one per created index in a single transaction; the per-partition design spreads them over separate transactions. The shared lock table is sized as `max_locks_per_transaction * (MaxBackends + max_prepared_xacts)` ([lock.c#NLOCKENTS](../../../../raw/postgres-12/src/backend/storage/lmgr/lock.c#L53-L57)) | Default 64, `PGC_POSTMASTER` — **requires a restart** ([guc.c#max_locks_per_transaction](../../../../raw/postgres-12/src/backend/utils/misc/guc.c#L2463-L2473)) |

`statement_timeout` and `lock_timeout` are both `PGC_USERSET` and default to 0, so they take session or transaction scope with no reload or restart ([guc.c#statement_timeout](../../../../raw/postgres-12/src/backend/utils/misc/guc.c#L2377-L2386), [guc.c#lock_timeout](../../../../raw/postgres-12/src/backend/utils/misc/guc.c#L2388-L2397)). Their exact behavior around index builds and lock waits is tabulated on [How CREATE INDEX CONCURRENTLY Is Implemented in PostgreSQL 12](create-index-concurrently.md). `enable_partition_pruning` is not an index setting — pruning does not consult indexes at all ([ddl.sgml#pruning-and-indexes](../../../../raw/postgres-12/doc/src/sgml/ddl.sgml#L4541-L4549)).

**Build and includes.** The catalog headers include generated `*_d.h` files. The catalog Makefile lists `pg_class.h`, `pg_index.h` and `pg_inherits.h` as inputs to `genbki.pl` and produces their generated headers plus `schemapg.h`. Reverse include users include both DDL (`indexcmds.c`) and routing (`execPartition.c`), which include `pg_inherits.h` and `partdesc.h` ([pg_index.h#includes](../../../../raw/postgres-12/src/include/catalog/pg_index.h#L21-L29), [pg_inherits.h#includes](../../../../raw/postgres-12/src/include/catalog/pg_inherits.h#L21-L32), [catalog/Makefile#generated-headers](../../../../raw/postgres-12/src/backend/catalog/Makefile#L28-L101), [parser/Makefile#gram-header](../../../../raw/postgres-12/src/backend/parser/Makefile#L24-L48), [indexcmds.c#includes](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L18-L50), [execPartition.c#includes](../../../../raw/postgres-12/src/backend/executor/execPartition.c#L16-L29)).

**Extension boundary.** These are core paths. A loaded `ProcessUtility_hook` can intercept the utility command; complete commands also invoke DDL event triggers before the switch. Physical builds cross into the chosen access method via `ambuild`. This page does not generalize core match-or-create behavior to arbitrary hook, event-trigger, or custom access-method code. Foreign-table partitions are also outside the ordinary-leaf comparison: core skips them for plain index cascades and rejects them for unique ones ([utility.c#ProcessUtility-hook](../../../../raw/postgres-12/src/backend/tcop/utility.c#L350-L362), [utility.c#ddl-command-start](../../../../raw/postgres-12/src/backend/tcop/utility.c#L966-L975), [index.c#ambuild](../../../../raw/postgres-12/src/backend/catalog/index.c#L2899-L2904), [indexcmds.c#foreign-partition](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1088-L1105)).

## Open Questions

- **Unmeasured lock waits.** Hierarchy pre-locking and lock retention establish writer exclusion after the cascade obtains its locks, but no concurrent-writer experiment was run. A two-session isolation test should distinguish waiting to acquire the hierarchy locks from the interval after all are held ([utility.c#prelock-index-hierarchy](../../../../raw/postgres-12/src/backend/tcop/utility.c#L1320-L1373), [indexcmds.c#keep-lock](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1167-L1176), [lock.c#LockConflicts](../../../../raw/postgres-12/src/backend/storage/lmgr/lock.c#L73-L87)).
- **Storage-less size-function result.** `pg_relation_size()` on a partitioned index was not observed. The no-storage result follows from the relkind and drop paths, but this page does not claim a measured scalar return from `calculate_relation_size` for it ([dbsize.c#pg_relation_size](../../../../raw/postgres-12/src/backend/utils/adt/dbsize.c#L310-L335), [dbsize.c#pg_relation_filenode](../../../../raw/postgres-12/src/backend/utils/adt/dbsize.c#L877-L896), [index.c#drop-storage](../../../../raw/postgres-12/src/backend/catalog/index.c#L2199-L2203)).
- **Unquantified index-opening work.** Benchmark planning separately from execution, and parent-targeted `INSERT` separately from leaf-targeted `UPDATE`. The source establishes the different paths, not their elapsed cost ([plancat.c#index-open-before-skip](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L193-L220), [nodeModifyTable.c#result-targets](../../../../raw/postgres-12/src/backend/executor/nodeModifyTable.c#L2293-L2349), [planner.c#resultRelations](../../../../raw/postgres-12/src/backend/optimizer/plan/planner.c#L1678-L1685)).
- **Invalid-leaf attachment needs a runtime fixture.** The source-derived edge case above has not been exercised. A fixture should compare cascading creation with table attachment, record parent/child valid and ready flags, and inspect leaf scan eligibility after adopting a matching invalid index ([tablecmds.c#attach-existing-index](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L15967-L16040), [indexcmds.c#adopt-invalid-child](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1156-L1164), [pg_index.h#state-flags](../../../../raw/postgres-12/src/include/catalog/pg_index.h#L35-L43)).
- **Documentation omits the empty-parent exception.** `create_index.sgml` says `ONLY` marks the index invalid without a qualification; `DefineIndex` sets that flag only if `nparts != 0`. This page follows the implementation ([create_index.sgml#ONLY](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L682-L689), [indexcmds.c#ON-ONLY-invalid](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L988-L998)).
- **Other majors are outside this review.** At this pin, family-level `REINDEX` is unsupported, index-partition grammar has only `ATTACH`, and table-partition `DETACH` has no `CONCURRENTLY` clause. Any comparison with another major requires that major's pinned evidence; no claim is made here about later support ([indexcmds.c#ReindexPartitionedIndex](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L3384-L3396), [index.c#reindex_relation-skip](../../../../raw/postgres-12/src/backend/catalog/index.c#L3686-L3700), [gram.y#partition-commands](../../../../raw/postgres-12/src/backend/parser/gram.y#L2019-L2062)).
