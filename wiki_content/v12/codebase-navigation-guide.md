## Answer

Use the PostgreSQL 12 tree as a set of entry points, not as one flat C program. Start with the build maps, then follow a statement through the frontend protocol, `tcop` (the traffic cop), parser, analyzer, rewriter, [planner](../glossary.md#planner), [portal](../glossary.md#portal), [executor](../glossary.md#executor), [access methods](../glossary.md#access-method), and command code [postgres.c#traffic-cop](../../raw/postgres-12/src/backend/tcop/postgres.c#L13-L16). The top-level `src/Makefile` lists the main source families, including `common`, `port`, `timezone`, `backend`, the separately built conversion-procedure and Snowball directories, `include`, `interfaces`, `fe_utils`, `bin`, procedural languages, and test directories [src/Makefile#SUBDIRS](../../raw/postgres-12/src/Makefile#L15-L32). The backend makefile narrows the server into subsystems such as `access`, `bootstrap`, `catalog`, `parser`, `commands`, `executor`, `optimizer`, `partitioning`, `postmaster`, `replication`, `rewrite`, `statistics`, `storage`, `tcop`, `utils`, and `jit` [backend/Makefile#SUBDIRS](../../raw/postgres-12/src/backend/Makefile#L20-L24).

### SQL Statement Path

1. A normal client backend reaches `PostgresMain()` from `BackendRun()`; `postgres --single` reaches it directly from `main()` [postmaster.c#BackendRun](../../raw/postgres-12/src/backend/postmaster/postmaster.c#L4378-L4438) [main.c#main-dispatch](../../raw/postgres-12/src/backend/main/main.c#L219-L228). `PostgresMain()` initializes standalone state when needed, processes backend switches and standalone configuration, installs signal handlers, initializes the backend with `InitPostgres()`, and enters normal processing [postgres.c#PostgresMain-startup](../../raw/postgres-12/src/backend/tcop/postgres.c#L3707-L3750) [postgres.c#PostgresMain-signals](../../raw/postgres-12/src/backend/tcop/postgres.c#L3752-L3813) [postgres.c#PostgresMain-InitPostgres](../../raw/postgres-12/src/backend/tcop/postgres.c#L3840-L3885).

2. `PostgresMain()` dispatches a simple-query (`Q`) message to `exec_simple_query()` [postgres.c#PostgresMain-simple-query](../../raw/postgres-12/src/backend/tcop/postgres.c#L4231-L4249). That path starts a transaction command, drops any previous unnamed statement, switches to `MessageContext`, calls `pg_parse_query()`, and loops over the returned raw statements [postgres.c#exec_simple_query-parse](../../raw/postgres-12/src/backend/tcop/postgres.c#L978-L1038) [postgres.c#exec_simple_query-loop](../../raw/postgres-12/src/backend/tcop/postgres.c#L1054-L1077). For each statement for which `analyze_requires_snapshot()` returns true, it pushes a transaction snapshot, performs analysis, rewrite, and planning, and then pops that snapshot [postgres.c#exec_simple_query-analyze-plan](../../raw/postgres-12/src/backend/tcop/postgres.c#L1123-L1148).

3. Extended-query protocol messages take the prepared-statement path. `PostgresMain()` dispatches Parse to `exec_parse_message()`, Bind to `exec_bind_message()`, and Execute to `exec_execute_message()` [postgres.c#PostgresMain-extended-protocol](../../raw/postgres-12/src/backend/tcop/postgres.c#L4253-L4309). Parse accepts at most one user statement, creates a `CachedPlanSource`, performs parameter-aware analysis and rewrite, completes that source, and stores either the named or unnamed source [postgres.c#exec_parse_message](../../raw/postgres-12/src/backend/tcop/postgres.c#L1314-L1527). Bind fetches that source, decodes parameter values, obtains a `CachedPlan`, defines a portal, and starts it [postgres.c#exec_bind_message](../../raw/postgres-12/src/backend/tcop/postgres.c#L1576-L1898). Execute retrieves the portal and calls `PortalRun()` [postgres.c#exec_execute_message](../../raw/postgres-12/src/backend/tcop/postgres.c#L1946-L2096). Parse itself leaves the transaction command open; Sync later calls `finish_xact_command()` to close any command that remains open [postgres.c#exec_parse_message-Sync-boundary](../../raw/postgres-12/src/backend/tcop/postgres.c#L1531-L1536) [postgres.c#PostgresMain-Sync](../../raw/postgres-12/src/backend/tcop/postgres.c#L4427-L4430).

4. Raw parsing is deliberately separate from analysis and rewrite because analysis and rewrite need [catalog](../glossary.md#catalog) access, while the raw parser must still identify transaction-control commands in an aborted transaction [postgres.c#pg_parse_query](../../raw/postgres-12/src/backend/tcop/postgres.c#L618-L668). The parser driver says grammar output is a raw parse tree that still needs analysis by `analyze.c`; `raw_parser()` initializes the Flex scanner and Bison parser, calls `base_yyparse()`, and returns a list of `RawStmt` nodes [parser.c#raw_parser-design](../../raw/postgres-12/src/backend/parser/parser.c#L3-L10) [parser.c#raw_parser](../../raw/postgres-12/src/backend/parser/parser.c#L28-L62).

5. Parse analysis turns a `RawStmt` into a `Query`. `parse_analyze()` builds a `ParseState`, records source text and the query environment, installs fixed parameters when supplied, calls `transformTopLevelStmt()`, invokes `post_parse_analyze_hook` if set, and returns a `Query` [analyze.c#parse_analyze](../../raw/postgres-12/src/backend/parser/analyze.c#L88-L124). `RawStmt` comments state that utility statements usually move the raw tree into `Query.utilityStmt` and perform useful work at execution time [parsenodes.h#RawStmt](../../raw/postgres-12/src/include/nodes/parsenodes.h#L1470-L1488).

6. Rewrite happens after analysis. `pg_analyze_and_rewrite()` calls `parse_analyze()` and then `pg_rewrite_query()` [postgres.c#pg_analyze_and_rewrite](../../raw/postgres-12/src/backend/tcop/postgres.c#L670-L709). `pg_rewrite_query()` sends regular queries to `QueryRewrite()` but leaves utility queries in a one-item list [postgres.c#pg_rewrite_query](../../raw/postgres-12/src/backend/tcop/postgres.c#L762-L789). `QueryRewrite()` applies non-SELECT rules and then RIR rules, preserving the input query ID on each rewritten query; RIR means “Retrieve-Instead-Retrieve,” an `ON SELECT DO INSTEAD SELECT` rule [rewriteHandler.c#RIR](../../raw/postgres-12/src/backend/rewrite/rewriteHandler.c#L11-L17) [rewriteHandler.c#QueryRewrite](../../raw/postgres-12/src/backend/rewrite/rewriteHandler.c#L3913-L3963).

7. Planning starts after rewrite. `pg_plan_queries()` wraps utility queries in a `PlannedStmt` without optimizer planning, while normal statements call `pg_plan_query()` [postgres.c#pg_plan_queries](../../raw/postgres-12/src/backend/tcop/postgres.c#L937-L975). `pg_plan_query()` returns `NULL` for utility input, requires an active snapshot for a normal query, and calls `planner()` for optimizer work [postgres.c#pg_plan_query](../../raw/postgres-12/src/backend/tcop/postgres.c#L856-L879). `planner()` uses `planner_hook` when installed and otherwise calls `standard_planner()` [planner.c#planner](../../raw/postgres-12/src/backend/optimizer/plan/planner.c#L254-L280).

8. The planner builds global and per-query state. For a normal join-tree query, it computes relation sizes, builds base and join paths, chooses a cheapest path for the requested tuple fraction, and converts the selected `Path` tree into a `Plan` tree. `standard_planner()` creates `PlannerGlobal`, calls `subquery_planner()`, selects a path from the final upper relation, and calls `create_plan()` [planner.c#standard_planner-global-state](../../raw/postgres-12/src/backend/optimizer/plan/planner.c#L280-L317) [planner.c#standard_planner-best-path](../../raw/postgres-12/src/backend/optimizer/plan/planner.c#L405-L413). `subquery_planner()` creates a `PlannerInfo`, handles CTEs, replaces empty jointrees, pulls up sublinks and subqueries, and flattens simple `UNION ALL` queries when possible [planner.c#subquery_planner-start](../../raw/postgres-12/src/backend/optimizer/plan/planner.c#L567-L680). `make_one_rel()` computes base-relation sizes and pathlists before building the join relation [allpaths.c#make_one_rel](../../raw/postgres-12/src/backend/optimizer/path/allpaths.c#L150-L235). `create_plan()` calls `create_plan_recurse()`, whose path-node switch dispatches scans, joins, append variants, results, aggregates, modification, and other path types to plan builders [createplan.c#create_plan](../../raw/postgres-12/src/backend/optimizer/plan/createplan.c#L297-L357) [createplan.c#create_plan_recurse](../../raw/postgres-12/src/backend/optimizer/plan/createplan.c#L359-L517).

9. Execution is portal-driven. `exec_simple_query()` creates an unnamed portal, defines it with the planned statement list, starts it, creates a destination receiver, and calls `PortalRun()` to completion [postgres.c#exec_simple_query-portal](../../raw/postgres-12/src/backend/tcop/postgres.c#L1153-L1222). `PortalStart()` chooses one of five strategies and starts the executor immediately for `PORTAL_ONE_SELECT`; the strategy definitions distinguish a single SELECT, `RETURNING`, a data-modifying CTE, a SELECT-like utility, and the general multi-query case [pquery.c#PortalStart](../../raw/postgres-12/src/backend/tcop/pquery.c#L420-L545) [portal.h#PortalStrategy](../../raw/postgres-12/src/include/utils/portal.h#L54-L95). `PortalRun()` marks the portal active, dispatches result-style strategies through `PortalRunSelect()` and the general strategy through `PortalRunMulti()`, and restores portal/resource-owner state [pquery.c#PortalRun](../../raw/postgres-12/src/backend/tcop/pquery.c#L662-L850). For an active SELECT executor, `PortalRunSelect()` pushes the query snapshot, calls `ExecutorRun()`, records the processed count, and pops the snapshot [pquery.c#PortalRunSelect](../../raw/postgres-12/src/backend/tcop/pquery.c#L871-L933).

10. The executor lifecycle has start, run, finish, and end phases, and each phase exposes a [hook](../glossary.md#hook) [executor.h#executor-hooks](../../raw/postgres-12/src/include/executor/executor.h#L63-L80). `standard_ExecutorStart()` creates `EState`, records external parameters, registers [snapshots](../glossary.md#snapshot), starts an AFTER-trigger context when needed, and initializes the plan-state tree [execMain.c#standard_ExecutorStart](../../raw/postgres-12/src/backend/executor/execMain.c#L151-L269). `standard_ExecutorRun()` calls `ExecutePlan()` unless the direction is `NoMovementScanDirection` [execMain.c#ExecutorRun](../../raw/postgres-12/src/backend/executor/execMain.c#L271-L385). `standard_ExecutorFinish()` post-processes the plan and fires queued AFTER triggers; `standard_ExecutorEnd()` ends the plan, unregisters snapshots, and frees `EState` plus its per-query context [execMain.c#ExecutorFinish](../../raw/postgres-12/src/backend/executor/execMain.c#L387-L447) [execMain.c#ExecutorEnd](../../raw/postgres-12/src/backend/executor/execMain.c#L449-L518). `ProcessQuery()` invokes all four phases for a run-to-completion query, while a single-SELECT portal defers finish/end to `PortalCleanup()` when the portal is dropped [pquery.c#ProcessQuery](../../raw/postgres-12/src/backend/tcop/pquery.c#L119-L207) [portalcmds.c#PortalCleanup](../../raw/postgres-12/src/backend/commands/portalcmds.c#L254-L306).

11. [Utility statements](../glossary.md#utility-command) are wrapped but not optimized into normal executor plans. `PortalRunMulti()` sends a utility `PlannedStmt` to `PortalRunUtility()`, which establishes a snapshot when the command class requires one and calls `ProcessUtility()` with top-level or query context [pquery.c#PortalRunMulti-utility](../../raw/postgres-12/src/backend/tcop/pquery.c#L1304-L1330) [pquery.c#PortalRunUtility](../../raw/postgres-12/src/backend/tcop/pquery.c#L1130-L1194). `ProcessUtility()` asserts `CMD_UTILITY`, exposes `ProcessUtility_hook`, and otherwise calls `standard_ProcessUtility()` [utility.c#ProcessUtility](../../raw/postgres-12/src/backend/tcop/utility.c#L320-L363). `standard_ProcessUtility()` directly handles commands without event-trigger support and sends supported commands to `ProcessUtilitySlow()`; some object-generic statements use `EventTriggerSupportsObjectType()` to choose the branch [utility.c#standard_ProcessUtility-design](../../raw/postgres-12/src/backend/tcop/utility.c#L365-L375) [utility.c#standard_ProcessUtility-event-trigger-split](../../raw/postgres-12/src/backend/tcop/utility.c#L816-L930). Direct cases include `EXPLAIN` and `SET`, while the slow path routes `CREATE TABLE` through `transformCreateStmt()` and `DefineRelation()`, `ALTER TABLE` through `transformAlterTableStmt()`/`AlterTable()`, and `CREATE INDEX` through `transformIndexStmt()` and `DefineIndex()` [utility.c#standard_ProcessUtility-Explain-Set](../../raw/postgres-12/src/backend/tcop/utility.c#L674-L686) [utility.c#ProcessUtilitySlow-CreateStmt](../../raw/postgres-12/src/backend/tcop/utility.c#L993-L1086) [utility.c#ProcessUtilitySlow-AlterTableStmt](../../raw/postgres-12/src/backend/tcop/utility.c#L1096-L1179) [utility.c#ProcessUtilitySlow-IndexStmt](../../raw/postgres-12/src/backend/tcop/utility.c#L1301-L1393).

12. Error and edge paths often explain control flow. In aborted transaction state, the simple path rejects every command except a transaction-exit statement before analysis, rewrite, or planning; Parse, Bind, and Execute have corresponding guards [postgres.c#aborted-transaction-check](../../raw/postgres-12/src/backend/tcop/postgres.c#L1091-L1105) [postgres.c#exec_parse_message-abort-check](../../raw/postgres-12/src/backend/tcop/postgres.c#L1414-L1428) [postgres.c#exec_bind_message-abort-check](../../raw/postgres-12/src/backend/tcop/postgres.c#L1670-L1686) [postgres.c#exec_execute_message-abort-check](../../raw/postgres-12/src/backend/tcop/postgres.c#L2069-L2079). An execution error makes `PortalRun()` mark the portal failed before rethrowing; `PortalCleanup()` then avoids calling executor shutdown code on that failed portal because transaction abort releases the resources [pquery.c#PortalRun-error](../../raw/postgres-12/src/backend/tcop/pquery.c#L743-L831) [portalcmds.c#PortalCleanup-failed](../../raw/postgres-12/src/backend/commands/portalcmds.c#L260-L305). The outer `PostgresMain()` recovery path reports the error, aborts the current transaction, cleans portal/SPI/replication-slot state, and makes an extended-protocol error skip messages until Sync; loss of framing while reading a message is fatal [postgres.c#PostgresMain-error-recovery](../../raw/postgres-12/src/backend/tcop/postgres.c#L3973-L4077). Utility dispatch applies read-only/parallel checks, while `CLUSTER`, `VACUUM`, and `ANALYZE` explicitly reject recovery before command-specific work [utility.c#check_xact_readonly](../../raw/postgres-12/src/backend/tcop/utility.c#L127-L229) [utility.c#Cluster-Vacuum](../../raw/postgres-12/src/backend/tcop/utility.c#L651-L671). Server code reports messages with `ereport()` or `elog()`; `ereport()` carries a severity and elements such as SQLSTATE and `errmsg()` [sources.sgml#error-reporting](../../raw/postgres-12/doc/src/sgml/sources.sgml#L83-L127). `errcodes.txt` drives generated C macros and documentation tables [errcodes.txt#generated-files](../../raw/postgres-12/src/backend/utils/errcodes.txt#L7-L35).

### Generated And Catalog Files

Treat generated files as source-driven artifacts, not independent sources of truth. The backend `generated-headers` target builds or links parser [grammar](../glossary.md#grammar), fixed-LWLock-name, catalog, and utility headers into the build include tree. Its `distprep` target also drives parser, bootstrap, replication-grammar, JSONPath, GUC scanner, and tuple-sort generators [backend/Makefile#generated-headers](../../raw/postgres-12/src/backend/Makefile#L123-L172) [backend/Makefile#distprep](../../raw/postgres-12/src/backend/Makefile#L180-L190). Several subtree makefiles say generated parser/scanner outputs are shipped in distribution tarballs, so a raw Git checkout and a release tarball need not expose the same generated files before a build or `distprep` [parser/Makefile#distributed-generated-files](../../raw/postgres-12/src/backend/parser/Makefile#L24-L54) [bootstrap/Makefile#distributed-generated-files](../../raw/postgres-12/src/backend/bootstrap/Makefile#L19-L23) [replication/Makefile#distributed-generated-files](../../raw/postgres-12/src/backend/replication/Makefile#L24-L32).

System catalogs start in `src/include/catalog/*.h` and selected `.dat` files. `src/backend/catalog/Makefile` declares the ordered catalog header list, requires bootstrap catalogs first, defines generated `_d.h` headers plus `schemapg.h`, places `toasting.h` and `indexing.h` after catalog definitions, and invokes `genbki.pl` over those headers and data files [catalog/Makefile#catalog-generation](../../raw/postgres-12/src/backend/catalog/Makefile#L28-L101). `genbki.h` makes `CATALOG()` and related annotations compile as C while documenting that `genbki.pl` recognizes the same words [genbki.h#CATALOG](../../raw/postgres-12/src/include/catalog/genbki.h#L1-L64). `genbki.pl` generates BKI and symbol-definition headers; the BKI initializes the `postgres` template database [genbki.pl#usage](../../raw/postgres-12/src/backend/catalog/genbki.pl#L960-L974). For a concrete dependency, `pg_index.h` includes generated `pg_index_d.h` before declaring `FormData_pg_index`, and `rel.h` then includes `pg_index.h` for its relcache fields [pg_index.h#generated-header-and-CATALOG](../../raw/postgres-12/src/include/catalog/pg_index.h#L18-L66) [rel.h#pg_index-include](../../raw/postgres-12/src/include/utils/rel.h#L14-L28).

Catalog indexes are not ordinary handwritten SQL files. `indexing.h` says `DECLARE_INDEX` and `DECLARE_UNIQUE_INDEX` lines become statements that the bootstrap parser turns into `DefineIndex()` calls, and C code should use the generated OID macros rather than literal index names or numbers [indexing.h#DECLARE_INDEX](../../raw/postgres-12/src/include/catalog/indexing.h#L47-L74).

Parser generated files come from Bison and Flex. The parser makefile builds `gram.o`/`scan.o`, makes `gram.h` the secondary output of `gram.c`, adds `-d` so Bison emits the header, and gives the scanner Flex flags; the global pattern rules perform the Bison/Flex invocations [parser/Makefile#parser-generated-files](../../raw/postgres-12/src/backend/parser/Makefile#L13-L54) [Makefile.global.in#Bison-Flex-rules](../../raw/postgres-12/src/Makefile.global.in#L728-L747). `gramparse.h` is a reverse include user of generated `parser/gram.h` [gramparse.h#gram.h](../../raw/postgres-12/src/include/parser/gramparse.h#L20-L35).

Utility generated headers include function-manager lookup files, error codes, DTrace probes, and fixed [LWLock](../glossary.md#lwlock) names. `Gen_fmgrtab.pl` generates `fmgroids.h`, `fmgrprotos.h`, and `fmgrtab.c` from `pg_proc.dat`; the utils makefile drives it, generates `errcodes.h`, and generates or stubs `probes.h` according to DTrace support [Gen_fmgrtab.pl#outputs](../../raw/postgres-12/src/backend/utils/Gen_fmgrtab.pl#L1-L7) [utils/Makefile#generated-files](../../raw/postgres-12/src/backend/utils/Makefile#L24-L76). The lock-manager makefile generates `lwlocknames.h` and `lwlocknames.c`, and `lwlock.h` includes the generated header [lmgr/Makefile#lwlocknames](../../raw/postgres-12/src/backend/storage/lmgr/Makefile#L28-L42) [lwlock.h#lwlocknames.h](../../raw/postgres-12/src/include/storage/lwlock.h#L90-L104). `src/include/Makefile` installs generated server headers including the function/error headers and, for VPATH builds, catalog `_d.h`, parser, LWLock, and probe headers [include/Makefile#generated-install](../../raw/postgres-12/src/include/Makefile#L43-L60).

[Memory contexts](../glossary.md#memory-context) are central to PostgreSQL navigation.
