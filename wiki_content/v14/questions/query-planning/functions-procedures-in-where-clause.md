## Question

In a statement execution that has functions or procedures used in the WHERE clause, what are the performance implications, and what can be done to minimize the overhead of calling functions or procedures in the statement's WHERE clause?

> Prompt note: this is a grammar-corrected restatement of the original request, applied with the asker's approval per the wiki's prompt-hygiene rule.

## Answer

### Short answer

A PostgreSQL 14 procedure cannot be part of a `WHERE` expression. `CREATE PROCEDURE` records `pg_proc.prokind = 'p'`; ordinary expression resolution rejects that routine kind and directs the caller to `CALL` [functioncmds.c#CreateFunction](../../../../raw/postgres-14/src/backend/commands/functioncmds.c#L1285-L1305) [pg_proc.c#ProcedureCreate](../../../../raw/postgres-14/src/backend/catalog/pg_proc.c#L303-L315) [parse_func.c#wrong-routine-kind](../../../../raw/postgres-14/src/backend/parser/parse_func.c#L275-L302). The performance question therefore concerns scalar functions. A set-returning function is not a second `WHERE` case: parse analysis rejects it in `EXPR_KIND_WHERE` [analyze.c#transformSelectStmt-WHERE](../../../../raw/postgres-14/src/backend/parser/analyze.c#L1328-L1334) [parse_func.c#check_srf_call_placement](../../../../raw/postgres-14/src/backend/parser/parse_func.c#L2555-L2582) [parse_func.c#EXPR_KIND_WHERE](../../../../raw/postgres-14/src/backend/parser/parse_func.c#L2605-L2620). Aggregates and window functions are also rejected in `WHERE` at their own query level, so they are not scalar-qual call cases either [parse_agg.c#aggregate-WHERE](../../../../raw/postgres-14/src/backend/parser/parse_agg.c#L380-L410) [parse_agg.c#window-WHERE](../../../../raw/postgres-14/src/backend/parser/parse_agg.c#L900-L923).

A fourth class is rejected in every expression context, `WHERE` included. `ParseFuncOrColumn` refuses any call whose resolved argument types or result type is `internal`, raising `ERRCODE_FEATURE_NOT_SUPPORTED` with `functions accepting type "internal" cannot be called explicitly` or `functions returning type "internal" cannot be called explicitly`. The check runs after `func_get_detail` has resolved the routine and before `make_fn_arguments` coerces the arguments, and its comment records that the `FUNCDETAIL_COERCION` path returns earlier and is therefore exempt [parse_func.c#internal-type-rejection](../../../../raw/postgres-14/src/backend/parser/parse_func.c#L675-L700). Commit `155dacbc547` (CVE-2026-14680) added it, and the same commit closes the two adjacent routes: `make_op` applies the identical test to operator syntax, and `can_coerce_type`/`find_coercion_pathway` reject casts to or from `internal` [parse_oper.c#internal-type-rejection](../../../../raw/postgres-14/src/backend/parser/parse_oper.c#L752-L772) [parse_coerce.c#can_coerce_type](../../../../raw/postgres-14/src/backend/parser/parse_coerce.c#L574-L576) [parse_coerce.c#find_coercion_pathway](../../../../raw/postgres-14/src/backend/parser/parse_coerce.c#L3157-L3159).

For a scalar function, **plan placement determines call count**. A non-indexable, row-dependent residual qualification (`qual`)—an executor Boolean filter left after specialized path conditions—is evaluated for every candidate tuple that reaches it; a join qual can instead be evaluated for candidate tuple pairs [pathnodes.h#RestrictInfo-placement](../../../../raw/postgres-14/src/include/nodes/pathnodes.h#L2012-L2021) [execScan.c#ExecScan](../../../../raw/postgres-14/src/backend/executor/execScan.c#L198-L245) [nodeNestloop.c#ExecNestLoop-quals](../../../../raw/postgres-14/src/backend/executor/nodeNestloop.c#L204-L247). That does not always mean one function-body invocation per tuple: an earlier false/null qual can short-circuit the expression, a `STRICT` function is skipped on a null argument, a simple SQL function can be inlined, an `IMMUTABLE` call with constant inputs can be folded during planning, and an expression index can avoid recomputing the expression during the indexed search [execExpr.c#ExecInitQual](../../../../raw/postgres-14/src/backend/executor/execExpr.c#L194-L283) [execExprInterp.c#function-opcodes](../../../../raw/postgres-14/src/backend/executor/execExprInterp.c#L715-L778) [clauses.c#evaluate_function](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4298-L4357) [clauses.c#inline_function](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4360-L4389) [indices.sgml#expression-indexes](../../../../raw/postgres-14/doc/src/sgml/indices.sgml#L785-L795).

The highest-leverage remedies are to reduce the candidate tuples or pairs before the residual function runs, make a frequently searched immutable result indexable or precomputed, and move a genuinely row-independent call to a one-time mechanism. Then use truthful `STRICT`, volatility, `COST`, planner-support, leakproofness, and parallel-safety metadata; inline simple SQL functions; and consider just-in-time (JIT) compilation only for sufficiently long CPU-bound queries [createplan.c#order_qual_clauses](../../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L5191-L5223) [indxpath.c#match_index_to_operand](../../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L3737-L3813) [subselect.c#uncorrelated-EXPR-initplan](../../../../raw/postgres-14/src/backend/optimizer/plan/subselect.c#L375-L410) [create_function.sgml#STRICT-LEAKPROOF-PARALLEL](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L356-L459) [xfunc.sgml#volatility](../../../../raw/postgres-14/doc/src/sgml/xfunc.sgml#L1624-L1671) [create_function.sgml#COST-and-SUPPORT](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L462-L502) [jit.sgml#when-to-JIT](../../../../raw/postgres-14/doc/src/sgml/jit.sgml#L95-L129).

### Procedures cannot appear in a WHERE clause

`CREATE PROCEDURE` passes `PROKIND_PROCEDURE` to `ProcedureCreate`, which stores that value in `pg_proc.prokind` [functioncmds.c#CreateFunction](../../../../raw/postgres-14/src/backend/commands/functioncmds.c#L1285-L1305) [pg_proc.c#ProcedureCreate](../../../../raw/postgres-14/src/backend/catalog/pg_proc.c#L303-L315) [pg_proc.h#PROKIND](../../../../raw/postgres-14/src/include/catalog/pg_proc.h#L149-L153). Ordinary function-call syntax reaches `ParseFuncOrColumn` with `proc_call = false`; a resolved procedure then raises `ERRCODE_WRONG_OBJECT_TYPE` with the hint `To call a procedure, use CALL.` [parse_expr.c#transformFuncCall](../../../../raw/postgres-14/src/backend/parser/parse_expr.c#L1389-L1396) [parse_func.c#wrong-routine-kind](../../../../raw/postgres-14/src/backend/parser/parse_func.c#L275-L302). `transformCallStmt` is the path that passes `proc_call = true` [analyze.c#transformCallStmt](../../../../raw/postgres-14/src/backend/parser/analyze.c#L2993-L3027).

`CALL` is a utility statement. Utility queries get only a wrapper `PlannedStmt`, not an optimizer plan, and `standard_ProcessUtility` dispatches `T_CallStmt` to `ExecuteCallStmt` [postgres.c#pg_plan_queries](../../../../raw/postgres-14/src/backend/tcop/postgres.c#L874-L914) [utility.c#T_CallStmt](../../../../raw/postgres-14/src/backend/tcop/utility.c#L849-L851). The procedure invocation itself is a direct fmgr call, but `CALL` is not wholly outside expression evaluation: `ExecuteCallStmt` prepares and evaluates each argument expression before `FunctionCallInvoke` [functioncmds.c#ExecuteCallStmt-arguments](../../../../raw/postgres-14/src/backend/commands/functioncmds.c#L2271-L2313). Those standalone argument expressions use `ExecPrepareExpr`, which initializes an expression with no parent `PlanState`; `jit_compile_expr` declines such expressions [execExpr.c#ExecPrepareExpr](../../../../raw/postgres-14/src/backend/executor/execExpr.c#L722-L747) [jit.c#jit_compile_expr](../../../../raw/postgres-14/src/backend/jit/jit.c#L147-L179). The regression test covers both procedure rejection in `SELECT` and valid `CALL` arguments, including a volatile argument [create_procedure.out:52-60](../../../../raw/postgres-14/src/test/regress/expected/create_procedure.out#L52-L60).

### Where and how often a WHERE-clause function runs

The planner can implement a `WHERE` clause as an index qual, merge/hash join clause, or a general plan qual; clauses that specialized paths do not implement remain in general-purpose expression evaluation [pathnodes.h#RestrictInfo-placement](../../../../raw/postgres-14/src/include/nodes/pathnodes.h#L2012-L2021). For a residual scan qual, `ExecScan` fetches a tuple and calls `ExecQual`; a failed tuple is discarded and the loop fetches another [execScan.c#ExecScan](../../../../raw/postgres-14/src/backend/executor/execScan.c#L198-L245). For a nested-loop join, `ExecQual` can run on every candidate inner/outer pair, first for the join qual and then for the other qual [nodeNestloop.c#ExecNestLoop-quals](../../../../raw/postgres-14/src/backend/executor/nodeNestloop.c#L204-L247). Similar placement in another node changes the multiplicity, so “once per table row” is not a universal rule.

`ExecInitFunc` checks `EXECUTE` privilege, builds `FmgrInfo` and `FunctionCallInfo` state, compiles argument steps, and selects one of four opcodes according to strictness and function-statistics tracking [execExpr.c#ExecInitFunc](../../../../raw/postgres-14/src/backend/executor/execExpr.c#L2457-L2563). The ordinary opcode invokes the stored `fn_addr`; strict opcodes first test every argument and skip the call when any is null; tracking opcodes wrap the same work in function-usage accounting [execExprInterp.c#function-opcodes](../../../../raw/postgres-14/src/backend/executor/execExprInterp.c#L715-L778) [execExprInterp.c#function-usage-opcodes](../../../../raw/postgres-14/src/backend/executor/execExprInterp.c#L2365-L2418).

A top-level qual list has implicit `AND` semantics. `ExecInitQual` emits `EEOP_QUAL` after each element, and that opcode jumps to the end on false or null [execExpr.c#ExecInitQual](../../../../raw/postgres-14/src/backend/executor/execExpr.c#L194-L283) [execExprInterp.c#EEOP_QUAL](../../../../raw/postgres-14/src/backend/executor/execExprInterp.c#L928-L940). Do not rely on SQL text order to control side effects or call count: PostgreSQL does not define subexpression order, can omit unneeded subexpressions, and can reorganize Boolean expressions while planning [syntax.sgml#expression-evaluation-rules](../../../../raw/postgres-14/doc/src/sgml/syntax.sgml#L2453-L2491).

### Row-independent quals can be one-time filters

A qual with no current-query-level `Var` and no volatile function can become a pseudoconstant. `distribute_qual_to_rels` marks it and requests a gating plan; `create_gating_plan` pulls it into a `Result` node [initsplan.c#pseudoconstant-qual](../../../../raw/postgres-14/src/backend/optimizer/plan/initsplan.c#L1659-L1711) [createplan.c#create_gating_plan](../../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L973-L1038). `RestrictInfo.pseudoconstant` means no `Var` of the current query level and no volatile function; parameters and outer-level variables can remain, so the precise lifetime is one scan, not necessarily one statement [pathnodes.h#pseudoconstant](../../../../raw/postgres-14/src/include/nodes/pathnodes.h#L2035-L2043) [clauses.c#is_pseudo_constant_clause](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L1986-L2016).

`ExecResult` checks its `resconstantqual` once and then clears `rs_checkqual`; `ExecReScanResult` sets that flag again [nodeResult.c#ExecResult](../../../../raw/postgres-14/src/backend/executor/nodeResult.c#L79-L92) [nodeResult.c#ExecReScanResult](../../../../raw/postgres-14/src/backend/executor/nodeResult.c#L259-L264). Thus a top-level no-`Var` `STABLE` qual is normally a one-time filter for that execution, while the same node inside a rescanned correlated plan is checked once per rescan. The planner also moves a pseudoconstant's per-tuple expression cost into startup cost [costsize.c#pseudoconstant-cost](../../../../raw/postgres-14/src/backend/optimizer/path/costsize.c#L4394-L4404). An `IMMUTABLE` call whose arguments are all constants can disappear even earlier through constant folding. `VOLATILE` prevents pseudoconstant gating and ordinary all-constant folding; the separate strict constant-null fold described below is an exception [clauses.c#evaluate_function](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4298-L4357).

### How volatility changes what the executor and planner can do

A function's `pg_proc.provolatile` value is a promise to the optimizer [pg_proc.h#PROVOLATILE](../../../../raw/postgres-14/src/include/catalog/pg_proc.h#L155-L165). `CREATE FUNCTION` defaults to `VOLATILE` [xfunc.sgml#volatility](../../../../raw/postgres-14/doc/src/sgml/xfunc.sgml#L1624-L1639).

- **`VOLATILE`** permits changing results and side effects, so PostgreSQL re-evaluates the function at each row where its value is needed [xfunc.sgml#VOLATILE](../../../../raw/postgres-14/doc/src/sgml/xfunc.sgml#L1633-L1640). It prevents pseudoconstant gating and cannot be on the non-index side of an ordinary index comparison [initsplan.c#pseudoconstant-qual](../../../../raw/postgres-14/src/backend/optimizer/plan/initsplan.c#L1666-L1701) [indxpath.c#match_opclause_to_indexcol](../../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L2495-L2535).
- **`STABLE`** promises one result for equal arguments within a statement. It does not memoize `stable_fn(col)` across rows, but it can be used as a non-index comparison value evaluated once per index scan or rescan, and a no-current-level-`Var` qual can use the gating path above [xfunc.sgml#STABLE](../../../../raw/postgres-14/doc/src/sgml/xfunc.sgml#L1642-L1652) [nodeIndexscan.c#ExecReScanIndexScan](../../../../raw/postgres-14/src/backend/executor/nodeIndexscan.c#L542-L593). During selectivity estimation only, the planner may evaluate an all-constant `STABLE` call; this estimate-time value does not replace the execution expression [clauses.c#evaluate_function](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4318-L4357).
- **`IMMUTABLE`** promises the same result forever for equal arguments. If every input is constant, the planner can evaluate it while creating the plan and replace it with a `Const` [xfunc.sgml#IMMUTABLE](../../../../raw/postgres-14/doc/src/sgml/xfunc.sgml#L1655-L1664) [clauses.c#evaluate_function](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4318-L4357). A row input such as `immutable_fn(col)` prevents that fold, though it can participate in an expression index [indxpath.c#match_index_to_operand](../../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L3737-L3813) [indexcmds.c#index-expression-immutability](../../../../raw/postgres-14/src/backend/commands/indexcmds.c#L1909-L1918).

The `STABLE`/`IMMUTABLE` distinction matters for saved plans. Falsely marking a changing function `IMMUTABLE` can fold a value during planning and reuse that stale value in prepared statements or PL/pgSQL plan caches [xfunc.sgml#saved-plan-volatility-hazard](../../../../raw/postgres-14/doc/src/sgml/xfunc.sgml#L1689-L1700).

For an index runtime key, `ExecReScanIndexScan` recomputes every non-constant key once on each scan or rescan; `ExecIndexEvalRuntimeKeys` evaluates the key expression and stores the resulting scan argument [nodeIndexscan.c#ExecReScanIndexScan](../../../../raw/postgres-14/src/backend/executor/nodeIndexscan.c#L542-L593) [nodeIndexscan.c#ExecIndexEvalRuntimeKeys](../../../../raw/postgres-14/src/backend/executor/nodeIndexscan.c#L596-L652). A parameterized nested-loop index scan can therefore evaluate the key once for each outer-row rescan, not once for the whole statement [indxpath.c#is_pseudo_constant_for_index](../../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L3816-L3831) [nodeNestloop.c#parameterized-inner-rescan](../../../../raw/postgres-14/src/backend/executor/nodeNestloop.c#L100-L153).

### How the planner costs and estimates a function qual

**Cost is an estimate, not a measurement.** `cost_qual_eval_walker` charges every function/operator node in the expression tree and deliberately does not model possible `AND`/`OR` short-circuiting; `add_function_cost` uses a support-function estimate when available or otherwise adds `pg_proc.procost * cpu_operator_cost` to per-tuple cost [costsize.c#cost_qual_eval_walker](../../../../raw/postgres-14/src/backend/optimizer/path/costsize.c#L4412-L4447) [plancat.c#add_function_cost](../../../../raw/postgres-14/src/backend/optimizer/util/plancat.c#L1993-L2050). `CREATE FUNCTION` defaults an omitted `COST` to 1 for C/internal routines and 100 for SQL or procedural-language routines; these values are planner assumptions, not evidence that every non-C call costs exactly 100 times as much [functioncmds.c#function-cost-defaults](../../../../raw/postgres-14/src/backend/commands/functioncmds.c#L1259-L1278) [create_function.sgml#COST](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L462-L476). The `RestrictInfo` caches that estimate, and pseudoconstant cost becomes startup work [costsize.c#eval-cost-cache](../../../../raw/postgres-14/src/backend/optimizer/path/costsize.c#L4367-L4409).

Selectivity estimates determine estimated output rows, while expression cost determines the cost of evaluating the qual. `set_baserel_size_estimates` multiplies relation tuples by clause selectivity and separately stores qual cost; the planner retains cheapest paths by estimated cost [costsize.c#set_baserel_size_estimates](../../../../raw/postgres-14/src/backend/optimizer/path/costsize.c#L4929-L4960) [pathnode.c#set_cheapest](../../../../raw/postgres-14/src/backend/optimizer/util/pathnode.c#L222-L249) [pathnode.c#cheapest-total](../../../../raw/postgres-14/src/backend/optimizer/util/pathnode.c#L320-L365).

- A bare Boolean function qual such as `WHERE f(x)` goes to `function_selectivity`; without a successful support-function estimate, PostgreSQL uses `0.3333333` [clausesel.c#function-clause](../../../../raw/postgres-14/src/backend/optimizer/path/clausesel.c#L890-L904) [plancat.c#function_selectivity](../../../../raw/postgres-14/src/backend/optimizer/util/plancat.c#L1935-L1991).
- An otherwise-unrecognized Boolean expression falls to `boolvarsel`. It can use matching expression statistics; without statistics its default is `0.5` [clausesel.c#boolvarsel-fallback](../../../../raw/postgres-14/src/backend/optimizer/path/clausesel.c#L974-L984) [selfuncs.c#boolvarsel](../../../../raw/postgres-14/src/backend/utils/adt/selfuncs.c#L1501-L1532).
- A function result inside an operator, such as `f(x) = k`, is an `OpExpr` and uses the operator's restriction estimator [clausesel.c#operator-clause](../../../../raw/postgres-14/src/backend/optimizer/path/clausesel.c#L858-L889). A whole-relation `ANALYZE` computes values for expression-index columns from sampled rows; an `ANALYZE` column list skips that expression-index setup. `examine_variable` can exact-match the query expression to a non-partial expression index and load that index column's statistics; partial-index statistics are not used as whole-relation statistics [analyze.c#index-expression-setup](../../../../raw/postgres-14/src/backend/commands/analyze.c#L450-L489) [analyze.c#compute_index_stats](../../../../raw/postgres-14/src/backend/commands/analyze.c#L849-L988) [selfuncs.c#expression-index-statistics](../../../../raw/postgres-14/src/backend/utils/adt/selfuncs.c#L5057-L5183). PostgreSQL 14 can also collect univariate statistics on an expression without creating an index, and `examine_variable` searches those statistics after expression-index statistics [create_statistics.sgml#expression-statistics](../../../../raw/postgres-14/doc/src/sgml/ref/create_statistics.sgml#L47-L56) [selfuncs.c#extended-expression-statistics](../../../../raw/postgres-14/src/backend/utils/adt/selfuncs.c#L5185-L5275).

`ROWS` is not a tuning lever for a function directly in `WHERE`. It applies only to set-returning functions, and `CreateFunction` rejects `ROWS` on a non-set function, while parse analysis rejects a set-returning function in `WHERE` [functioncmds.c#ROWS-default-and-error](../../../../raw/postgres-14/src/backend/commands/functioncmds.c#L1259-L1283) [parse_func.c#EXPR_KIND_WHERE](../../../../raw/postgres-14/src/backend/parser/parse_func.c#L2605-L2620). `ROWS` can matter if a set-returning routine is moved into a legal `FROM` item or subquery, but that is a different plan node [plancat.c#get_function_rows](../../../../raw/postgres-14/src/backend/optimizer/util/plancat.c#L2052-L2110) [createplan.c#create_functionscan_plan](../../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L3687-L3728).

### A function result does not match a plain column index

For a simple-column index, the candidate operand must be a matching `Var`; for an expression index, it must be structurally `equal()` to the stored index expression [indxpath.c#match_index_to_operand](../../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L3737-L3813). Thus `lower(email) = 'a@b.com'` does not use an index on `email` as the search condition. That does not make the plain index universally unusable: PostgreSQL can choose indexes for ordering or covering scans even when a filter is residual [indices.sgml#index-ordering](../../../../raw/postgres-14/doc/src/sgml/indices.sgml#L523-L564) [indices.sgml#index-only-scans](../../../../raw/postgres-14/doc/src/sgml/indices.sgml#L1115-L1146).

A matching expression index stores the derived value. PostgreSQL does not recompute the expression during the indexed search, but computes it for inserts and non-HOT updates [indices.sgml#expression-indexes](../../../../raw/postgres-14/doc/src/sgml/indices.sgml#L785-L795). Index creation runs the expression through `expression_planner` and rejects the result if it contains mutable functions; inserted default arguments and SQL-function inlining therefore affect the immutability check [indexcmds.c#index-expression-immutability](../../../../raw/postgres-14/src/backend/commands/indexcmds.c#L1909-L1918) [clauses.c#contain_mutable_functions_after_planning](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L424-L449). `DefineIndex` has a second rejection: when `check_rights` is set and the invoking role lacks `USAGE` on a type referenced by the index expressions or by the partial-index predicate, the command fails with `permission denied for type` before `index_create` records the type dependencies. Commit `1a358b8f2a2` (CVE-2026-6470) added that check [indexcmds.c#DefineIndex-type-USAGE](../../../../raw/postgres-14/src/backend/commands/indexcmds.c#L927-L942) [dependency.c#check_usage_on_types](../../../../raw/postgres-14/src/backend/catalog/dependency.c#L1740-L1756), and the `privileges` regression test covers it with `CREATE INDEX ON test9a ((a::priv_testdomain1))` [privileges.sql:737](../../../../raw/postgres-14/src/test/regress/sql/privileges.sql#L737) [privileges.out#index-type-USAGE](../../../../raw/postgres-14/src/test/regress/expected/privileges.out#L1109-L1110).

A stored generated column can precompute the value in the table and be indexed separately; its generation expression goes through the same post-planning mutability test [ddl.sgml#generated-columns](../../../../raw/postgres-14/doc/src/sgml/ddl.sgml#L244-L252) [heap.c#generation-expression-immutability](../../../../raw/postgres-14/src/backend/catalog/heap.c#L3198-L3208). Commit `1a358b8f2a2` added the same type-`USAGE` requirement to stored expressions: `AddRelationNewConstraints` checks it for column defaults, generated-column expressions, and `CHECK` constraints whenever the command is not internal, and `StorePartitionKey` checks it for partition-key expressions [heap.c#default-and-generated-type-USAGE](../../../../raw/postgres-14/src/backend/catalog/heap.c#L2753-L2759) [heap.c#check-constraint-type-USAGE](../../../../raw/postgres-14/src/backend/catalog/heap.c#L2800-L2807) [heap.c#partition-key-type-USAGE](../../../../raw/postgres-14/src/backend/catalog/heap.c#L3852-L3860).

There are two important exceptions to “use an expression index.” First, a simple SQL wrapper can inline into an already-indexable expression [clauses.c#inline_function](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4360-L4389). Second, a function's planner `SUPPORT` routine can answer `SupportRequestIndexCondition` and synthesize index quals; `match_funcclause_to_indexcol` invokes it when a function argument matches the index column [indxpath.c#match_funcclause_to_indexcol](../../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L2576-L2619) [indxpath.c#get_index_clause_from_support](../../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L2622-L2679). A derived condition is lossy by default, so the original function still runs as a recheck unless the support function marks the condition as an exact equivalent [supportnodes.h#SupportRequestIndexCondition-lossy](../../../../raw/postgres-14/src/include/nodes/supportnodes.h#L175-L210).

The comparison value on the other side of a normal indexable operator may contain a function if it has no volatile function and no `Var` from the indexed table [indxpath.c#match_opclause_to_indexcol](../../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L2495-L2535). If the expression survives planning as a runtime key, the executor evaluates it once per scan or rescan; an all-constant immutable expression can instead be folded while planning [nodeIndexscan.c#ExecIndexEvalRuntimeKeys](../../../../raw/postgres-14/src/backend/executor/nodeIndexscan.c#L596-L652) [clauses.c#evaluate_function](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4318-L4357).

### Leakproofness, security barriers, and qual ordering

Row-level-security and `security_barrier` conditions enter planner restriction lists at lower `security_level` values than user-supplied quals [initsplan.c#process_security_barrier_quals](../../../../raw/postgres-14/src/backend/optimizer/plan/initsplan.c#L1070-L1126) [pathnodes.h#security_level](../../../../raw/postgres-14/src/include/nodes/pathnodes.h#L2003-L2010). The relevant property is not simply whether a function lacks `LEAKPROOF`: `contain_leaked_vars` asks whether a non-leakproof function receives a current-query `Var`. A non-leakproof call on protected row values must wait, while a no-argument call or a call on constants can still be considered non-leaking for that clause [clauses.c#contain_leaked_vars](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L1208-L1233) [clauses.c#leaked-var-check](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L1273-L1283) [create_function.sgml#LEAKPROOF](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L356-L378).

Two distinct planner decisions use this property:

1. **Pushdown and index eligibility.** `restriction_is_securely_promotable` accepts a clause if it is already at the relation's minimum security level or is leakproof; index-clause matching rejects other clauses. This decision has no cost threshold [restrictinfo.c#restriction_is_securely_promotable](../../../../raw/postgres-14/src/backend/optimizer/util/restrictinfo.c#L390-L409) [indxpath.c#security-promotion-check](../../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L2179-L2195). Security-barrier subquery pushdown likewise rejects leaky calls that receive subquery values [allpaths.c#qual_is_pushdown_safe](../../../../raw/postgres-14/src/backend/optimizer/path/allpaths.c#L3394-L3443).
2. **Runtime order at one plan node.** `order_qual_clauses` sorts by `security_level` and then estimated per-tuple cost; it deliberately ignores selectivity. A leakproof qual is treated as level 0 for this sort only when its cost is **less than** `10 * cpu_operator_cost` [createplan.c#order_qual_clauses](../../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L5191-L5223) [createplan.c#leakproof-cost-cutoff](../../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L5254-L5277) [createplan.c#qual-sort](../../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L5281-L5303).

`LEAKPROOF` is superuser-only and asserts no side effects and no information disclosure through anything except the return value, including value-dependent errors [create_function.sgml#LEAKPROOF](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L356-L378). It is a security contract, not a general-purpose performance switch.

### Parallel safety

A function's `pg_proc.proparallel` category is part of parallel-plan safety [pg_proc.h#PROPARALLEL](../../../../raw/postgres-14/src/include/catalog/pg_proc.h#L167-L174). User-defined functions default to `PARALLEL UNSAFE`, whose presence forces a serial plan; `PARALLEL RESTRICTED` confines execution to the leader [create_function.sgml#PARALLEL](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L425-L457). After checking command type, cursor options, worker availability, and other gates, the planner scans the query tree and permits parallel mode only when the maximum hazard is not `PROPARALLEL_UNSAFE` [planner.c#parallelModeOK](../../../../raw/postgres-14/src/backend/optimizer/plan/planner.c#L315-L352).

A parallel-restricted `WHERE` qual has a narrower but still important effect: PostgreSQL 14 does not defer it above `Gather`, so the planner will not put that table's scan in the parallel portion [parallel.sgml#restricted-WHERE](../../../../raw/postgres-14/doc/src/sgml/parallel.sgml#L581-L591). Falsely marking a function safer can produce errors or wrong answers; C functions can exhibit undefined behavior [create_function.sgml#parallel-label-safety](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L439-L457).

### JIT and function-call observability

`ExecReadyExpr` first asks the JIT provider to compile an expression and otherwise selects the interpreted evaluator [execExpr.c#ExecReadyExpr](../../../../raw/postgres-14/src/backend/executor/execExpr.c#L864-L877). The LLVM path handles ordinary and strict function opcodes directly, while tracked-function opcodes call their out-of-line helpers [llvmjit_expr.c#function-opcodes](../../../../raw/postgres-14/src/backend/jit/llvm/llvmjit_expr.c#L578-L677). JIT can accelerate `WHERE` expression evaluation and inline small C/internal function bodies, but its compilation overhead often exceeds the saving for short queries [jit.sgml#accelerated-operations](../../../../raw/postgres-14/doc/src/sgml/jit.sgml#L46-L78) [jit.sgml#when-to-JIT](../../../../raw/postgres-14/doc/src/sgml/jit.sgml#L95-L129).

The planner enables JIT and its optimization/inlining levels by comparing total estimated plan cost with `jit_above_cost`, `jit_optimize_above_cost`, and `jit_inline_above_cost` [planner.c#jitFlags](../../../../raw/postgres-14/src/backend/optimizer/plan/planner.c#L530-L552). `jit` and all three thresholds are `PGC_USERSET`, so any change is session/transaction-scoped and needs neither reload nor restart [guc.c#jit](../../../../raw/postgres-14/src/backend/utils/misc/guc.c#L2032-L2040) [guc.c#jit-cost-thresholds](../../../../raw/postgres-14/src/backend/utils/misc/guc.c#L3645-L3675). JIT also requires a server built with LLVM support [jit.sgml#JIT-build-boundary](../../../../raw/postgres-14/doc/src/sgml/jit.sgml#L34-L40) [jit.sgml#JIT-availability](../../../../raw/postgres-14/doc/src/sgml/jit.sgml#L132-L138).

For direct call counts and time, `track_functions` can track procedural functions (`pl`) or SQL and C functions too (`all`); the default is `none`, and inlined SQL functions are not tracked [config.sgml#track_functions](../../../../raw/postgres-14/doc/src/sgml/config.sgml#L7717-L7738). Its `PGC_SUSET` definition makes it a superuser-controlled session/transaction setting, with no reload or restart [guc.c#track_functions](../../../../raw/postgres-14/src/backend/utils/misc/guc.c#L4846-L4853). Enabling it is not free: `ExecInitFunc` selects function-usage opcodes, which add start/end accounting around each body call [execExpr.c#function-statistics-opcode-selection](../../../../raw/postgres-14/src/backend/executor/execExpr.c#L2549-L2563) [execExprInterp.c#function-usage-opcodes](../../../../raw/postgres-14/src/backend/executor/execExprInterp.c#L2365-L2418). `pg_stat_user_functions` and `pg_stat_xact_user_functions` expose calls, total time, and self time [system_views.sql#function-statistics-views](../../../../raw/postgres-14/src/backend/catalog/system_views.sql#L1023-L1045) [monitoring.sgml#pg_stat_user_functions](../../../../raw/postgres-14/doc/src/sgml/monitoring.sgml#L4751-L4833).

### Minimizing the overhead

Ordered roughly by leverage.

#### Reduce candidate tuples or pairs first

Prefer a selective index condition or join strategy that prevents tuples or pairs from reaching a residual function. Specialized index/join quals run before general plan quals by placement, while residual quals at one node are ordered by security level and estimated per-tuple cost, not selectivity [pathnodes.h#RestrictInfo-placement](../../../../raw/postgres-14/src/include/nodes/pathnodes.h#L2012-L2021) [createplan.c#order_qual_clauses](../../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L5191-L5223). A materialized view is another precomputation boundary: reads return stored rows directly, while its defining query runs when the view is populated or refreshed. This shifts work to population/refresh and can leave results stale between refreshes [rules.sgml#materialized-views](../../../../raw/postgres-14/doc/src/sgml/rules.sgml#L913-L939).

#### Make a repeated derived search indexable or precomputed

A matching expression index avoids recomputing the function during search; a stored generated column plus an ordinary index stores the derived value in the table as well [indices.sgml#expression-indexes](../../../../raw/postgres-14/doc/src/sgml/indices.sgml#L785-L795) [heap.c#generation-expression-immutability](../../../../raw/postgres-14/src/backend/catalog/heap.c#L3198-L3208). Both require an immutable planned expression. If the immediate problem is only a bad row estimate, expression statistics can improve estimates without index-maintenance overhead, but they do not make the predicate an index search condition or remove runtime calls [create_statistics.sgml#expression-statistics](../../../../raw/postgres-14/doc/src/sgml/ref/create_statistics.sgml#L47-L56) [selfuncs.c#extended-expression-statistics](../../../../raw/postgres-14/src/backend/utils/adt/selfuncs.c#L5185-L5275).

#### Use a one-time form only when semantics allow it

For a genuinely row-independent call embedded in a row-dependent filter, an uncorrelated scalar sub-SELECT can become an `EXPR_SUBLINK` InitPlan whose result is a `PARAM_EXEC` parameter [subselect.c#make_subplan](../../../../raw/postgres-14/src/backend/optimizer/plan/subselect.c#L139-L160) [subselect.c#uncorrelated-EXPR-initplan](../../../../raw/postgres-14/src/backend/optimizer/plan/subselect.c#L375-L410). The executor evaluates that InitPlan lazily when first needed and caches its output; a correlated subquery has `parParam` entries and remains a regular SubPlan [nodeSubplan.c#initplan-parameter-setup](../../../../raw/postgres-14/src/backend/executor/nodeSubplan.c#L853-L876) [nodeSubplan.c#ExecSetParamPlan](../../../../raw/postgres-14/src/backend/executor/nodeSubplan.c#L1051-L1076) [execExprInterp.c#ExecEvalParamExec](../../../../raw/postgres-14/src/backend/executor/execExprInterp.c#L2421-L2441). Wrapping a `VOLATILE` call this way changes repeated-call semantics, so do it only when zero-or-one execution per statement is intended. It is redundant when pseudoconstant gating or an index runtime key already gives the required lifetime.

#### Label volatility correctly

Use the strictest truthful volatility category. This enables constant folding, gating, or index runtime keys as described above; falsely marking a changing value immutable risks stale saved-plan results [xfunc.sgml#volatility](../../../../raw/postgres-14/doc/src/sgml/xfunc.sgml#L1624-L1671) [xfunc.sgml#saved-plan-volatility-hazard](../../../../raw/postgres-14/doc/src/sgml/xfunc.sgml#L1689-L1700). `ALTER FUNCTION ... IMMUTABLE|STABLE|VOLATILE` updates the `pg_proc` catalog tuple; it is not a server GUC and requires no restart or reload [alter_function.sgml#actions](../../../../raw/postgres-14/doc/src/sgml/ref/alter_function.sgml#L35-L57) [functioncmds.c#AlterFunction](../../../../raw/postgres-14/src/backend/commands/functioncmds.c#L1437-L1450) [functioncmds.c#CatalogTupleUpdate](../../../../raw/postgres-14/src/backend/commands/functioncmds.c#L1531-L1532).

#### Mark a function STRICT when null input must imply null output

`STRICT` / `RETURNS NULL ON NULL INPUT` tells PostgreSQL not to execute the body when any argument is null [create_function.sgml#STRICT](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L382-L401). The planner can fold a strict call with a constant-null argument to a null `Const` regardless of the function's volatility, and the executor's strict opcodes skip runtime calls for dynamic nulls [clauses.c#strict-null-fold](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4298-L4316) [execExprInterp.c#EEOP_FUNCEXPR_STRICT](../../../../raw/postgres-14/src/backend/executor/execExprInterp.c#L740-L763). This is correct only when the declared null behavior matches the function.

#### Let simple SQL functions inline

A scalar SQL function that is a simple `SELECT expression` can inline, removing SQL-function call overhead and exposing more constant folding [clauses.c#inline_function](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4360-L4389). Inlining has additional gates: among others, the function cannot be `SECURITY DEFINER`, set-returning, `RECORD`-returning, recursive, configured with a `SET` clause, or needed by an fmgr hook, and the body must preserve the declared volatility and strictness [clauses.c#inline-showstoppers](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4418-L4441) [clauses.c#inline-body-shape](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4540-L4568) [clauses.c#inline-volatility-strictness](../../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L4613-L4630).

#### Set accurate COST; ROWS is not a direct WHERE lever

Set scalar function `COST` to a realistic estimate so path costing and same-security-level residual-qual ordering account for the call [create_function.sgml#COST](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L462-L476) [plancat.c#add_function_cost](../../../../raw/postgres-14/src/backend/optimizer/util/plancat.c#L1993-L2050) [createplan.c#order_qual_clauses](../../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L5191-L5223). `ROWS` is valid only for set-returning functions, which cannot appear directly in `WHERE` [functioncmds.c#ROWS-default-and-error](../../../../raw/postgres-14/src/backend/commands/functioncmds.c#L1259-L1283) [parse_func.c#EXPR_KIND_WHERE](../../../../raw/postgres-14/src/backend/parser/parse_func.c#L2605-L2620).

#### Add a planner SUPPORT function for domain-specific estimates or index conditions

A superuser can attach a `SUPPORT` function [create_function.sgml#SUPPORT](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L491-L502). It can provide selectivity, startup/per-tuple cost, set-returning row estimates in legal SRF contexts, or a derived index condition [supportnodes.h#SupportRequestSelectivity](../../../../raw/postgres-14/src/include/nodes/supportnodes.h#L91-L107) [supportnodes.h#SupportRequestCost](../../../../raw/postgres-14/src/include/nodes/supportnodes.h#L131-L143) [supportnodes.h#SupportRequestRows](../../../../raw/postgres-14/src/include/nodes/supportnodes.h#L158-L169) [supportnodes.h#SupportRequestIndexCondition](../../../../raw/postgres-14/src/include/nodes/supportnodes.h#L175-L240). A lossy derived condition reduces candidates but retains the original function as a recheck [supportnodes.h#SupportRequestIndexCondition-lossy](../../../../raw/postgres-14/src/include/nodes/supportnodes.h#L203-L210).

#### Mark leakproof and parallel-safe only when true

Truthful `LEAKPROOF` metadata can permit security-safe pushdown or index use; truthful `PARALLEL SAFE` metadata can avoid an otherwise serial plan [restrictinfo.c#restriction_is_securely_promotable](../../../../raw/postgres-14/src/backend/optimizer/util/restrictinfo.c#L390-L409) [create_function.sgml#LEAKPROOF](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L356-L378) [create_function.sgml#PARALLEL](../../../../raw/postgres-14/doc/src/sgml/ref/create_function.sgml#L425-L457). Both labels are correctness contracts, not speculative tuning knobs.

#### Measure before changing JIT or tracking settings

Use temporary session/transaction settings when comparing JIT thresholds or enabling `track_functions`; neither requires restart or reload [guc.c#jit](../../../../raw/postgres-14/src/backend/utils/misc/guc.c#L2032-L2040) [guc.c#jit-cost-thresholds](../../../../raw/postgres-14/src/backend/utils/misc/guc.c#L3645-L3675) [guc.c#track_functions](../../../../raw/postgres-14/src/backend/utils/misc/guc.c#L4846-L4853). JIT targets long CPU-bound work, while `track_functions` itself adds accounting and cannot report SQL functions that were inlined [jit.sgml#when-to-JIT](../../../../raw/postgres-14/doc/src/sgml/jit.sgml#L95-L129) [config.sgml#track_functions](../../../../raw/postgres-14/doc/src/sgml/config.sgml#L7717-L7738).

### Extension, generated-catalog, and test boundaries

The routine attributes used by this page live in `pg_proc`: `procost`, `prorows`, `prosupport`, `prokind`, `proleakproof`, `proisstrict`, `proretset`, `provolatile`, and `proparallel` [pg_proc.h#FormData_pg_proc](../../../../raw/postgres-14/src/include/catalog/pg_proc.h#L30-L84). `pg_proc.h` is a catalog source consumed by `Catalog.pm`; the build runs `genbki.pl` over it and generates `pg_proc_d.h` plus the bootstrap catalog data [pg_proc.h#catalog-source](../../../../raw/postgres-14/src/include/catalog/pg_proc.h#L11-L30) [catalog/Makefile#catalog-generation](../../../../raw/postgres-14/src/backend/catalog/Makefile#L50-L75) [catalog/Makefile#genbki](../../../../raw/postgres-14/src/backend/catalog/Makefile#L88-L116). ## Open Questions

- This page establishes mechanisms and qualitative consequences. It does not provide a calls-per-second benchmark, a JIT break-even point, or a sequential-scan-versus-expression-index crossover; those depend on the function body, data distribution, candidate count, cache state, build options, and hardware.
- Minor-release provenance within the PostgreSQL 14 series was not traced, apart from the two 14.24 security commits named above. The page describes behavior at pinned commit `a92fbdfb830046e907813e9067b2c9de9708d600`, not when each mechanism first appeared or changed.
