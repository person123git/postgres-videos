## Answer

### Answer Up Front

PostgreSQL 18 implements [Row-Level Security](../../../glossary.md#row-level-security) during query [rewrite](../../../glossary.md#rewriter), not as a table access method or executor-only feature. For each ordinary or partitioned table range-table entry, the rewriter calls `get_row_security_policies()`, decides whether RLS applies for the RTE's permission-check role (`checkAsUser`, or the current effective role when that OID is invalid) and the `row_security` setting, then injects policy expressions as [range-table entry](../../../glossary.md#range-table) [security quals](../../../glossary.md#security-barrier) (`RangeTblEntry.securityQuals`) for row visibility and as [`WithCheckOption`](../../../glossary.md#withcheckoption) entries for writes.[rowsecurity.c:97-150](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L97-L150) [rewriteHandler.c#fireRIRrules](../../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2224-L2334)

The visibility rule is "OR permissive policies, AND restrictive policies". If RLS applies but no applicable permissive policy supplies a `USING` expression, PostgreSQL adds a constant-false qual. That is the default-deny behavior.[rowsecurity.c#add_security_quals](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L688-L778) Write checks use `WITH CHECK` expressions when present, fall back to `USING` expressions when needed, and create error-producing `WithCheckOption` entries for `INSERT`, `UPDATE`, `ON CONFLICT DO UPDATE`, and `MERGE` actions.[rowsecurity.c#add_with_check_options](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L780-L909) [parsenodes.h#WCOKind](../../../../raw/postgres-18/src/include/nodes/parsenodes.h#L1386-L1404)

The main costs are these:

- walking the policy list and copying policy trees at rewrite;[rowsecurity.c#get_policies_for_relation](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L532-L654) [rowsecurity.c#copy-policy-quals](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L714-L765)
- planning larger OR/AND trees under security-ordering constraints;[createplan.c#order_qual_clauses](../../../../raw/postgres-18/src/backend/optimizer/plan/createplan.c#L5386-L5506)
- estimating opaque functions, and losing column statistics for non-[leakproof](../../../glossary.md#leakproof-function) operators on the protected table;[plancat.c#function_selectivity](../../../../raw/postgres-18/src/backend/optimizer/util/plancat.c#L2055-L2108) [selfuncs.c#statistic_proc_security_check](../../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L6245-L6269)
- policy sublinks, which never become joins;[prepjointree.c#pull_up_sublinks](../../../../raw/postgres-18/src/backend/optimizer/prep/prepjointree.c#L469-L488)
- rebuilding [custom](../../../glossary.md#custom-and-generic-plan) physical plans, and in 18.6 re-rewriting every saved RLS-dependent plan after any role-catalog change or change to the current database's `pg_database` row;[plancache.c#BuildCachedPlan](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1055-L1083) [plancache.c#PlanCacheRoleCallback](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L2290-L2340)
- duplicating parent restrictions across surviving partitions;[inherit.c#apply_child_basequals](../../../../raw/postgres-18/src/backend/optimizer/util/inherit.c#L830-L920)
- taking [`AccessExclusiveLock`](../../../glossary.md#accessexclusivelock) for policy DDL.[policy.c#CreatePolicy-lock](../../../../raw/postgres-18/src/backend/commands/policy.c#L626-L633)

Suitable visibility quals can still become index conditions or partition-pruning steps.[indxpath.c#match_clause_to_index](../../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2586-L2629) [partprune.c#prune_append_rel_partitions](../../../../raw/postgres-18/src/backend/partitioning/partprune.c#L769-L833) Relation policy rows and role-membership expansions are cached, so neither catalog scan is repeated for every policy test.[policy.c#RelationBuildRowSecurity](../../../../raw/postgres-18/src/backend/commands/policy.c#L192-L322) [acl.c#roles_is_member_of-cache](../../../../raw/postgres-18/src/backend/utils/adt/acl.c#L5133-L5170)

The cached query tree of an RLS-dependent [prepared statement](../../../glossary.md#prepared-statement) is still keyed on the current user OID and `row_security`, not on membership edges, `BYPASSRLS`, superuser status, or current-database ownership.[plancache.c#RLS-invalidation](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L718-L725) [acl.c#roles_is_member_of](../../../../raw/postgres-18/src/backend/utils/adt/acl.c#L5209-L5246) [aclchk.c#has_bypassrls_privilege](../../../../raw/postgres-18/src/backend/catalog/aclchk.c#L4188-L4205) PostgreSQL 18.6 adds a second mechanism. `InitPlanCache()` registers `PlanCacheRoleCallback()` on the `AUTHMEMROLEMEM`, `AUTHOID` and `DATABASEOID` [syscaches](../../../glossary.md#syscache). The callback invalidates saved role-dependent plans, so a membership `GRANT`/`REVOKE`, an `inherit_option` change, a `BYPASSRLS` or superuser change, or a current-database ownership change reaches saved plans in a live session.[plancache.c#InitPlanCache](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L146-L164) [plancache.c#PlanCacheRoleCallback](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L2290-L2340) [release-18.sgml#CVE-2026-14666](../../../../raw/postgres-18/doc/src/sgml/release-18.sgml#L669-L687) The callback does not filter by role, so any role-catalog change in the cluster, and any change to the current database's `pg_database` row, also forces saved RLS-dependent plans to be rewritten and replanned. The page's measurement on the pin shows both effects; see [RLS and the plan cache](#rls-and-the-plan-cache).

The only RLS-specific server GUC is `row_security`; it is `PGC_USERSET`, defaults to `on`, and therefore has session or transaction scope, not reload or restart scope.[guc_tables.c#row_security](../../../../raw/postgres-18/src/backend/utils/misc/guc_tables.c#L1697-L1704) Direct related surfaces include table and policy DDL, role membership and `BYPASSRLS`, `security_invoker` views, `row_security_active()`, logical-subscription `run_as_owner`, adjacent `plan_cache_mode` and `enable_partitionwise_aggregate`, catalog/`psql` inspection, and dump/restore options.[pg_class.h#relrowsecurity](../../../../raw/postgres-18/src/include/catalog/pg_class.h#L110-L114) [pg_policy.h#FormData_pg_policy](../../../../raw/postgres-18/src/include/catalog/pg_policy.h#L29-L44) [reloptions.c#security_invoker-registration](../../../../raw/postgres-18/src/backend/access/common/reloptions.c#L141-L149) [rls.c#row_security_active](../../../../raw/postgres-18/src/backend/utils/misc/rls.c#L135-L167) [Settings and Related Surfaces](#settings-and-related-surfaces) states the exact scope and restart impact for each.

The reproducible history audit identifies 24 in-scope corrections or RLS-specific security, operational, performance, metadata, and documentation changes that were not already present in the PostgreSQL 14.0 release. See [Fixes Since PostgreSQL 14](#fixes-since-postgresql-14) and [Context Reviewed](#context-reviewed).

### Implementation Path

RLS starts with table metadata. `pg_class` stores whether a relation has row security enabled and whether owners are forced through policies, and `pg_policy` stores policy name, command, permissive/restrictive mode, role array, `USING` expression, and `WITH CHECK` expression.[pg_class.h#relrowsecurity](../../../../raw/postgres-18/src/include/catalog/pg_class.h#L110-L114) [pg_policy.h#FormData_pg_policy](../../../../raw/postgres-18/src/include/catalog/pg_policy.h#L29-L44)

When the [relcache](../../../glossary.md#relcache) initializes or rebuilds an RLS-enabled relation descriptor, it calls `RelationBuildRowSecurity()`. That function scans `pg_policy`, copies each policy's roles, deserializes its stored expression text with `stringToNode()` into trees in a dedicated `RowSecurityDesc` [memory context](../../../glossary.md#memory-context), and caches whether policy expressions contain sublinks.[relcache.c#RelationBuildRowSecurity-caller](../../../../raw/postgres-18/src/backend/utils/cache/relcache.c#L1265-L1268) [policy.c#RelationBuildRowSecurity](../../../../raw/postgres-18/src/backend/commands/policy.c#L192-L322) The in-memory `RowSecurityPolicy` stores the command kind, permissive flag, roles, policy qual, `WITH CHECK` qual, and sublink marker; `RelationData.rd_rsdesc` holds the relation-level descriptor.[rowsecurity.h#RowSecurityPolicy](../../../../raw/postgres-18/src/include/rewrite/rowsecurity.h#L20-L35) [rel.h#rd_rsdesc](../../../../raw/postgres-18/src/include/utils/rel.h#L111-L120)

`pg_policy.h` is also a build input for [BKI](../../../glossary.md#bki) generation, not only a C struct declaration. It includes the generated `pg_policy_d.h`; the Make and Meson catalog builds pass `pg_policy.h` through `genbki.pl` to produce that header and `postgres.bki`. The generated header supplies catalog, index, and attribute-number constants such as `PolicyRelationId`, `PolicyPolrelidPolnameIndexId`, and `Anum_pg_policy_*` used by `policy.c`.[pg_policy.h#generated-header](../../../../raw/postgres-18/src/include/catalog/pg_policy.h#L18-L56) [catalog/Makefile#generated-headers](../../../../raw/postgres-18/src/include/catalog/Makefile#L16-L88) [catalog/Makefile#genbki](../../../../raw/postgres-18/src/include/catalog/Makefile#L117-L143) [catalog/meson.build:55](../../../../raw/postgres-18/src/include/catalog/meson.build#L55) [catalog/meson.build#generated_catalog_headers](../../../../raw/postgres-18/src/include/catalog/meson.build#L104-L145) [policy.c#generated-catalog-constants](../../../../raw/postgres-18/src/backend/commands/policy.c#L218-L286)

During rewrite, `fireRIRrules()` loops over range-table entries, skips non-table and non-partitioned-table entries, calls `get_row_security_policies()`, prepends the returned security quals to the RTE's list and the returned write checks to `Query.withCheckOptions`, and marks the query if RLS or sublinks are present.[rewriteHandler.c#fireRIRrules](../../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2224-L2334) [rewriteHandler.c#prepend-RLS-quals-and-WCOs](../../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2312-L2322) When a policy expression contains sublinks, rewrite recurses into those sublinks and also locks relations referenced by the sublink query.[rewriteHandler.c#fireRIRrules-sublinks](../../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2259-L2323)

`get_row_security_policies()` returns without policies for anything other than an ordinary or partitioned table, finds the user to check from the RTE permission info, and calls `check_enable_rls()` to classify the relation as no RLS, no RLS but environment-dependent, or RLS enabled.[rowsecurity.c:97-150](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L97-L150) The environment-dependent case (`RLS_NONE_ENV`, used for owners, superusers and `BYPASSRLS` roles) adds no quals but still reports RLS dependence through the `hasRowSecurity` out-parameter, which `fireRIRrules()` copies into `Query.hasRowSecurity`, so a cached plan is invalidated if the role or `row_security` setting later changes.[rowsecurity.c:136-150](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L136-L150) [plancache.c#RLS-invalidation](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L718-L725)

Policy selection is command-specific and can require several passes over the policy list. The query command applies only to the result relation; every other table in the query gets its `SELECT` policies.[rowsecurity.c#result-relation-command](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L153-L165) A `SELECT` with any row-locking clause (`FOR [NO KEY] UPDATE`, `FOR [KEY] SHARE`) first adds `UPDATE` visibility policies.[rowsecurity.c#locking-clause-UPDATE-policies](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L186-L209) `UPDATE`/`DELETE`/`MERGE` add `SELECT` visibility policies when the statement needs SELECT rights. `INSERT` and `UPDATE` add the `SELECT` policies' `USING` expressions as write checks whenever the statement needs SELECT rights on the target: for `UPDATE`, any read of a target column in `WHERE`, `SET` or `RETURNING`; for `INSERT`, `RETURNING`, `ON CONFLICT DO UPDATE`, or `ON CONFLICT DO NOTHING` with an arbiter.[rowsecurity.c#SELECT-rights-WCO](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L284-L301) [create_policy.sgml#SELECT-rights-for-writes](../../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L284-L311) [create_policy.sgml#UPDATE-needs-SELECT](../../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L379-L393) `ON CONFLICT DO UPDATE` adds its UPDATE and SELECT passes, while `MERGE` uses action-specific SELECT, UPDATE, DELETE, and INSERT paths rather than a separate MERGE policy kind.[rowsecurity.c:153-301](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L153-L301) [rowsecurity.c#ON-CONFLICT](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L303-L378) [rowsecurity.c#MERGE](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L381-L514)

PostgreSQL copies the protected RTE's `checkAsUser` into relation permission records inside `Query` nodes found in policy quals and write checks, so relations referenced through those query nodes are permission-checked under that identity.[rowsecurity.c#setRuleCheckAsUser-caller](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L516-L523) [rewriteDefine.c#setRuleCheckAsUser](../../../../raw/postgres-18/src/backend/rewrite/rewriteDefine.c#L612-L671) Policy functions still follow the normal `SECURITY INVOKER` default or `SECURITY DEFINER` rule; the querying identity must otherwise have access to objects referenced by the policy expression.[create_policy.sgml#policy-expression-permissions](../../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L727-L739) [create_function.sgml#SECURITY-INVOKER-DEFINER](../../../../raw/postgres-18/doc/src/sgml/ref/create_function.sgml#L405-L419) Direct or mutual recursion through policy subqueries raises `infinite recursion detected in policy for relation` during rewrite.[rewriteHandler.c#policy-recursion](../../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2257-L2309) [rowsecurity.sql#policy-recursion](../../../../raw/postgres-18/src/test/regress/sql/rowsecurity.sql#L479-L577)

Extensions can add policies through two exported in-process hooks. Permissive hook policies are OR-combined with internal permissive policies, and restrictive hook policies are AND-combined with internal restrictive policies.[rowsecurity.h#hook-API](../../../../raw/postgres-18/src/include/rewrite/rowsecurity.h#L37-L47) [rowsecurity.c#hooks](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L77-L87) [rowsecurity.c#hook-callers](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L608-L653) Hook policies arrive only at rewrite; `pg_policies` and pg_dump read `pg_policy`, so they do not expose or dump hook-provided policies.[system_views.sql#pg_policies](../../../../raw/postgres-18/src/backend/catalog/system_views.sql#L73-L106) [pg_dump.c#getPolicies](../../../../raw/postgres-18/src/bin/pg_dump/pg_dump.c#L4124-L4233) The only in-tree hook assignment is the `src/test/modules/test_rls_hooks` module; no v18 `contrib` module consumes either hook.[test_rls_hooks.c#hooks](../../../../raw/postgres-18/src/test/modules/test_rls_hooks/test_rls_hooks.c#L32-L164) [test_rls_hooks.sql#coverage](../../../../raw/postgres-18/src/test/modules/test_rls_hooks/sql/test_rls_hooks.sql#L20-L161)

### Visibility and Write Checks

For visibility, `add_security_quals()` gathers policy `USING` expressions. It appends restrictive policy expressions as separate ANDed quals, ORs all permissive policy expressions into one qual, and injects a constant-false qual if no applicable permissive policy supplies a `USING` expression.[rowsecurity.c#add_security_quals](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L688-L778)

For writes, `add_with_check_options()` builds [`WithCheckOption`](../../../glossary.md#withcheckoption) (WCO) entries. Permissive policies are combined into one OR expression, restrictive policies become separate checks with policy names for error reporting, and the case with no applicable permissive expression becomes a false check.[rowsecurity.c#add_with_check_options](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L780-L909) The executor evaluates those entries per tuple and suppresses row data in RLS error messages.[execMain.c#ExecWithCheckOptions](../../../../raw/postgres-18/src/backend/executor/execMain.c#L2222-L2370)

Default deny has different visible effects by operation. A false visibility qual makes `SELECT`, `UPDATE`, and `DELETE` find no eligible rows; a false RLS write check rejects a proposed `INSERT` or new `UPDATE` row with an RLS violation. Two paths raise an error instead of skipping an existing row that fails its `USING` check: `INSERT ... ON CONFLICT DO UPDATE` (`WCO_RLS_CONFLICT_CHECK`) and the `UPDATE` and `DELETE` actions of `MERGE` (`WCO_RLS_MERGE_UPDATE_CHECK`, `WCO_RLS_MERGE_DELETE_CHECK`).[rowsecurity.c#ON-CONFLICT](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L303-L378) [rowsecurity.c#MERGE](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L381-L514) [create_policy.sgml#existing-row-errors](../../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L395-L408)[rowsecurity.c#default-deny-visibility](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L767-L777) [rowsecurity.c#default-deny-write-check](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L890-L908) [execMain.c#ExecWithCheckOptions](../../../../raw/postgres-18/src/backend/executor/execMain.c#L2222-L2370)

`INSERT` and `UPDATE` use a policy's `WITH CHECK` expression when it has one and its `USING` expression otherwise; `SELECT`-policy write checks always use `USING` (the `force_using` argument).[rowsecurity.c#QUAL_FOR_WCO](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L808-L811) [rowsecurity.c#INSERT-UPDATE-WCO](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L258-L301) `ON CONFLICT DO UPDATE` uses conflict-check WCOs for update `USING`, adds `SELECT` policies if the statement needs SELECT rights, and then adds update `WITH CHECK` checks.[rowsecurity.c#ON-CONFLICT](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L303-L378) `MERGE` uses the dedicated `WCO_RLS_MERGE_UPDATE_CHECK` and `WCO_RLS_MERGE_DELETE_CHECK` kinds for existing-row checks, while a `MERGE` INSERT action uses the ordinary `WCO_RLS_INSERT_CHECK`; the executor applies an UPDATE or DELETE MERGE check only after that action's `WHEN` qual passes.[parsenodes.h#WCOKind](../../../../raw/postgres-18/src/include/nodes/parsenodes.h#L1386-L1404) [rowsecurity.c#MERGE](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L381-L514) [nodeModifyTable.c#MERGE-WCO](../../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L3168-L3197)

The SQL documentation matches the source rule: `USING` filters visible rows, `WITH CHECK` checks new rows for `INSERT` and `UPDATE`, `WITH CHECK` defaults to the `USING` expression when absent, and policy expressions run before ordinary user conditions except where leakproof functions can move earlier.[create_policy.sgml#USING-WITH-CHECK](../../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L43-L68) [create_policy.sgml#WITH-CHECK-fallback](../../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L85-L93) [ddl.sgml#RLS-expression-order](../../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L2649-L2662)

For INSERT, PostgreSQL runs BEFORE ROW triggers, computes stored generated columns, checks RLS WCOs, and only then checks ordinary and partition constraints; UPDATE follows the same WCO-before-ordinary-constraints boundary after its BEFORE ROW trigger and generated-column work, except that it skips the WCO check when the new row fails the partition constraint and will move to another partition.[nodeModifyTable.c#ExecInsert-check-order](../../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L895-L913) [nodeModifyTable.c#ExecInsert-WCO](../../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L1057-L1107) [nodeModifyTable.c#ExecUpdate-check-order](../../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L2084-L2153) [nodeModifyTable.c#ExecUpdate-WCO](../../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L2194-L2215) [nodeModifyTable.c#ExecUpdate-ExecConstraints](../../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L2285-L2292) A cross-partition UPDATE routes the moved row through `ExecInsert()` and checks it there against the target table's UPDATE policies, remapped to the destination partition's columns; the destination partition's own policies are not used.[nodeModifyTable.c#routed-update-uses-target-policies](../../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L1065-L1083)[execPartition.c#ExecInitPartitionInfo-WCO](../../../../raw/postgres-18/src/backend/executor/execPartition.c#L550-L614) [nodeModifyTable.c#cross-partition-ExecInsert](../../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L2057-L2071) [nodeModifyTable.c#ExecInsert-routed-update-WCO](../../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L1066-L1090)

Policies can reference virtual generated columns, which are new in PostgreSQL 18. The planner expands those columns across the whole query, including security quals, and the regression suite covers `USING` and sublink policies on them.[planner.c:768](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L768) [rowsecurity.sql#virtual-generated-columns](../../../../raw/postgres-18/src/test/regress/sql/rowsecurity.sql#L2080-L2104)

### Policy Storage and DDL

### Scalability and Performance Issues

A fresh analysis and rewrite copies the applicable policy trees, and planning preprocesses each security qual. A valid cached query tree avoids that repeated rewrite work. A changed current user or `row_security` value forces it again, and in 18.6 so does any role-catalog change or change to the current database's `pg_database` row; see [RLS and the plan cache](#rls-and-the-plan-cache).[rowsecurity.c#add_security_quals](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L688-L778) [planner.c#preprocess-securityQuals](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L1059-L1070) [plancache.c#RLS-invalidation](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L718-L725) At execution, RLS visibility expressions can be per-candidate-tuple filters, and write WCO expressions are checked for each proposed tuple of the relevant kind. This is not an unconditional per-row surcharge, because ordinary optimization can turn suitable visibility quals into index conditions or partition-pruning steps.[execMain.c#ExecWithCheckOptions](../../../../raw/postgres-18/src/backend/executor/execMain.c#L2222-L2370) [indxpath.c#match_clause_to_index](../../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2586-L2629) [partprune.c#prune_append_rel_partitions](../../../../raw/postgres-18/src/backend/partitioning/partprune.c#L769-L833)

Policy count affects both tree size and rewrite work. Permissive expressions form one OR tree; restrictive expressions remain separate ANDed quals or WCOs. Each call to `get_policies_for_relation()` walks every cached policy, checks role applicability only for policies whose command matched, sorts matching restrictive policies by name, and calls each extension [hook](../../../glossary.md#hook) that is set. Command-specific layering can call it several times, so complex write statements scale roughly with policy count times policy-selection passes.[rowsecurity.c#get_policies_for_relation](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L532-L654) [rowsecurity.c#command-specific-policy-passes](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L186-L514) [rowsecurity.c#add_with_check_options](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L780-L909) The `pg_policy` scan itself happens when the relcache builds or rebuilds `rd_rsdesc`, not on every rewrite, and repeated `has_privs_of_role()` calls for one role reuse the ACL membership cache.[policy.c#RelationBuildRowSecurity](../../../../raw/postgres-18/src/backend/commands/policy.c#L192-L322) [rowsecurity.c#check_role_for_policy](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L911-L932) [acl.c#roles_is_member_of-cache](../../../../raw/postgres-18/src/backend/utils/adt/acl.c#L5133-L5170)

Security levels constrain predicate order and early index or TID use. A higher-level non-leakproof qual cannot be promoted ahead of lower-level security quals.[restrictinfo.c#restriction_is_securely_promotable](../../../../raw/postgres-18/src/backend/optimizer/util/restrictinfo.c#L415-L434) [tidpath.c:248](../../../../raw/postgres-18/src/backend/optimizer/path/tidpath.c#L248) When quals are ordered for execution, a leakproof qual jumps ahead of lower security levels only if its estimated cost is below 10 × `cpu_operator_cost`.[createplan.c#order_qual_clauses](../../../../raw/postgres-18/src/backend/optimizer/plan/createplan.c#L5386-L5506) [ddl.sgml#RLS-expression-order](../../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L2649-L2662) Policy functions take part in the query's [parallel](../../../glossary.md#parallel-query)-safety walk. Sequential scans charge residual restriction cost against base tuples, while index paths charge residual quals against fetched tuples.[costsize.c#set_baserel_size_estimates](../../../../raw/postgres-18/src/backend/optimizer/path/costsize.c#L5336-L5368) [costsize.c#cost_seqscan](../../../../raw/postgres-18/src/backend/optimizer/path/costsize.c#L295-L360) [costsize.c#cost_index-residual-quals](../../../../raw/postgres-18/src/backend/optimizer/path/costsize.c#L799-L814) An opaque Boolean policy function without planner support gets the default selectivity `0.3333333`. Its estimated execution cost comes from a support function or from `pg_proc.procost * cpu_operator_cost`.[clausesel.c#clause_selectivity_ext-default](../../../../raw/postgres-18/src/backend/optimizer/path/clausesel.c#L863-L876) [plancat.c#function_selectivity](../../../../raw/postgres-18/src/backend/optimizer/util/plancat.c#L2055-L2108) [plancat.c#add_function_cost](../../../../raw/postgres-18/src/backend/optimizer/util/plancat.c#L2111-L2168)

RLS also changes which statistics the planner may use. When a range-table entry carries security quals, `all_rows_selectable()` returns false. The planner then passes `pg_statistic` data ([MCV lists and histograms](../../../glossary.md#most-common-values-and-histogram)) only to leakproof operator functions, and [extended statistics](../../../glossary.md#extended-statistics) skip clauses with non-leakproof operators. Estimates for such operators on an RLS table, in policy quals and user quals alike, fall back to defaults. The regression suite's leaky-operator tests exercise this.[selfuncs.c#examine_variable-acl_ok](../../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L5741-L5754) [selfuncs.c#all_rows_selectable-securityQuals](../../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L6106-L6111) [selfuncs.c#statistic_proc_security_check](../../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L6245-L6269) [extended_stats.c#leakproof-check](../../../../raw/postgres-18/src/backend/statistics/extended_stats.c#L1620-L1661) [rowsecurity.sql#leaky-operator-tests](../../../../raw/postgres-18/src/test/regress/sql/rowsecurity.sql#L2196-L2256) Opaque Boolean helpers and large permissive OR trees can therefore produce inaccurate estimates and poor join or aggregate choices even when enforcement is correct. The planner estimates the remaining OR branches as independent, and within one security level it orders quals by estimated evaluation cost rather than selectivity.[clausesel.c#clauselist_selectivity_or](../../../../raw/postgres-18/src/backend/optimizer/path/clausesel.c#L344-L419) [createplan.c#order_qual_clauses](../../../../raw/postgres-18/src/backend/optimizer/plan/createplan.c#L5386-L5506)

Policy subqueries need relation locking after parse and recursive rewrite.[rewriteHandler.c#fireRIRrules-sublinks](../../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2259-L2323) They never become joins. `pull_up_sublinks()`, which turns `EXISTS` and `ANY` sublinks into semi-joins and anti-joins, walks only the query's join tree. Security quals are preprocessed later as expressions, so the same `EXISTS` or `IN` that could become a join in `WHERE` stays a [SubPlan](../../../glossary.md#subplan) in a policy.[planner.c#pull_up_sublinks-call](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L745-L752) [prepjointree.c#pull_up_sublinks](../../../../raw/postgres-18/src/backend/optimizer/prep/prepjointree.c#L469-L488) [planner.c#preprocess-securityQuals](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L1059-L1070) How often a policy subquery runs depends on its shape:

- uncorrelated scalar, `EXISTS` and array sublinks can become InitPlans;[subselect.c#build_subplan](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L375-L445)
- hashable uncorrelated `ANY` subplans can use a hash table;[subselect.c#ANY-and-materialization](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L511-L539)
- a simple correlated `EXISTS` gets a hashed `ANY` alternative as well, and `setrefs.c` picks the cheaper of the two by estimated executions;[subselect.c#EXISTS-to-ANY-alternative](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L243-L262) [setrefs.c#fix_alternative_subplan](../../../../raw/postgres-18/src/backend/optimizer/plan/setrefs.c#L2155-L2191)
- other correlated subplans run again for each outer tuple.

The documentation's function and subquery policy examples therefore add ordinary function and subquery costs, but not necessarily one full subquery execution per protected row.[ddl.sgml#RLS-subquery-example](../../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L2990-L3007)

[Prepared statements](../../../glossary.md#prepared-statement) can save analysis and rewrite work while an RLS-dependent cached query tree remains valid; only a valid generic physical plan also saves planning. Custom plans copy the rewritten tree and run the [planner](../../../glossary.md#planner) again. For statements with bound parameters, automatic mode tries at least five custom plans before its generic-versus-custom cost decision; statements without parameters always use the generic plan, whatever `plan_cache_mode` says.[plancache.c#RevalidateCachedQuery](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L661-L743) [plancache.c#BuildCachedPlan](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1055-L1083) [plancache.c#choose_custom_plan](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1160-L1213) [plancache.c#GetCachedPlan](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1269-L1373) A change of current user or `row_security` invalidates the RLS-dependent query tree. Inlining a set-returning SQL function in `FROM` marks the generic plan as role-dependent when the inlined query has RLS.[plancache.c#RLS-invalidation](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L718-L725) [clauses.c#inline_set_returning_function-RLS](../../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L5361-L5366) [plancache.c#BuildCachedPlan-role](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1112-L1138) Role-membership, role-attribute and current-database-ownership changes also end that reuse, through the `PlanCacheRoleCallback()` syscache callbacks, and so do unrelated role and database-row changes; see [RLS and the plan cache](#rls-and-the-plan-cache). `DISCARD PLANS` remains a blunt manual tool with session-local scope, not a reload or restart.[plancache.c#PlanCacheRoleCallback](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L2290-L2340) [discard.c#DISCARD_PLANS](../../../../raw/postgres-18/src/backend/commands/discard.c#L27-L41)

Partition expansion translates parent RLS restrictions to children, so large surviving append sets duplicate those restriction trees across child planning.[inherit.c#apply_child_basequals](../../../../raw/postgres-18/src/backend/optimizer/util/inherit.c#L830-L920) Quals on partition keys can shrink the set, but only a policy value that is a constant compared with an immutable operator prunes at plan time. A `STABLE` function value, such as a session setting or a JWT helper, prunes only when the executor starts, and an InitPlan parameter prunes only at scan time.[partprune.c#plan-time-needs-Const](../../../../raw/postgres-18/src/backend/partitioning/partprune.c#L2047-L2061) [partprune.c#exec-param-pruning](../../../../raw/postgres-18/src/backend/partitioning/partprune.c#L2076-L2086) [partprune.c#make_partition_pruneinfo](../../../../raw/postgres-18/src/backend/partitioning/partprune.c#L209-L320) [partprune.c#prune_append_rel_partitions](../../../../raw/postgres-18/src/backend/partitioning/partprune.c#L769-L833)

Policy and table-RLS DDL has high lock impact. `CREATE POLICY`, every form of `ALTER POLICY`, `DROP POLICY`, and `ALTER TABLE ... ROW LEVEL SECURITY` take `AccessExclusiveLock` on the table. That lock conflicts with every standard table [lock mode](../../../glossary.md#lock-mode). Policy DDL closes the table with `NoLock`, so it keeps the lock until transaction end.[policy.c#CreatePolicy-lock](../../../../raw/postgres-18/src/backend/commands/policy.c#L626-L633) [policy.c#CreatePolicy-unlock](../../../../raw/postgres-18/src/backend/commands/policy.c#L747-L762) [policy.c#AlterPolicy-lock](../../../../raw/postgres-18/src/backend/commands/policy.c#L805-L811) [policy.c#rename_policy-lock](../../../../raw/postgres-18/src/backend/commands/policy.c#L1115-L1123) [policy.c#RemovePolicyById](../../../../raw/postgres-18/src/backend/commands/policy.c#L331-L400) [tablecmds.c#AlterTableGetLockLevel-RLS](../../../../raw/postgres-18/src/backend/commands/tablecmds.c#L4717-L4727) [lock.c#LockConflicts](../../../../raw/postgres-18/src/backend/storage/lmgr/lock.c#L65-L105) [table.c#table_close](../../../../raw/postgres-18/src/backend/access/table/table.c#L116-L129)

`COPY TO` under active RLS uses query planning and policy evaluation instead of the direct relation-copy path.[copy.c#DoCopy-RLS](../../../../raw/postgres-18/src/backend/commands/copy.c#L208-L234) `COPY FROM`, logical-replication DML, and initial table synchronization do not evaluate policies per row. They reject the operation when `check_enable_rls()` says RLS applies to the relevant role.[copy.c#DoCopy-COPY-FROM-RLS](../../../../raw/postgres-18/src/backend/commands/copy.c#L230-L234) [worker.c#TargetPrivilegesCheck](../../../../raw/postgres-18/src/backend/replication/logical/worker.c#L2361-L2391) [tablesync.c#initial-copy-role-and-check](../../../../raw/postgres-18/src/backend/replication/logical/tablesync.c#L1512-L1548)

The pinned docs give qualitative guidance only. They call policies based only on the current row's values the simplest and best-performing case, which implies that sub-`SELECT`s and functions cost more. They also warn that using `SELECT ... FOR SHARE` to close the documented policy race can become a problem under heavy row-share locking and frequent updates.[ddl.sgml#RLS-best-performing](../../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L2950-L2960) [ddl.sgml#RLS-row-share-lock](../../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L3046-L3062)

The checkout has no benchmark that quantifies overhead by policy, role, partition, or predicate count. Core and hook tests use `EXPLAIN` without `ANALYZE`, contain no `\timing`, `EXPLAIN (ANALYZE)` or `pg_sleep`, and use at most 100 generated rows in the inheritance, partition and leaky-operator cases.[rowsecurity.sql#EXPLAIN-COSTS-OFF](../../../../raw/postgres-18/src/test/regress/sql/rowsecurity.sql#L133-L142) [test_rls_hooks.sql#EXPLAIN](../../../../raw/postgres-18/src/test/modules/test_rls_hooks/sql/test_rls_hooks.sql#L61-L91) Their 104 `CREATE POLICY` statements (100 in `rowsecurity.sql`, 4 in `test_rls_hooks.sql`) are separate correctness scenarios, not a policy-count workload. This page's [Measurement Script](#measurement-script) counts plan rebuilds and helper calls, not elapsed time, so the page still reports mechanisms rather than an overhead percentage.

### RLS and the plan cache

There is no separate RLS plan cache. PostgreSQL's ordinary caches provide three relevant layers: the relation cache stores parsed policy definitions in `rd_rsdesc`; a `CachedPlanSource` can retain the analyzed and rewritten query tree; and a valid generic `CachedPlan` can retain the physical plan. ### RLS and MultiXact

RLS rewrite itself does not create [MultiXacts](../../../glossary.md#multixact); it returns `USING` quals and write checks.[rowsecurity.c:97-114](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L97-L114) Two concrete ways RLS can add MultiXact work are locking policy subqueries and the foreign-key validation fallback.[nodeLockRows.c#ExecLockRows](../../../../raw/postgres-18/src/backend/executor/nodeLockRows.c#L159-L189) [ri_triggers.c#RI_Initial_Check-RLS](../../../../raw/postgres-18/src/backend/utils/adt/ri_triggers.c#L1555-L1610)

A policy subquery that explicitly locks referenced rows — for example `SELECT ... FOR SHARE` — reaches `ExecLockRows`, which maps `ROW_MARK_SHARE` to `LockTupleShare` and calls `table_tuple_lock`.[nodeLockRows.c#ExecLockRows](../../../../raw/postgres-18/src/backend/executor/nodeLockRows.c#L159-L189) A lone locker stores its plain transaction ID in `xmax`. `heap_lock_tuple()` creates or expands a MultiXact only when `xmax` already holds another in-progress locker or updater, through `MultiXactIdCreate()`/`MultiXactIdExpand()`, so the cost grows with concurrent sessions locking the same referenced rows.[heapam.c#no-previous-locker](../../../../raw/postgres-18/src/backend/access/heap/heapam.c#L5569-L5595)[heapam.c#heap_lock_tuple](../../../../raw/postgres-18/src/backend/access/heap/heapam.c#L5357-L5366) [heapam.c#compute_new_xmax_infomask](../../../../raw/postgres-18/src/backend/access/heap/heapam.c#L5641-L5808) How often that locking subquery runs depends on its sublink shape: a correlated subplan can execute per outer tuple, while an eligible uncorrelated scalar sublink becomes an InitPlan evaluated at most once per occurrence.[subselect.c#build_subplan](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L375-L445)

Foreign-key validation can also fall back from one bulk query to per-row checks. `RI_Initial_Check()` returns false when either table has RLS enabled unless the validating role has `BYPASSRLS` or owns every RLS-enabled table among the referenced and referencing tables, so `validateForeignKeyConstraint()` scans the referencing table and calls `RI_FKey_check_ins()` for each row.[ri_triggers.c#RI_Initial_Check-RLS](../../../../raw/postgres-18/src/backend/utils/adt/ri_triggers.c#L1555-L1610) [tablecmds.c#validateForeignKeyConstraint](../../../../raw/postgres-18/src/backend/commands/tablecmds.c#L13746-L13798) For each row whose key is fully non-null (under `MATCH SIMPLE`, a partly-null key also skips the check), `RI_FKey_check()` builds or reuses a `FOR KEY SHARE` lookup. The [row lock](../../../glossary.md#row-lock) lands on the referenced row the lookup finds, which can reach the same tuple-lock and MultiXact machinery.[ri_triggers.c#RI_FKey_check-null-checks](../../../../raw/postgres-18/src/backend/utils/adt/ri_triggers.c#L287-L352)[ri_triggers.c#RI_FKey_check-query](../../../../raw/postgres-18/src/backend/utils/adt/ri_triggers.c#L369-L426)

Once a MultiXact exists, member lookup returns at once for a lock-only MultiXact older than the backend's oldest visible one, which covers old `FOR SHARE` and `FOR KEY SHARE` MultiXacts. Otherwise it consults a backend-local cache of up to 256 entries that lasts for one transaction, and a miss reads the MultiXact offset and member [SLRUs](../../../glossary.md#slru) through `SimpleLruReadPage`.[multixact.c#old-lock-only-multi](../../../../raw/postgres-18/src/backend/access/transam/multixact.c#L1509-L1520) [multixact.c#cache-per-transaction](../../../../raw/postgres-18/src/backend/access/transam/multixact.c#L1866-L1872)[multixact.c#mXactCacheEnt](../../../../raw/postgres-18/src/backend/access/transam/multixact.c#L378-L403) [multixact.c#GetMultiXactIdMembers-cache](../../../../raw/postgres-18/src/backend/access/transam/multixact.c#L1490-L1510) [multixact.c#GetMultiXactIdMembers-SLRU](../../../../raw/postgres-18/src/backend/access/transam/multixact.c#L1583-L1690)

### RLS and aggregation

RLS can slow aggregation by changing the rows and plan that feed `ExecAgg`; PostgreSQL has no separate RLS aggregate executor.[initsplan.c#process_security_barrier_quals](../../../../raw/postgres-18/src/backend/optimizer/plan/initsplan.c#L1653-L1706) [nodeAgg.c#ExecAgg](../../../../raw/postgres-18/src/backend/executor/nodeAgg.c#L2230-L2274)

`process_security_barrier_quals()` moves RLS `USING` expressions into `baserestrictinfo`.[initsplan.c#process_security_barrier_quals](../../../../raw/postgres-18/src/backend/optimizer/plan/initsplan.c#L1653-L1706) `ExecAgg` then receives the tuples produced by its outer subplan after those restrictions.[nodeAgg.c#ExecAgg](../../../../raw/postgres-18/src/backend/executor/nodeAgg.c#L2230-L2274) Practical mitigations visible in v18 source are:

1. **Make the predicate cheap and indexable.** Because RLS quals live in `baserestrictinfo`, `match_clause_to_index()` can promote securely promotable clauses into index quals, and `check_index_predicates()` can use them to prove a [partial index](../../../glossary.md#partial-index)'s predicate when the policy value is a constant that matches the predicate [indxpath.c#match_clause_to_index](../../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2586-L2629) [indxpath.c#check_index_predicates](../../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L3921-L4059).
2. **Use partitioning and consider `enable_partitionwise_aggregate`.** `prune_append_rel_partitions()` consumes `baserestrictinfo`, so an RLS predicate on the partition key can prune partitions before aggregation. It prunes at plan time only when the policy value is a constant; a `STABLE` function value prunes at executor startup and an InitPlan value at scan time.[partprune.c#plan-time-needs-Const](../../../../raw/postgres-18/src/backend/partitioning/partprune.c#L2047-L2061)[partprune.c#prune_append_rel_partitions](../../../../raw/postgres-18/src/backend/partitioning/partprune.c#L769-L833) `enable_partitionwise_aggregate` is `PGC_USERSET` (session/transaction scope, no reload or restart) and lets the planner consider partitionwise aggregation over a partitioned input when grouping sets are absent. Full partitionwise aggregation needs `GROUP BY` to contain the partition key; otherwise the planner can aggregate partially per partition. RLS quals do not enable it.[planner.c#create_ordinary_grouping_paths-patype](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L4176-L4206)[guc_tables.c#enable_partitionwise_aggregate](../../../../raw/postgres-18/src/backend/utils/misc/guc_tables.c#L952-L961) [planner.c#create_grouping_paths-patype](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L3997-L4010)
3. **Keep policy functions parallel-safe.** The planner's `max_parallel_hazard()` walk descends into `securityQuals`; a parallel-unsafe policy function disables parallel mode for the aggregate query, and a parallel-restricted one prevents a parallel scan of the protected table, and with it partial aggregation over that scan.[allpaths.c#parallel-restricted-quals](../../../../raw/postgres-18/src/backend/optimizer/path/allpaths.c#L744-L754)[planner.c#max_parallel_hazard](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L381-L397) [clauses.c#max_parallel_hazard](../../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L737-L757) [nodeFuncs.c#securityQuals-walk](../../../../raw/postgres-18/src/backend/nodes/nodeFuncs.c#L2864-L2879)
4. **Separate query-tree reuse from physical-plan reuse.** A stable effective role and `row_security` value can preserve the rewritten tree, but only a valid generic plan avoids planning; custom plans still invoke the planner.[plancache.c#RevalidateCachedQuery](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L661-L743) [plancache.c#GetCachedPlan](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1269-L1373)
5. **Do not use `row_security = off` as a shortcut.** For a non-bypass role it raises an error rather than disabling RLS.[rls.c:120-132](../../../../raw/postgres-18/src/backend/utils/misc/rls.c#L120-L132)

Direct aggregates, grouping operations, and window functions are rejected in a policy expression itself; a subquery inside the policy can contain them, with ordinary subquery planning and execution costs; the regression suite has such a policy.[rowsecurity.sql:2111](../../../../raw/postgres-18/src/test/regress/sql/rowsecurity.sql#L2111)[parse_agg.c#aggregate-policy-error](../../../../raw/postgres-18/src/backend/parser/parse_agg.c#L409-L413) [parse_agg.c#window-policy-error](../../../../raw/postgres-18/src/backend/parser/parse_agg.c#L934-L936)

### Do RLS filter conditions need to be in the query?

No, with one exception. PostgreSQL 18 already gives the planner every applicable `USING` expression, so the complete effective visibility predicate does not need to be copied into `WHERE` for the planner to see it. The exception is a policy whose value is known only at run time, such as a `STABLE` function or an InitPlan parameter. A query that also states the same value as a literal (for example `tenant_id = 42`, where 42 is what the policy would compute) gives the planner a constant, which enables plan-time partition pruning, partial-index proofs and a value-specific estimate that the policy alone cannot.[partprune.c#plan-time-needs-Const](../../../../raw/postgres-18/src/backend/partitioning/partprune.c#L2047-L2061) [predtest.c#proof-needs-equal-or-constant](../../../../raw/postgres-18/src/backend/optimizer/util/predtest.c#L1753-L1776) [selfuncs.c#eqsel-Const-vs-non-Const](../../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L244-L290) The literal must equal the policy's value; any other value changes the result.[rewriteHandler.c#fireRIRrules](../../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2224-L2334) [initsplan.c#process_security_barrier_quals](../../../../raw/postgres-18/src/backend/optimizer/plan/initsplan.c#L1653-L1706)

`fireRIRrules()` prepends the returned RLS quals to the range-table entry's `securityQuals` [rewriteHandler.c#fireRIRrules](../../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2224-L2334). `process_security_barrier_quals()` then transfers them into the table's `baserestrictinfo` at successively higher security levels [initsplan.c#process_security_barrier_quals](../../../../raw/postgres-18/src/backend/optimizer/plan/initsplan.c#L1653-L1706). The planner therefore already uses them, subject to the constant rules above, for index paths [indxpath.c#match_clause_to_index](../../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2586-L2629), partial-index proofs [indxpath.c#check_index_predicates](../../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L3921-L4059), and partition pruning [partprune.c#prune_append_rel_partitions](../../../../raw/postgres-18/src/backend/partitioning/partprune.c#L769-L833).

Restating the predicate adds another qual but does not lower the original RLS qual's security level. Restrictive policy sublists are inserted before the permissive OR sublist, successive policy sublists receive increasing security levels, and user-written quals are distributed at the maximum `qual_security_level`.[rowsecurity.c#add_security_quals](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L688-L778) [planner.c#qual_security_level](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L843-L851) [initsplan.c#distribute-user-quals](../../../../raw/postgres-18/src/backend/optimizer/plan/initsplan.c#L1549-L1556) Only genuinely leakproof filters may cross a lower security level, and `LEAKPROOF` is a superuser-set security property rather than a tuning hint.[restrictinfo.c#restriction_is_securely_promotable](../../../../raw/postgres-18/src/backend/optimizer/util/restrictinfo.c#L415-L434) [create_function.sgml#LEAKPROOF](../../../../raw/postgres-18/doc/src/sgml/ref/create_function.sgml#L356-L378) Copying only one branch of a permissive-policy OR is not an optimization of the same condition; it changes which rows the query asks for.[rowsecurity.c#permissive-policy-OR](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L755-L765)

`WITH CHECK` expressions are write-time checks, not read restrictions. The planner preprocesses them separately from `RangeTblEntry.securityQuals`, so an index or pruning predicate needed for reading must come from a `USING` policy or the query, not only from `WITH CHECK`.[planner.c#preprocess-WCOs](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L923-L932) [planner.c#preprocess-securityQuals](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L1059-L1070)

### Wrapping a function in a subquery to evaluate it once

Sometimes. When the wrapper survives planning as an **uncorrelated scalar sublink**, it can remove repeated executor calls. The call-count rule is zero or one InitPlan evaluation per surviving planner occurrence per execution of the outer plan that contains it. That guarantee does not by itself prove the wrapped query is faster, and it is not one global function call per SQL text, transaction, session, or prepared statement.[subselect.c#scalar-InitPlan](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L376-L411) [nodeSubplan.c#lazy-InitPlan](../../../../raw/postgres-18/src/backend/executor/nodeSubplan.c#L1059-L1081) [perform.sgml#initplan-execution](../../../../raw/postgres-18/doc/src/sgml/perform.sgml#L674-L701)

For `(SELECT helper())`, the planner creates a `PARAM_EXEC`, registers the SubPlan as an InitPlan, and replaces that scalar sublink with the parameter. The executor leaves the InitPlan unevaluated until the parameter is first demanded, stores the result in the current `EState`, and clears the parameter's `execPlan` link. Later reads of that parameter reuse the stored value. A new `ExecutorStart` creates a new `EState` and zeroed `PARAM_EXEC` workspace, so each execution of the containing saved or prepared plan starts fresh.[subselect.c#scalar-InitPlan](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L376-L411) [subselect.c#register-InitPlan](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L542-L551) [nodeSubplan.c#mark-InitPlan-unevaluated](../../../../raw/postgres-18/src/backend/executor/nodeSubplan.c#L853-L875) [execExprInterp.c#ExecEvalParamExec](../../../../raw/postgres-18/src/backend/executor/execExprInterp.c#L3056-L3070) [execMain.c#per-execution-PARAM_EXEC](../../../../raw/postgres-18/src/backend/executor/execMain.c#L172-L193) Because evaluation is lazy, an occurrence that is never demanded executes zero times.[nodeSubplan.c#ExecSetParamPlan](../../../../raw/postgres-18/src/backend/executor/nodeSubplan.c#L1059-L1077) Two paths evaluate InitPlans eagerly, still at most once each: a `Gather` evaluates the InitPlan outputs it passes to parallel workers, and `EvalPlanQual` evaluates the parameters its plan tree needs.[execParallel.c#force-initplan-outputs](../../../../raw/postgres-18/src/backend/executor/execParallel.c#L625-L635) [execMain.c#EvalPlanQual-initplans](../../../../raw/postgres-18/src/backend/executor/execMain.c#L3063-L3077)

RLS uses this ordinary planner mechanism. PostgreSQL preprocesses sublinks in both RLS security quals and write checks, but the RLS rewriter first copies stored policy expressions into the generated `securityQuals` and `WithCheckOption` trees.[planner.c#preprocess-WCOs](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L923-L932) [planner.c#preprocess-securityQuals](../../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L1059-L1070) [rowsecurity.c#copy-policy-quals](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L714-L765) [rowsecurity.c#copy-policy-WCOs](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L817-L875) Each surviving `SubLink` node is processed separately, so a policy used in more than one RTE or copied into visibility and write-check layers can produce more than one InitPlan; structurally equal policy quals can also be deduplicated before planning.[subselect.c#SS_process_sublinks](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L2028-L2066) [rowsecurity.c#list_append_unique](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L742-L765) [list.c#list_append_unique](../../../../raw/postgres-18/src/backend/nodes/list.c#L1334-L1349) Wrapping a query-written helper affects only that occurrence; it does not cache a separate bare helper copied from a policy. The regression suite likewise shows one written scalar subquery becoming two InitPlans after pull-up, while another survives as one.[subselect.sql#surviving-sublink-occurrences](../../../../raw/postgres-18/src/test/regress/sql/subselect.sql#L626-L639) [subselect.out#surviving-InitPlans](../../../../raw/postgres-18/src/test/regress/expected/subselect.out#L1156-L1217) A correlated scalar subquery has outer parameters and follows the regular SubPlan path instead, where it can be recomputed for outer rows.[subselect.c#build-parParam](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L347-L374) [subselect.c#correlated-regular-SubPlan](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L488-L540)

The main win is a residual filter. Marking a function `STABLE` promises one result for the same arguments within the statement and permits optimizations, but it does not install a general executor memoization cache. If the bare call remains in a filter evaluated for many candidate tuples, its function opcode runs whenever that expression is evaluated; a lossy bitmap heap scan can also recheck the original qual for every tuple on a lossy page. Replacing the call with an InitPlan parameter avoids those repeated function calls.[xfunc.sgml#function-volatility](../../../../raw/postgres-18/doc/src/sgml/xfunc.sgml#L1612-L1689) [execExprInterp.c#EEOP_FUNCEXPR](../../../../raw/postgres-18/src/backend/executor/execExprInterp.c#L928-L939) [nodeBitmapHeapscan.c#lossy-recheck](../../../../raw/postgres-18/src/backend/executor/nodeBitmapHeapscan.c#L130-L165)

The call count is not monotonically lower in every plan. An index runtime key can demand the InitPlan before a scan that finds no tuples, while a bare residual call is not evaluated when the access method returns no tuple because scan quals run only after a tuple is fetched.[nodeIndexscan.c#ExecReScanIndexScan](../../../../raw/postgres-18/src/backend/executor/nodeIndexscan.c#L541-L570) [execScan.h#ExecScanExtended](../../../../raw/postgres-18/src/include/executor/execScan.h#L160-L224) PostgreSQL's cost model conservatively charges each InitPlan as if it runs once even though the executor may run it later or not at all.[subselect.c#SS_compute_initplan_cost](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L2303-L2338)

An indexed comparison is different. If the qual is securely promotable and its table-side operand, collation, operator family, and nonvolatile comparison side match an index, a value with no Vars from the indexed table can already be an index runtime key.[indxpath.c#match_clause_to_index](../../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2586-L2629) [indxpath.c#match_opclause_to_indexcol](../../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2903-L3014) [indxpath.c#is_pseudo_constant_for_index](../../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L4508-L4535) PostgreSQL evaluates that key when the scan starts and again on a rescan. A non-lossy index clause is also dropped from the scan's residual quals. On an exact scan, the bare helper in that index condition is therefore not called for every candidate tuple.[createplan.c#create_indexscan_plan-residual](../../../../raw/postgres-18/src/backend/optimizer/plan/createplan.c#L3040-L3082)[nodeIndexscan.c#ExecIndexBuildScanKeys](../../../../raw/postgres-18/src/backend/executor/nodeIndexscan.c#L1245-L1305) [nodeIndexscan.c#ExecReScanIndexScan](../../../../raw/postgres-18/src/backend/executor/nodeIndexscan.c#L541-L570) If an index access method reports a lossy match, however, `IndexScan` and `IndexOnlyScan` re-evaluate the original qual for each fetched tuple; a bare helper in that recheck can repeat, while an InitPlan parameter reuses its stored value.[nodeIndexscan.c#lossy-recheck](../../../../raw/postgres-18/src/backend/executor/nodeIndexscan.c#L131-L148) [nodeIndexonlyscan.c#lossy-recheck](../../../../raw/postgres-18/src/backend/executor/nodeIndexonlyscan.c#L197-L208) The wrapper may therefore save no call for one exact scan, but can avoid helper calls during lossy rechecks and recalculation of a bare runtime key across rescans because the uncorrelated InitPlan value remains in the execution's `PARAM_EXEC` slot.[subselect.c#InitPlan-rewind-boundary](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L553-L562)

Wrapping can also worsen estimates. For ordinary equality selectivity, PostgreSQL applies `estimate_expression_value()` to the non-table side, and that estimation mode may execute a bare `STABLE` function and reduce it to a `Const`.[selfuncs.c#get_restriction_variable](../../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L5184-L5230) [clauses.c#estimate_expression_value](../../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L2406-L2438) When the statistics security check permits value comparisons, the constant branch can match most-common values.[selfuncs.c#var_eq_const-MCV](../../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L325-L444) [selfuncs.c#statistic_proc_security_check](../../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L6245-L6269) The wrapped form is a not-yet-known `PARAM_EXEC`; expression estimation substitutes only eligible bound `PARAM_EXTERN` values.[clauses.c#parameter-substitution](../../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L2465-L2552) For a non-unique expression with statistics, the non-constant equality branch averages the non-null fraction over the estimated distinct values and caps that estimate by the largest most-common-value frequency. Unique expressions and no-statistics cases take separate branches.[selfuncs.c#eqsel-Const-vs-non-Const](../../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L244-L290) [selfuncs.c#var_eq_non_const](../../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L469-L545) On a skewed column, losing that value-specific estimate can change the chosen plan. A runtime parameter also generally cannot prove a value-dependent partial-index predicate at planning time.[indxpath.c#check_index_predicates](../../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L3921-L4059) [indices.sgml#partial-index-parameters](../../../../raw/postgres-18/doc/src/sgml/indices.sgml#L983-L1008)

The [Measurement Script](#measurement-script) shows these effects on the pin with a `STABLE` PL/pgSQL helper that raises one notice per call:

| Policy on a 100-row table, run as the policy's role | Helper calls |
|---|---:|
| `rp_helper() = uid`, `EXPLAIN` only | 1 (selectivity estimation while planning) |
| `rp_helper() = uid`, one `SELECT` | 101 (1 while planning, 100 per row) |
| `(SELECT rp_helper()) = uid`, `EXPLAIN` only | 0 |
| `(SELECT rp_helper()) = uid`, one `SELECT` | 1 |
| wrapped policy, self-join (two occurrences) | 2 |
| wrapped policy, forced generic plan, first and second `EXECUTE` | 1 and 1 |
| `IMMUTABLE` helper, bare, forced generic plan, first and second `EXECUTE` | 1 and 0 (folded while planning) |

On a 100,000-row table where half the rows hold one value and the rest spread over 1,000 values, the bare `STABLE` policy `v = rp_helper()` was estimated at 50 rows and returned 50. The wrapped `v = (SELECT rp_helper())` was estimated at 100 rows, the average for a non-constant equality.

Do not use this wrapper merely to suppress calls to a truthfully `VOLATILE` function. InitPlan conversion checks correlation and sublink type, not function volatility, so `(SELECT volatile_helper())` can still become an InitPlan. That changes observable results, errors, or side effects from per-needed-row behavior to lazy zero-or-one behavior; the resulting `Param` can even qualify as an index comparison value although the bare volatile call cannot.[subselect.c#scalar-InitPlan](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L376-L411) [indxpath.c#is_pseudo_constant_for_index](../../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L4508-L4535) [xfunc.sgml#VOLATILE-semantics](../../../../raw/postgres-18/doc/src/sgml/xfunc.sgml#L1621-L1667) The in-tree plan test confirms that an uncorrelated `(SELECT random())` can appear under one InitPlan.[subselect.sql#volatile-scalar-sublink](../../../../raw/postgres-18/src/test/regress/sql/subselect.sql#L631-L633) [subselect.out#volatile-InitPlan](../../../../raw/postgres-18/src/test/regress/expected/subselect.out#L1173-L1185) Conversely, an `IMMUTABLE` call with constant arguments can be folded during planning; a saved plan can then reuse that folded value, so the wrapper does not guarantee one helper call on every execution.[clauses.c#evaluate_function](../../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L4515-L4527) [xfunc.sgml#saved-plan-IMMUTABLE-hazard](../../../../raw/postgres-18/doc/src/sgml/xfunc.sgml#L1677-L1689) Function volatility must describe the helper truthfully; it is not a tuning switch.

Only the scalar subquery's target expression becomes the InitPlan output parameter.[primnodes.h#EXPR_SUBLINK](../../../../raw/postgres-18/src/include/nodes/primnodes.h#L963-L1003) [subselect.c#EXPR_SUBLINK-target](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L397-L411) For example, `(SELECT auth.jwt()) ->> 'claim'` stores the JSON result but leaves extraction in the outer expression, whereas `(SELECT auth.jwt() ->> 'claim')` places both operations in the InitPlan. Outside an index runtime key or another one-time placement, that outer work can still repeat with a residual filter.[execExprInterp.c#ExecEvalParamExec](../../../../raw/postgres-18/src/backend/executor/execExprInterp.c#L3056-L3070) [execExprInterp.c#EEOP_FUNCEXPR](../../../../raw/postgres-18/src/backend/executor/execExprInterp.c#L928-L939)

Wrapping does not grant `EXECUTE`, change which function the subquery calls, or alter that function's `SECURITY INVOKER`/`SECURITY DEFINER` mode or catalog `LEAKPROOF` declaration.[subselect.c#EXPR_SUBLINK-target](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L397-L411) [execExpr.c#ExecInitFunc-ACL](../../../../raw/postgres-18/src/backend/executor/execExpr.c#L2703-L2718) [create_policy.sgml#policy-expression-permissions](../../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L727-L739) [create_function.sgml#LEAKPROOF](../../../../raw/postgres-18/doc/src/sgml/ref/create_function.sgml#L356-L378) [create_function.sgml#SECURITY-INVOKER-DEFINER](../../../../raw/postgres-18/doc/src/sgml/ref/create_function.sgml#L405-L419) Wrapping also does not automatically make the enclosing RLS qual leakproof. In the uncorrelated zero- or constant-argument form here, the helper has no current-level table `Var` beneath it; the comparison operator around `user_id` controls whether that `Var` is passed to a leaky function both before and after sublink replacement. That classification controls secure promotion at nonzero security levels.[clauses.c#contain_leaked_vars](../../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L1276-L1348) [restrictinfo.c#compute-leakproof](../../../../raw/postgres-18/src/backend/optimizer/util/restrictinfo.c#L118-L137) [restrictinfo.c#restriction_is_securely_promotable](../../../../raw/postgres-18/src/backend/optimizer/util/restrictinfo.c#L415-L434)

A general scalar subquery that returns no row produces NULL, while more than one row raises a cardinality violation; the direct `(SELECT helper())` form normally produces exactly one row, whose value may itself be NULL. An RLS predicate admits a row only when its final expression is true, so a NULL comparison does not pass.[nodeSubplan.c#scalar-InitPlan-cardinality](../../../../raw/postgres-18/src/backend/executor/nodeSubplan.c#L1125-L1240) [ddl.sgml#RLS-true-only](../../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L2649-L2661) PostgreSQL charges each InitPlan's startup plus per-call cost to the final paths, and an InitPlan that is not parallel-safe removes partial paths and parallel consideration.[subselect.c#SS_charge_for_initplans](../../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L2236-L2338) Core PostgreSQL 18 does not define `auth.uid()` or `auth.jwt()`, so their volatility, parallel safety, cost, internal token caching, security mode, and side effects must be checked in the installed definitions; that boundary remains under [Open Questions](#open-questions).

### The script

```bash
#!/usr/bin/env bash
# Measurements for the wiki page
#   wiki/v18/questions/server-administration/row-level-security-rls.md
#
# Builds the pinned PostgreSQL 18 checkout out of tree, starts one isolated
# cluster, and measures RLS plan-cache behaviour and InitPlan call counts:
#   plancache  same-role prepared statements across five role-catalog changes
#   overinval  which catalog changes force a saved RLS plan to be rebuilt
#   initplan   helper call counts, bare versus wrapped in a scalar subquery
#   estimate   row estimates on a skewed column, bare versus wrapped
# A helper that raises one NOTICE per call counts executions.  Under a
# forced generic plan, one extra notice on an EXECUTE means the planner ran
# (selectivity estimation calls the STABLE helper once while planning).
#
# Safety: raw/postgres-18 is read only and must be at $PIN with no tracked
# change.  Everything is written under $SANDBOX, which must sit directly in
# .wiki-runtime/tmp and carries a marker file.  The cluster has its own data
# directory, socket directory and port.  Every fixture (tables, roles,
# functions, the database rlsperf) is disposable and not meant for a database
# anyone cares about.
#
# GUCs: port, listen_addresses, unix_socket_directories are postmaster
# context (set once at start); autovacuum is sighup (off, so only this
# script's VACUUM advances datfrozenxid); plan_cache_mode, statement_timeout,
# lock_timeout and row_security are user context, set per session.
#
# Usage: bash .wiki-runtime/tmp/rlsperf.sh [stage ...]
# Stages: build cluster plancache overinval initplan estimate summary stop
#         (default order), plus clean.
set -uo pipefail

PIN=baa7b142aace6821ce085906f314a75bcc4d95c8
WIKI_ROOT=${WIKI_ROOT:-$PWD}
SRC=${SRC:-$WIKI_ROOT/raw/postgres-18}
SANDBOX=${SANDBOX:-$WIKI_ROOT/.wiki-runtime/tmp/rlsperf}
PORT=${PORT:-55482}
JOBS=${JOBS:-8}
INST=$SANDBOX/install
DATA=$SANDBOX/data
SOCK=$SANDBOX/sock
OUT=$SANDBOX/out
MARK=$SANDBOX/.rlsperf-sandbox

die() { echo "rlsperf: $*" >&2; exit 1; }

case "$(cd "$(dirname "$SANDBOX")" 2>/dev/null && pwd)" in
  "$WIKI_ROOT/.wiki-runtime/tmp") ;;
  *) die "SANDBOX must be directly inside $WIKI_ROOT/.wiki-runtime/tmp" ;;
esac

claim() {
  if [ -d "$SANDBOX" ] && [ ! -f "$MARK" ]; then die "$SANDBOX exists without marker"; fi
  mkdir -p "$SANDBOX" "$OUT" "$SOCK" && touch "$MARK"
}

sql() {   # sql <db> : run stdin, session timeouts first
  { echo "SET statement_timeout = '10min'; SET lock_timeout = '30s';"; cat; } |
    "$INST/bin/psql" -X -v ON_ERROR_STOP=1 -h "$SOCK" -p "$PORT" -U postgres -d "$1" 2>&1
}

notices() { grep -c 'rp_helper called' || true; }

record() { echo "$1" | tee -a "$OUT/results.txt"; }

stage_build() {
  claim
  [ "$(git -C "$SRC" rev-parse HEAD)" = "$PIN" ] || die "checkout is not at $PIN"
  [ -z "$(git -C "$SRC" status --porcelain --untracked-files=no)" ] || die "checkout has tracked changes"
  if [ -x "$INST/bin/postgres" ] && [ "$(cat "$INST/PIN" 2>/dev/null)" = "$PIN" ]; then
    echo "build: binaries from $PIN present, skipping"; return
  fi
  mkdir -p "$SANDBOX/build"
  ( cd "$SANDBOX/build" && "$SRC/configure" --prefix="$INST" --without-icu --without-readline ) \
    > "$OUT/configure.log" 2>&1 || die "configure failed"
  make -C "$SANDBOX/build" -j"$JOBS" > "$OUT/make.log" 2>&1 || die "make failed"
  make -C "$SANDBOX/build" install > "$OUT/install.log" 2>&1 || die "install failed"
  echo "$PIN" > "$INST/PIN"
}

stage_cluster() {
  claim
  [ "$(cat "$INST/PIN" 2>/dev/null)" = "$PIN" ] || die "install is not from $PIN"
  stage_stop quiet
  rm -rf "$DATA"; : > "$OUT/results.txt"
  "$INST/bin/initdb" -D "$DATA" -U postgres --locale=C --encoding=UTF8 > "$OUT/initdb.log" 2>&1 || die initdb
  "$INST/bin/pg_ctl" -D "$DATA" -l "$OUT/server.log" -w start \
    -o "-p $PORT -k $SOCK -c listen_addresses= -c autovacuum=off" > /dev/null || die "start failed"
  sql postgres <<'EOF' > "$OUT/cluster.log" || die "cluster setup failed"
CREATE /* wiki_rlsperf_setup */ DATABASE rlsperf;
EOF
  sql rlsperf <<'EOF' >> "$OUT/cluster.log" || die "fixture setup failed"
CREATE /* wiki_rlsperf_setup */ ROLE rp_u LOGIN;
CREATE /* wiki_rlsperf_setup */ ROLE rp_g NOLOGIN;
CREATE /* wiki_rlsperf_setup */ FUNCTION rp_helper() RETURNS int LANGUAGE plpgsql STABLE
  AS $$BEGIN RAISE NOTICE 'rp_helper called'; RETURN 7; END$$;
CREATE /* wiki_rlsperf_setup */ FUNCTION rp_helper_imm() RETURNS int LANGUAGE plpgsql IMMUTABLE
  AS $$BEGIN RAISE NOTICE 'rp_helper called'; RETURN 7; END$$;
GRANT /* wiki_rlsperf_setup */ EXECUTE ON FUNCTION rp_helper(), rp_helper_imm() TO PUBLIC;
EOF
  "$INST/bin/postgres" --version > "$OUT/version.txt"
}

# plancache: one prepared statement per role-catalog change, same effective role.
stage_plancache() {
  sql rlsperf <<'EOF' > "$OUT/plancache.log" || die plancache
DROP TABLE IF EXISTS rp_t;
CREATE /* wiki_rlsperf_plancache */ TABLE rp_t (id int);
INSERT /* wiki_rlsperf_plancache */ INTO rp_t VALUES (1);

# overinval: generic plan; 101 notices = planner ran, 100 = plan reused.
stage_overinval() {
  sql rlsperf <<'EOF' > "$OUT/overinval-setup.log" || die overinval-setup
DROP TABLE IF EXISTS rp_f, rp_hold;
DROP ROLE IF EXISTS rp_unrelated;
CREATE /* wiki_rlsperf_overinval */ TABLE rp_f (id int, uid int);
INSERT /* wiki_rlsperf_overinval */ INTO rp_f SELECT g, g FROM generate_series(1, 100) g;
ALTER TABLE rp_f ENABLE ROW LEVEL SECURITY;
CREATE POLICY p_bare ON rp_f FOR SELECT TO rp_u USING (rp_helper() = uid);
GRANT SELECT ON rp_f TO rp_u;
EOF
  rel=$(sql rlsperf <<'EOF' | grep '^ *rels=' | sed 's/^ *rels=//'
SELECT /* wiki_rlsperf_overinval */ 'rels=' || string_agg(format('%I.%I', n.nspname, c.relname), ', ')
  FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
 WHERE c.relkind IN ('r', 'm') AND c.oid <> 'public.rp_f'::regclass;
EOF
)
  [ -n "$rel" ] || die "no relation list"
  sql rlsperf > "$OUT/overinval.log" <<EOF || die overinval
SET ROLE rp_u; SET plan_cache_mode = force_generic_plan;
PREPARE g AS SELECT /* wiki_rlsperf_overinval */ count(*) FROM rp_f;
\echo STEP first-execute
EXECUTE g;
\echo STEP reuse
EXECUTE g;
RESET ROLE; CREATE ROLE rp_unrelated NOLOGIN; SET ROLE rp_u;
\echo STEP after-create-unrelated-role
EXECUTE g;
RESET ROLE; ALTER ROLE rp_unrelated CONNECTION LIMIT 5; SET ROLE rp_u;
\echo STEP after-alter-unrelated-role
EXECUTE g;
RESET ROLE; ALTER DATABASE postgres CONNECTION LIMIT 50; SET ROLE rp_u;
\echo STEP after-alter-other-database
EXECUTE g;
RESET ROLE; ALTER DATABASE rlsperf CONNECTION LIMIT 50; SET ROLE rp_u;
\echo STEP after-alter-current-database
EXECUTE g;
RESET ROLE;
SELECT /* wiki_rlsperf_overinval */ 'FROZEN before ' || datfrozenxid FROM pg_database WHERE datname = current_database();
VACUUM (FREEZE) $rel;
SELECT /* wiki_rlsperf_overinval */ 'FROZEN after-1 ' || datfrozenxid FROM pg_database WHERE datname = current_database();
SET ROLE rp_u;
\echo STEP after-vacuum-advancing-datfrozenxid
EXECUTE g;
RESET ROLE;
VACUUM (FREEZE) $rel;
SELECT /* wiki_rlsperf_overinval */ 'FROZEN after-2 ' || datfrozenxid FROM pg_database WHERE datname = current_database();
SET ROLE rp_u;
\echo STEP after-vacuum-not-advancing-datfrozenxid
EXECUTE g;
EOF
  count_steps overinval
  grep 'FROZEN' "$OUT/overinval.log" | sed 's/^ */overinval datfrozenxid /' | tee -a "$OUT/results.txt"
}

count_steps() {   # split a log on "STEP name" lines and count notices per step
  local log="$OUT/$1.log" name="" n=0
  while IFS= read -r line; do
    case "$line" in
      STEP\ *) [ -n "$name" ] && record "$1 $name: $n notices"; name=${line#STEP }; n=0 ;;
      *'rp_helper called'*) n=$((n + 1)) ;;
    esac
  done < "$log"
  [ -n "$name" ] && record "$1 $name: $n notices"
}

stage_initplan() {

ALTER POLICY p_bare ON rp_f USING (rp_helper() = uid);
SET ROLE rp_u;
\echo STEP bare-explain-only

\echo STEP bare-select

\echo STEP wrapped-explain-only

\echo STEP wrapped-select

\echo STEP wrapped-two-occurrences
SELECT /* wiki_rlsperf_initplan */ count(*) FROM rp_f a JOIN rp_f b USING (id);
SET plan_cache_mode = force_generic_plan;
PREPARE w AS SELECT /* wiki_rlsperf_initplan */ count(*) FROM rp_f;
\echo STEP wrapped-generic-execute-1
EXECUTE w;
\echo STEP wrapped-generic-execute-2
EXECUTE w;
RESET ROLE;
ALTER POLICY p_bare ON rp_f USING (rp_helper_imm() = uid);
SET ROLE rp_u;
PREPARE im AS SELECT /* wiki_rlsperf_initplan */ count(*) FROM rp_f;
\echo STEP immutable-generic-execute-1

\echo STEP immutable-generic-execute-2
EXECUTE im;

ALTER POLICY p_bare ON rp_f USING (rp_helper() = uid);
EOF
  count_steps initplan
}

# estimate: 100,000 rows, half one value, the rest spread over 1,000 values.
stage_estimate() {
  sql rlsperf > "$OUT/estimate.log" <<'EOF' || die estimate
DROP TABLE IF EXISTS rp_skew;
CREATE /* wiki_rlsperf_estimate */ TABLE rp_skew (id int, v int);
INSERT /* wiki_rlsperf_estimate */ INTO rp_skew
  SELECT g, CASE WHEN g <= 50000 THEN 0 ELSE g % 1000 + 1 END FROM generate_series(1, 100000) g;
ANALYZE rp_skew;
ALTER TABLE rp_skew ENABLE ROW LEVEL SECURITY;
CREATE POLICY p_skew ON rp_skew FOR SELECT TO rp_u USING (v = rp_helper());
GRANT SELECT ON rp_skew TO rp_u;
SET ROLE rp_u;
\echo STEP bare
EXPLAIN SELECT /* wiki_rlsperf_estimate */ * FROM rp_skew;
SELECT /* wiki_rlsperf_estimate */ 'ACTUAL ' || count(*) FROM rp_skew;
RESET ROLE;
ALTER POLICY p_skew ON rp_skew USING (v = (SELECT rp_helper()));
SET ROLE rp_u;
\echo STEP wrapped
EXPLAIN SELECT /* wiki_rlsperf_estimate */ * FROM rp_skew;
EOF
  local name=""
  while IFS= read -r line; do
    case "$line" in
      STEP\ *) name=${line#STEP } ;;
      *'Seq Scan on rp_skew'*) r=${line##*rows=}; record "estimate $name: ${r%% *} rows" ;;
      *ACTUAL*) record "estimate actual rows: ${line##*ACTUAL }" ;;
    esac
  done < "$OUT/estimate.log"
}

stage_summary() {
  { cat "$OUT/version.txt"
    echo "pin $PIN"
    sql rlsperf <<'EOF' | grep '|'
SELECT /* wiki_rlsperf_summary */ current_setting('block_size') AS block_size,
       current_setting('server_version') AS server_version;
EOF
    cat "$OUT/results.txt"
    echo "server log ERROR lines: $(grep -c 'ERROR' "$OUT/server.log" || true)"
  } > "$OUT/summary.txt"
  cat "$OUT/summary.txt"
}

stage_stop() {
  if [ -f "$MARK" ] && [ -f "$DATA/postmaster.pid" ]; then
    "$INST/bin/pg_ctl" -D "$DATA" -m fast -w stop > /dev/null || die "stop failed"
  fi
  [ "${1:-}" = quiet ] && return
  [ -f "$DATA/postmaster.pid" ] && die "postmaster.pid left"
  pgrep -f "$DATA" > /dev/null && die "process naming $DATA left"
  [ -S "$SOCK/.s.PGSQL.$PORT" ] && die "socket left"
  echo "stop: no server, no postmaster.pid, no process, no socket for $PORT"
}

stage_clean() {
  [ -d "$SANDBOX" ] || { echo "clean: nothing to delete"; return; }
  [ -f "$MARK" ] || die "refusing to delete $SANDBOX without marker"
  stage_stop
  rm -rf "$SANDBOX" && echo "clean: deleted $SANDBOX"
}

STAGES=${*:-build cluster plancache overinval initplan estimate summary stop}
for s in $STAGES; do
  case "$s" in build|cluster|plancache|overinval|initplan|estimate|summary|stop|clean) ;;
    *) die "unknown stage $s" ;; esac
done
for s in $STAGES; do "stage_$s" || exit 1; done

A feature inventory would instead add independent RLS-facing additions: `security_invoker` views, `createuser --bypassrls`, the original `run_as_owner` feature, `--no-policies`, PostgreSQL 16's `f1358ca52d` (a non-superuser with `CREATEROLE` and `BYPASSRLS` can grant `BYPASSRLS`), and PostgreSQL 17's `352ea3acf8` (object-access hooks on the RLS subcommands of `ALTER TABLE`). `66ddac6982c` is the separate CVE-2026-2004 restriction on non-built-in selectivity estimators, not an RLS-specific companion fix.
- How often the 18.6 over-invalidation matters in production is workload-dependent and unmeasured. The mechanism and single-event replans are measured on this pin. How often a cluster changes roles, and how often `VACUUM` or autovacuum advances `datfrozenxid` or `datminmxid`, decide the cost, and the checkout has no benchmark for either.[plancache.c#PlanCacheRoleCallback](../../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L2290-L2340)
- The `CREATE ROLE` documentation says table owners "always bypass RLS" in the context of pg_dump, while `check_enable_rls()` applies RLS to an owner when the table has `FORCE ROW LEVEL SECURITY`. Source wins; the doc sentence is narrower than it reads.[create_role.sgml#BYPASSRLS](../../../../raw/postgres-18/doc/src/sgml/ref/create_role.sgml#L205-L221) [rls.c:80-118](../../../../raw/postgres-18/src/backend/utils/misc/rls.c#L80-L118)
- The hook API has no invalidation callback, and hook expressions are copied into the rewritten tree.[rowsecurity.h#hook-API](../../../../raw/postgres-18/src/include/rewrite/rowsecurity.h#L37-L47) [rowsecurity.c#hook-callers](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L608-L653) [rowsecurity.c#copy-hook-visibility-quals](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L716-L753) [rowsecurity.c#copy-hook-write-checks](../../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L828-L870) It follows that an extension whose hook output changes with extension state must arrange plan invalidation or re-prepare, but the static in-tree hook test does not verify that dynamic case.[test_rls_hooks.c#hooks](../../../../raw/postgres-18/src/test/modules/test_rls_hooks/test_rls_hooks.c#L32-L164)
- Core PostgreSQL 18 does not define the example helpers `auth.uid()` or `auth.jwt()`. Their volatility, parallel safety, function cost, selectivity support, security mode, side effects, and whether their own implementation caches a parsed token remain outside this evidence base.
- Exact first-minor-release and complete backpatch matrices are not asserted because the repository has no pinned PostgreSQL 15 or 16 checkouts, the pinned PostgreSQL 17 checkout has no tags or cross-branch refs, and the PostgreSQL 14 checkout has locally unavailable promisor objects. The release-based scope needs only the locally verified PostgreSQL 14.0 baseline and equivalent-commit ancestry.
